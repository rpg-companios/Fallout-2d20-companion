## Крафт — новое окно: квадраты категорий, спойлеры рецептов, выбор количества (патч 318)

Слово владельца: приятности — удобное окно крафта вместо вкладок-верстаков.
Механика не менялась: те же гейты по перкам, подсчёт сумки, проверка навыка
и отчёт (формат 265).

- Кнопка «Крафт» в инвентаре открывает окно квадратов: еда, напитки,
  препараты, взрывчатка, оружие, броня, силовая броня, патроны (решение
  владельца — 8-й квадрат). У каждой — иконка и счётчик «доступно/всего».
- Квадрат открывает список рецептов-спойлеров: недоступные серые, доступные
  белые. Внутри спойлера — материалы по редкости (обычные/необычные/редкие,
  только требуемые типы, у каждого «есть · нужно») и кнопка «Создать».
- Если материалов хватает больше чем на одну штуку — перед созданием окно
  «Вы можете создать N „предмет", сколько штук?» с − и + (по умолчанию 1).
- «Назад» слева сверху — к квадратам из любой категории; «Закрыть» внизу
  окна квадратов — в инвентарь. За один заход можно скрафтить сколько
  угодно разных предметов.
- Категории без рецептов (взрывчатка, броня, силовая броня) видны с пометкой
  «рецептов пока нет» — заполнятся данными, когда появятся рецепты.
- Предохранитель: приёмочный тест (патч 318) — квадраты и порядок, редкость
  материалов на ammo_38, гейт перка, партия, словарь.

## МК-3, шаг 2 — хранилище само пересчитывает производные, ручные вызовы умерли (патч 317)

Продолжение «каскада в хранилище». Для игрока — ничего не поменялось,
все цифры те же. Изменилось внутри: теперь нельзя «забыть пересчитать».

- Любое действие хранилища, меняющее вход (атрибуты, эффекты, перки, черта,
  уровень, ориджин, робо-слоты, зеркало экипировки), автоматически и
  синхронно обновляет производные (ОЗ, инициатива, защита, бонус ближнего
  боя, грузоподъёмность) — одной функцией, теми же формулами 316.
- Удалены все 26 ручных вызовов пересчёта (22 в хранилище, 3 в робо-срезе,
  1 в синхронизации эффектов); действие пересчёта осталось как публичная
  точка принудительного обновления.
- Предохранитель: приёмочный тест (патч 317) — 7 проверок, и ни одна не
  зовёт пересчёт руками: атрибуты, эффекты, перк, робо-слоты, зеркало
  экипировки, форс-точка, отсутствие зацикливания.
- Это фундамент для будущего мастера: когда состояния мира будут приходить
  с сервера, каскад пересчитает цифры сам — забывать нечего.

Иначе это была бы отдельная запись с отдельным id и отдельными
характеристиками».

- Связь переведена на готовый механизм вариантов (как «Опасная бритва» —
  вариант бритвы-переключателя): в записи робо-оружия поле trueItemId, а
  боевых полей больше НЕТ — только личность (id, имя, группа, флаг

  пистолет = Пистолет 10мм с авто-ресивером из коробки.
- Что меняется на экране: у Огнемёта скорострельность 2 → 4 (как у
  людского), проверка атаки по СИЛЕ (была ЛОВКОСТЬ), тип урона
  «энергия» (был «огонь»); у Лазерного резака скорострельность 1 → 2;
  Автоматический 10-мм без изменений (3 урона / 4 выстрела — база
  4/2 плюс авто-ресивер −1/+2). Правка людского оружия теперь едет в
  робо-версию целиком: статы, эффекты, качества, ammo, моды.
- Окно улучшения предлагает робо-версиям все людские моды (как и в 312);
  предпросмотр в окне считает от базы.
- Предохранители: 14 проверок — у варианта не существует собственных
  боевых полей (иначе падает), развёрнутый каталог несёт статы базы и
  СВОЁ имя («Лазерный резак», а не «Лазерный пистолет»), строки экранного
  каталога согласованы, математика авто-ресивера на карточке (замена и
  возврат заводского), худая форма сейва. Сюит 863/863, tsc чист.

## Данные — робо-оружие наследует людские моды по связи в данных; оружие «с модом из коробки» (патч 312)

Слово владельца: Огнемёт Мистера Помощника — это людской Огнемёт;
Лазерный резак — людской Лазерный пистолет; Автоматический 10-мм пистолет —
Пистолет 10мм с установленным авто-ресивером, как оружие с модом в ките
супермутанта.

- Связь живёт в данных: поле baseWeaponId в записи робо-оружия (Огнемёт →
  weapon_flamer, Лазерный резак → weapon_laser_gun, Автоматический 10-мм
  пистолет → weapon_10mm_pistol). Окно улучшения теперь предлагает
  робо-оружию людские моды: Огнемёту — топливо и стволы (6 модов),
  Лазерному резаку — конденсаторы и стволы (21), Автоматическому 10-мм —
  весь набор Пистолета 10мм (28). Правка людского мода едет в робо-версию
  без правки программы.
- «Из коробки»: запись оружия может нести modIds — заводские моды. У
  Автоматического 10-мм это авто-ресивер mod_008: урон 4 → 3,
  скорострельность 3 → 5, качество «Неточный». Карточка показывает мод
  как установленный. Мод игрока в том же слоте снимает заводской; снятие
  всех модов возвращает заводской — это часть сути оружия.
- Предохранители: 10 проверок в
  `__tests__/weapons/robot-weapon-inheritance.test.js` — связи указывают
  на существующие записи (урок мёртвой карты 311), окна улучшения видят
  людские моды, математика авто-ресивера на карточке, замена и возврат
  заводского, худая форма сейва. Сюит 859/859, tsc чист.

## Унификация — моды оружия: одна правда и один путь записи; моды собственной атаки конечности переживают сохранение (патч 311)

Правило владельца: модификация предметов — свойство многих игр, поэтому
форма правды и место записи решаются в движке (универсальный контракт на
TypeScript), сеттинг подставляет каталог модов и хранилища.

- Единая форма правды: экземпляр оружия несёт СПИСОК id модов; карта
  «слот → id» — выводимый вид для экрана (мод сам знает свой слот).
  Двоевластие «список или карта» убрано: приоритет безусловный, пустая
  карта означает «модов нет».
- Один путь записи: окно улучшения больше не выбирает из четырёх веток
  по месту хранения. Место классифицирует движок и отдаёт план (предмет
  инвентаря / надетое оружие человека / ладонь робота / оружие,
  установленное в конечность / собственная атака конечности), экран
  только исполняет план.
- Новое состояние: моды можно ставить на СОБСТВЕННУЮ атаку конечности
  (коготь руки Штурмотрона, Головной лазер родной головы). Раньше окно
  их предлагало, но место в сохранении не было предусмотрено — после
  перезахода в героя моды пропадали. Теперь моды хранятся на самой
  конечности и переживают сохранение; в худой форме сейва появляется
  необязательное поле (старые сейвы читаются как раньше).
- Данные: из кода удалена зашитая карта «робо-оружие наследует людские
  моды» — проверкой по всем файлам данных установлено, что она указывала
  на номерные id, которых в данных нет, и никогда не срабатывала
  (Огнемёт, Лазерный резак и Автоматический 10-мм пистолет никогда не
  наследовали людские моды). Механизм наследования перенесён в данные
  (поле связи в записи робо-оружия); пары «робо-оружие → людское» — на
  решение владельца.
- Убран осиротевший файл-перечень слотов робо-модов: знание «какие моды
  в каких слотах» живёт в описаниях самих модов (переиздание 306 — ручной
  шаг удаления больше не нужен).
- Заперто 15 проверками в `__tests__/robot/weapon-mods-one-truth.test.js`
  (форма правды, план записи на все пять мест хранения, конденсатор
  Mk III на Головном лазере: урон 5 → 6 и обратно, худая форма сейва,
  роли карточек, отсутствие мёртвой карты). Сюит 849/849, tsc чист.

## Установщик патчей — переписан по принципу «истина — в файлах» (патч 309)

Слово владельца: единственный источник истины — реальное содержимое
файлов, проверяемое заново при каждом запуске для каждого патча.
Журнал состояния больше не решает (как и ключи --3way, --mark-through,
--mark, --unmark и вся эвристика угадывания статусов — удалены).
Патч, не проходящий ни одну проверку, откладывается; вердикт выносят
более поздние патчи на тех же файлах или след добавленных строк в
дереве. Остатки отката (git reset не трогает новые файлы будущих
патчей) узнаются по побайтовому совпадению и воссоздаются патчем.
После применения и на повторных запусках проверяется целостность всех
файлов данных: склейки ловятся сразу, с рецептом лечения. Откат
пачки патчей и повторная установка работают без правки истории.
Миграция не нужна: .git/arena-patches.state больше не используется.

## Инструмент — починка склейки «два JSON подряд» в файлах данных (патч 308)

У владельца в рабочем дереве шесть файлов данных оказались склеены:
после полного JSON в каждом — ещё один кусок содержимого. Ни один патч
300–307 эти файлы не трогал (кроме material.json, который патч 303 чинил,
а не ломал); применятель патчей строгий — применяет точно или отказывается
целиком, приклеить в конец ничего не может. Инструмент
tools/fix-double-json.js находит склейки, показывает что склеено,
сохраняет резервную копию .bak и сливает куски: при дублях побеждает
более поздний кусок. Запуск: node tools/fix-double-json.js

## Роботы — Моды на оружие, установленное в конечность (патч 305)

Репорт владельца: лазер-ган из комплекта «assaultron_us_military»
(installTo: 'arm' — оружие является частью руки, ладонь свободна)

в ладонь и в инвентарь, а установленное в конечность оружие живёт внутри

- моды установленного оружия пишутся в его запись внутри конечности

- карточка оружия читает моды из записи — урон и имя считаются с модом;
- запись с модами переживает сохранение и загрузку (формат сейва не

- патч 304 закрыл соседний случай (оружие, зажатое в ладони); этот закрывает
  установленные — теперь оба способа ношения принимают моды.

Заперто проверками в `__tests__/robot/robot-slot-model.test.js`:
карточка читает моды из записи; запись-функция обновляет только нужную
запись, исходная карта не тронута; сейв-цикл сохраняет мод. Сюит 833/833,
tsc чист.

## Роботы — Оружие в ладони получает карточку (патч 304)

Репорт владельца: «на лазер штурмотрона в руке не ставятся моды».
Экипировка в ладонь руки робота разрешена (вес и двуручность проверяются),
но карточки оружия в списке атак не было: смонтированное оружие робота
(«не ручное») выпадало из списка — ставить моды было не на что.

- ладонь показывает всё, что в ней лежит: человеческое оружие, навес
  (arm attachment) и смонтированное оружие робота (Головной лазер);
- единственное исключение — собственная атака самой конечности
  (коготь/манипулятор в старом сейве): её карточку даёт сама конечность,
  дубль из ладони не нужен (заодно закрыт старый дубль карточки когтя);
- цепочка после фикса: карточка → урон с конденсатором (база + мод) →

## Функция — универсальное списание зарядов за выстрел (патч 296)

Расход за выстрел теперь считается механизмом `mechAmmoSpend`
(domain/mechAmmoSpend.js) — суммой условий, и условие бывает двух видов:

- **безусловное** — списывается всегда, без вопросов: пожиратель патронов
  (`ammo-hungry_x`, «тратит X за выстрел»);
- **с запросом** — у условия есть потолок, ячейка списания спрашивает
  «сколько максимум из доступного потратить», и после утверждения
  пользователя списывается указанное количество: конденсатор Головного
  лазера Штурмотрона (`ammoPerAttack`, Mk III–VI = 3–6 зарядов за атаку)
  и заводная рукоятка лазерного мушкета (`crank_x`, 1–4 оборота).

Оружие без особых условий жрёт один заряд за выстрел, как и раньше.
Новое правило расхода = новый читатель в механизме, контракт ячейки не
меняется. Робо-оружие слотов (не предмет инвентаря) теперь тоже списывает
заряды: `spendAmmoForWeapon` получил режим `untrackedWeapon` — списание
без записи износа прочности. Диалог утверждения — в ячейке ПАТРОНЫ
карточки оружия (кнопка «−»).

Заперто 12 проверками в `__tests__/domain/mech-ammo-spend.test.js`
(безусловное, запросы, обрезка потолка доступным,_combo пожиратель+запрос,
Головной лазер с Mk VI из восстановления слота, мушкет с 4-оборотным
конденсатором и без модов).

## Разворот серии — Режим округления: направление диктует сеттинг (патч 284)

> Слово владельца (2026-09-18): «(10+18)×1.15 = 32.2 → 32 — тоже не обязательное состояние. Сеттинг может диктовать, в какую сторону должно быть округление. И может быть и 32 и 33. И например при 32.01 правило будет заставлять округлить в большую или меньшую сторону до целого.»

- Режим округления — часть словаря, а не константа движка. Объявляется на значении: `math` (математическое, 0.5 вверх — по умолчанию), `up` (всегда в большую: 32.01 → 33), `down` (всегда в меньшую: 32.99 → 32), `none` (не округлять — 32.2 остаётся 32.2).
- Фаза конвейера может округлять на своём шаге тем же режимом (`round: true`) или собственным (`round: 'up'`) — правило, у которого шаг и итог округляются по-разному, выразимо.
- Примеры владельца — в тестах дословно: (10+18)×1.15 = 32.2 даёт 32 (математическое), 32 (вниз), 33 (вверх) и 32.2 (без округления) на одной и той же базе; 32.01 по правилу становится 33 или 32. Чистая функция applyPercent тоже принимает режим: 26×1.15 = 29.9 → вниз 29, математически 30.
- Неизвестный режим — ошибка регистрации с перечислением доступных. Тест контракта вырос до 36 проверок; контракт по-прежнему изолирован, в работающей программе ничего не изменилось.

## Разворот серии — Фазы модификаторов: порядок объявляют правила (патч 283)

> Слово владельца (2026-09-18): «Это программа rpg игр. Там есть правила, и как в правилах напишут, так % и будут рассчитываться. [...] Базовая скорострельность будет зависеть от установленных модов, % от черты будет влиять на неё, а перк уже после удваивать. Но может быть и случай, когда черта вместо базовой скорострельности будет увеличивать итоговую [...] А может вообще примениться, если скорострельность будет меньше или равна определённому значению. И это хрен угадаешь.»

- Движок больше не диктует порядок модификаторов — патч 282 зашил жёсткие уровни («проценты только на производных»), патч 283 разворачивает это в словарь: значение объявляет свой конвейер фаз в порядке исполнения (`modifierPhases`), модификатор привязывается к фазе. «Черта +10% базовой» и «черта +10% итоговой» — одно и то же правило с разным местом фазы.
- Новое в словаре: операция-множитель `×` (перк «х2»), условия `when(value)` — «перк действует, только если скорострельность ≤ N», и пофазное округление для правил, округляющих на своём шаге. Модификатор в необъявленную фазу — ошибка с перечислением объявленных фаз.
- Пример владельца про скорострельность целиком в тесте: база 5, моды +1/−2, черта +10%, перк ×2 → 9; якорь наблюдаем через пофазное округление (8 против 9); условный перк включается/выключается порогом.

## Разворот серии — Семантика процентов: всегда от объявленной базы (патч 282)

> Слово владельца (2026-09-18): «% всегда будут от чего-либо. +15% к защите от магии огня будут рассчитываться, как −15% входящего урона от атаки со свойством стихии огня. +15% жизней будут считаться как базовое значение параметра ОЗ (например атр1+атр2) × 1.15, округлённого математически до целого».

- Поправка контракта выводимости (патч 281): процент больше не участвует в аддитивной цепочке параметра. Уровни разделены и не смешиваются: на параметрах (атрибуты, навыки) живут set и аддитивы (перки, раны, броня); на производных (здоровье, манна) живут проценты — база формулы × (1 + Σ%/100) с одним математическим округлением в конце.
- Появилась чистая функция `applyPercent(база, проценты)` — она же обслужит будущие каналы урона: «+15% защиты от магии огня» считается как −15% входящего урона от атаки со свойством огня.
- Нарушения разделения — ошибки контракта, а не молчаливый пересчёт: процент в аддитивной цепочке параметра и аддитив на производном отклоняются с внятным сообщением. Приёмочный тест контракта вырос до 22 проверок, включая оба примера владельца дословно (26 × 1.15 = 29.9 → 30; 100 × 0.85 = 85).

## Инфраструктура — Предохранители TypeScript: покрытие tsconfig и запрет дублей .js/.ts (патч 280)

> Слово владельца (2026-09-17): серию разворачиваем — сначала карта каскада (279), потом предохранители (280), потом контракт выводимости (281), потом тестовый сеттинг (282) и реализация каскада (283+).

- Два храповика на время TS-серии. Первый: каждый `.ts`/`.tsx` репозитория обязан входить в `include` tsconfig — новый TS-файл вне поля типизации роняет тест, как и протухшая запись в include (include только растёт). Второй: запрещены стопки `foo.js` + `foo.ts`/`foo.tsx` в одной папке — сборщик Metro резолвит `.js` первым, и TS-файл оказался бы мёртвым кодом, который «типизирован», но не исполняется.
- Vitest-плагин из патча 274 продлён на `.ts`/`.tsx`: замена `require('<ассет>')` на `{}` работает и там; сам TypeScript трансформирует vite/esbuild, babel не привлекается. Модули на TS заходят в тестовый прогон без отдельной инфраструктуры.
- В устав добавлено правило конверсии: патч-конверсия не меняет поведение; всё, что типизация вскрыла (возможный null, расхождение форм), — отдельный патч-фикс со своим номером и тестом, а не «заодно поменял».

## Обновление — Крафт, часть 1: рецепты как данные (патч 249)

> Первый шаг системы крафта: рецепты поселились в данных как отдельная категория. Игрок пока ничего не видит — скрафчивать начнёт следующий патч, когда движок научится их проверять, списывать и выдавать.

### Что появилось в данных
- В пакете Fallout завелась категория «рецепты»: `modules/fallout/data/crafting/` — пять файлов по тому, что крафт даёт (боеприпасы, взрывчатка, препараты, еда, напитки), и индекс категории. Всего **75 рецептов**: 19 боеприпасов, 9 гранат и мин, 12 препаратов, 27 блюд, 8 напитков.
- Идентификатор рецепта = **id предмета, который он даёт**: «скрафтить ягодные ментаты» — это `chem_mentats_berry`, а не отдельный ключ `craft_chems_berry_mentats`. Второй таблицы соответствий «рецепт ↔ предмет» в программе нет: она была бы вторым источником правды и умерла бы при первом же переименовании. Если один предмет умеют давать несколько рецептов (у книги так у боеприпасов: другой ранг перка — другой рецепт), различие дописывается к id после подчёркивания — например `ammo_45_ammosmith2`; сейчас таких мест нет, все 75 рецептов дают 75 разных предметов.
- Каждый рецепт — только ссылки: что получится (предмет из каталога), из чего (предметы и количество), каким навыком и какой сложности, какая особенность разрешает и с какого ранга, у какого станка делается. Имён, описаний и «названий материалов» в рецептах нет намеренно: имя, вес и цену предмету по-прежнему даёт каталог, а не рецепт.
- Ингредиенты бывают двух видов: выписанные таблицей книги (например, «ягодные ментаты» = Ментаты ×1 + Смоляника ×2 + Редкие материалы ×1) или взятые по печатному правилу «материалы определяет сложность» (с. 210). Вторые помечены в данных, и тест сверяет метку с настоящей кривой сложности — она уже была проставлена на 143 модах оружия, расхождений ноль.
- Боеприпасы крафтятся в том же объёме, в котором находятся: количество берётся из нашей таблицы находки (.38 → 10+5 БК, термоядерное ядро — ровно 1, бросок к ядрам неприменим).
- Ни одно число правила не зашито в данные: длительность работы, 2 ОД, осложнения и «сгорает ли сырьё при провале» — это будущие настройки, а не поля рецепта.

### Чего в этом патче нет и почему
- **Модификации.** Крафт выдаёт предметы; ветка «установить мод на предмет» настраивается отдельно (ваше решение). Колонки сложности/перков/материалов уже проставлены на 205 модах оружия и на модах брони, так что их рецепты переложатся в тот же формат без новых сведений.
- **Дыры в каталоге.** Девять препаратов упираются в ингредиенты, которых у нас нет как предметов (светящийся гриб, хаб-цвет, «Абраксо», мешок с кровью, антисептик, кроволист, шприц берсерка); девять рецептов дротиков шприцера и «верстак-кухня» — в то, что самих этих предметов в каталоге нет. Генератор не придумывает предметы и не решает за владельца, какой книгой их описывать: все 19 таких позиций выгружены в `docs/reference-data/Missing_craft.json` — файл-обменник с полями как у рецептов, где неизвестное записано строкой `unknown`. Владелец дописывает числа по своим книгам и возвращает файл для слияния.
- **Совпадения названий закрыты сразу**, потому что это не новые сведения, а одно и то же, названное иначе: «Tato Juice» = наш «Potato Juice», «Mutant Hound Chops» = наше «Mutant Hound Ribs» (эффект слово в слово), «Mutt Chops» = «Dog Chops», «Queen Mirelurk Meat» = «Mirelurk Queen Meat» — десять соответствий, каждое с причиной в отчёте `docs/reference-data/CRAFTING-MAPPING.md`.
- **Формат сейва и хранилище не тронуты**, экраны тоже: данные пока читает только тест-предохранитель `__tests__/crafting/` (18 проверок: индекс, ссылки, отсутствие имён, кривая материалов, совпадение файлов и обменника с генератором). 737 тестов зелёные, `tsc --noEmit` чистый.

### Как это править дальше
Справочный датасет (`docs/reference-data/pipboyapp_crafting.json`) → `node scripts/build-crafting-data.mjs` → файлы категории `crafting` + отчёт + обменник. Править JSON рецептов руками бесполезно: тест сверяет их с выводом генератора и падает на расхождении.

## Обновление — Переустройство «сердца» игры: единое хранилище, сохранения, паспорта данных (патчи 219–247)

> Большая закулисная работа: всё, что игра помнит о персонаже, переехало в единое хранилище, сохранения стали самостоятельным модулем, у данных и операций появились машинные «описи». Игроку — тише, надёжнее и несколько игровых фиксов; формат сейвов не менялся (старые сейвы загружаются).

### Единое хранилище персонажа (219–243)
- Всё состояние персонажа — профиль (имя, происхождение, черта, уровень), атрибуты/навыки, здоровье/радиация, крышки, инвентарь и надетое, комплект, робот, силовая броня, перки, болезни и состояния, счётчик сцен, временные эффекты, изменённые предметы, отметки «сохранено» — переехало из React-обёртки в единое хранилище (Zustand). Экраны читают и пишут напрямую, без зеркал и посредников.
- Переезд шёл шагами (каждый патч — группа полей, приложение рабочее после каждого), в финале (243) старый файл-«раздатчик» и его обёртка в точке входа удалены целиком — минус ~1300 строк и целый класс ошибок рассинхрона.
- Правила операций закреплены в хранилище: списание возвращает «куплено/отказ с причиной» и не трогает кошелёк при отказе («нельзя купить на больше, чем есть»); все сеттеры принимают и «от текущего значения»; таймер Ядерного блока тикает только при открытом приложении.

### Игровые фиксы и решения по книге (229–241)
- 229 — «фальшивая вода»: битый предмет очищенной воды из старых сейвов чинится при загрузке.
- 230 — предметы без цены в правилах продаются за разумный дефолт, а не за 0.
- 231 — лестница усталости показывает уровень цветом, без текстовых подсказок.
- 232 — усталость по книге: −⌊N/2⌋ текущих ОЗ за игровой час активности; сон из правила исключён (лечение — постелью).
- 237 — схема предмета «база + id модов на предмете»: имя собирает каталог (пример: `weapon_huntingRifle_05_76_48_35` → «.50 длинноствольная охотничья высокоемкая тихая винтовка»); верстак обновляет предмет на месте.
- 238 — подтверждение атрибутов: единая операция с проверкой границ и пересчётом здоровья.
- 239–240 — сцены и время: эффекты тикают от сцен и игровых часов; расходники применяются одной операцией (лечение → радиация → эффекты → риск заражения); превью радиации до применения; «Сопротивляться» болезни — одна попытка в сутки; лечение снижает ранги болезни.
- 241 — «смена комплекта» больше не обнуляет здоровье/радиацию/сцены/условия/журнал доз; tagged-навыки при смене комплекта сохраняются (а полный сброс честно чистит всё).

### Сохранения (242)
- Блокнот сохранений (сохранить/загрузить/список/удалить/автосохранение) — отдельный модуль без привязки к React. Автосейв пишет только уже сохранённого героя, с паузой полсекунды, и не перезаписывает сейв, если ничего не изменилось; облако синхронизируется фоном.

### «Паспорта» данных и операций (244–246, TypeScript)
- У хранилища и формата сейва появились машинные «описи» со строгой проверкой: новое поле или операция без записи в опись роняет контрактный тест — «тихо проскочить мимо» больше нельзя.
- Опись сразу нашла живой дефект (244): журнал «подарки за отмеченные навыки выданы» писался в сейв, но при загрузке не читался — цепочка «сохранился → загрузился → подтвердил навыки» могла вручить стартовые подарки второй раз. Исправлено (формат сейва не тронут).
- 246 — опись операций доведена до полного покрытия (все 98 действий хранилища), введён единый контракт ответа «сделано / отказ с причиной».

### Формат-v2: сейвы без картотеки модов (247)
- Из записи сейвов убрана старая картотека изменённых предметов — дублирующий учёт, оставшийся от прежней схемы (запись прекратилась ещё в 237, теперь ключа в сейве нет вовсе). Ничего видимого не меняется: имя и моды восстанавливаются каталогом из id предмета.
- Мост для старых героев: при загрузке сейва до-237 эпохи содержимое картотеки один раз переносится на сами предметы; записи о потерянных/проданных предметах остаются в read-only картотеке инвентаря. После пересохранения сейв уже без картотеки. Версия схемы и цепочка миграций не тронуты.

## 65 — Уникальные качества (uniq qualities): навешиваемые модификаторы экипировки

- МОДЕЛЬ (владелец): «свойства» экипировки называются **уникальными качествами** (uniq quality, в духе uniq_armor_mods). Качество — навешиваемый модификатор: у него id (учёт/механика) и имя (i18n), имя добавляется к имени предмета: «Дерзкая» + «Формальная шляпа» = «Дерзкая Формальная шляпа». ## 64 — Варианты предметов (trueItemId + modifiers): «Опасная бритва» — не самостоятельный предмет

- МОДЕЛЬ (владелец): бритва — НЕ клон и НЕ отдельное оружие. Это **вариант** выкидного ножа: запись читается как модификаторы —
  `{ "id": "weapon_straight_razor", "trueItemId": "weapon_switchblade", "modifiers": { "replaceOriginalNameTo": "weapon_straight_razor" } }`
  — «истинный id предмета» (механика: статы, качество, моды — всё от ножа) и «перезаписать оригинальное имя» (имя из i18n-ключа: «Опасная бритва» / Straight Razor; в данных имя не хардкодится — только i18n).
- Будущее: `modifiers` поддерживает точечные правки статов — `{ "fireRateModifier": { "op": "+", "value": 1 } }` (поля damage/fireRate/weight/cost/rarity, операции + − × ÷). Быстрый револьвер = револьвер + имя + одна правка, без копирования стат-блока.
- Движок: `expandTrueItems` в domain/packMerge.js разворачивает запись в полную (deep merge с истинным предметом + модификаторы); имя варианта — из i18n каталога. `domain/itemIdentity.js` — единая логика id/стек-ключа.
- Инвентарь: предмет живёт под ИСТИННЫМ id (для программы это нож — моды ножа доступны без алиасов, обвязка catalogSource не нужна). Стек-ключ — простая склейка: id + прочность + моды + имя, без маркеров (`weapon_switchblade_dur_50_mods_mod_113_опасная_бритва`). ЗАКОН стека: два 100% идентичных предмета — один стек; любой отличающийся параметр (прочность, моды, имя) разделяет: бритва и нож — разные стеки, две бритвы — один, меч 50 и меч 100 прочности — разные.
- Случайная прочность (randomWeaponQualityEnabled/rollWeaponDurability): убрано принудительное «никогда не стакается» (уникальный ключ на каждый экземпляр) — теперь два экземпляра с одинаковой прочностью склеиваются (купленные — все 100, один стек).
