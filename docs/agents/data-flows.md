# Потоки данных: как что откуда и куда идёт

> Дополнение к `docs/agents/README.md`. Каждый поток проверен по коду;
> при переезде потока править и этот файл (в том же патче).

## 1. Каталог предметов (источник правды — JSON сеттинга)

```
modules/fallout/data/**/*.json          (механика: id, статы, цены)
modules/fallout/i18n/<локаль>/**.json   (имена/тексты; зеркало объявленных файлов)
        │
        ▼
modules/fallout/index.js                (дверь SETTING: data + names по локалям)
        │
        ├──► domain/registry.js         (единая точка чтения: геттеры, робо-каталог)
        ├──► i18n/equipmentCatalog.js   (слияние данных+имён, робо-оружие → общий пул)
        └──► db/catalogSource.js        (строки «как ряды старой БД»: weapons, mods,
                                         modSlots, perks, items) → экраны/модалки
```

Правила: файл без объявления в двери = файла нет (ошибка, не пустой
список); «вариант» оружия — `trueItemId` (механика от истинного предмета,
имя своё: «Опасная бритва» ← бритва-переключатель).

## 2. Моды оружия (единая правда, патч 311)

```
ФОРМА ПРАВДЫ (src/engine/items/weaponMods.ts):
  экземпляр несёт СПИСОК id модов (modIds);
  карта «слот → id» (appliedMods) — выводимый вид для окна/карточки.
  modIdList()  — читает любую из двух форм (appliedMods приоритетнее);
  modIdMap()   — строит карту по каталогу (мод сам знает свой слот).

ПЛАН ЗАПИСИ (classifyModWritePlan):
  карточка (sourceSlot/attackRole/storeItemId/uniqueId)
        → план: robotSlot{role: held|installed|ownAttack}
              | storeItem | equippedWeapon
  экран (WeaponsAndArmorScreen) только ИСПОЛНЯЕТ план:
    held       → запись оружия в слоте робота (heldWeapon)
    installed  → запись в limb.builtinWeapons (setInstalledWeaponMods)
    ownAttack  → на саму конечность (setOwnWeaponMods, поле ownWeaponMods)
    storeItem  → updateItem (предмет инвентаря)
    equippedWeapon → список надетого оружия человека

ЧТЕНИЕ: domain/enrichItem.js (applyWeaponMods, enrichWeaponItem) — база
из каталога + моды; карточки роботов — domain/robotSlots.js
(materializeWeapon: база + заводские modIds записи + моды экземпляра).
```

## 3. Робо-слоты (анатомия робота — из данных)

```
ДАННЫЕ (modules/fallout/data/equipment/robot/):
  limbs.json        конечности: limbType (arm/head/body/mover),
                    canHoldWeapons, weaponSlots, builtinWeaponId,
                    replaceable, compatibleBodyPlans
  weaponAsLimb.json конечность-оружие (attackId, установка: сложность/
                    перки/навык)
  weapons.json      робо-оружие; trueItemId → ПОЛНЫЙ вариант людского
                    (314): робо-запись несёт только личность (id, имя,
                    weaponType, handheld) и заводские modIds «из коробки»;
                    боевые характеристики — от людской базы
  weapon_mods.json  моды робо-оружия (slot + applies_to_ids — слоты
                    ВЫВОДЯТСЯ из модов; файла-перечня больше нет)

СОСТОЯНИЕ СЛОТА (domain/robotSlots.js):
  худая форма (сейв): { content, armorLayers, heldWeaponId,
                        heldWeaponMods, installedWeapons[],
                        ownWeaponMods? }
  живая форма (экран): { limb, armor, plating, frame, heldWeapon }
  normalizeSlot / serializeSlot / deserializeSlot — мосты; каталог важнее
  экземпляра для механики, экземпляр — для модов/имени.

КАРТОЧКИ АТАК: attacksFromSlot → collectAttacks (instanceKey = слот:
источник:id; дедуп — правило экрана). Роль карточки: attackRole =
held | installed | ownAttack — её читает план записи модов.
```

## 9. Моды брони: крафт → установка → снятие (патчи 341–343)

```
КРАФТ (окно «Крафт», квадрат «Броня»):
  recipes/armor.json (генератор build-crafting-data.mjs)
        │  domain/resolveItem.js case 'armorMod' (каталог armorMods/uniqArmorMods)
        ▼
  мод-ПРЕДМЕТ в сумке (items[instanceKey], weaponId = id мода)

УСТАНОВКА (WeaponsAndArmorScreen → ArmorModificationModal):
  выбор в окне → setEquippedArmor(slot, modifiedItem)  — запись id модов
  на предмет брони (appliedUniqueArmorModId / appliedArmorModId /
  appliedClothingModId; форма правды — см. §1 справочника armor-mods)
        │  ПАРАЛЛЕЛЬНО (343, слово владельца):
        ▼
  installArmorMod({modId, hostKey}) — экземпляр мода в сумке:
    equipped: true (невидим в сумке: selectItemsByEquipped(false),
    вес не задваивается — вес брони уже включает weightModifier)
    installedOn: hostKey (ключ экземпляра носителя, иначе «слот.слой»)
    экземпляра в сумке нет (гейт ВЫКЛ) → null, просто запись на броне

СНЯТИЕ/ЗАМЕНА (окно установки):
  uninstallArmorMod({modId, hostKey}) — equipped: false, installedOn
  стирается → мод снова виден в сумке

РОБО-ОРУЖИЕ (359, тот же закон 343/344): оружие в слоте робота — НЕ предмет
  сумки (комплект кладёт его в конечность), поэтому мод привязывается к
  синтетическому носителю robotWeaponHostKey(слот, id оружия) =
  «robotSlot:слот:id». Экран (ветка robotSlot плана classifyModWritePlan):
  дифф модов → installRobotWeaponMod (как installArmorMod, но без требования
  items[hostKey]) / uninstallArmorMod. Оружие уходит из слота
  (replaceLimb/unequipHeldWeapon) — слайс возвращает его моды в сумку.

УДАЛЕНИЕ НОСИТЕЛЯ — одна копия правила В СТОРЕ (344):
  adjustItemQuantity(itemId, delta) — кнопки «Продать»/«Потратить»/
  «Выбросить» инвентаря (UI-хелпер делегирует) и крафт-расход
  (spendItemStacks, боеприпас spendAmmoForWeapon): при удалении предмета
  collectModsBoundTo уводит его моды («продали предмет с модом —
  ушли оба»); releaseModsBoundTo — действие для будущих точек.
  ПРИВЯЗКА — К ПРЕДМЕТУ (344): id модов пишутся и на слот-копию, и на
  ЭКЗЕМПЛЯР в сумке (updateItem в handleApplyArmorModification) —
  снятие/надевание брони моды не теряет. Слот без ключа экземпляра
  (только старые сохранения/перенос файлом; предметы комплектов создания
  ВСЕГДА имеют экземпляры) — мод не флагается, остаётся видимым (345).

ПАСПОРТ: installedOn — в SAVE_STATE_FIELDS (saveSlimming) и
INSTANCE_FIELDS (resolveItem); действия — в CRUD_OP_KEYS
(characterActions.ts, fuse action-passports).

МОДЫ ОРУЖИЯ (351): тот же закон. Экран модификации оружия исполняет
план classifyModWritePlan; ветки storeItem/equippedWeapon дополнительно
проводят дифф (diffModInstallPlan в domain/modsEquip) через те же
store actions (modIdList — форма правды, appliedMods приоритетен).
Кулаки/isBuiltin без экземпляра в сумке — виртуальный носитель, флага
нет. Робо-ветки (held/installed/ownAttack) флага НЕ получают.
Гейт «Установка модификаций» в WeaponModificationModal: фильтр
modsBySlot по ownedModIds (bag weaponIds) + моды, уже установленные
на этом оружии (иначе не снять).
```

## 10. Фильтры снаряжения: окна добычи/покупки (патчи 425–438, релиз 3)

```
modules/fallout/logic/equipmentFilter.js   (ЧИСТЫЕ функции, без React/stores)
  buildEquipmentFilterOptions(locale, labels)   — варианты панели
  applyEquipmentFilter(item, filter)            — предикат одного предмета
  pruneTreeByEquipmentFilter(tree, filter)      — обрезка дерева категорий
  countFilteredItems(tree, gearOnly) / countFoundItems(tree, labels, active)
components/screens/InventoryScreen/modals/AddItemModal.js  (одно окно =
  добыча loot И покупка buy — selectionMode; фильтр сразу в обоих)
modules/fallout/screens/InventoryScreen/modals/EquipmentFilterModal.js
  (+ styles)  — ОТДЕЛЬНОЕ окно фильтра (429)
public/version.json … /styles/AddItemModal.styles.js (тулбар, черта)
```

Откуда данные: ТОЛЬКО каталоги JSON сеттинга (weapons/armor/powerArmor/
clothes) — «каталог = истина». Границы диапазонов — фактические min/max
по каталогу (редкость 0–6, урон 0–21, скорострельность 0–7, СУ физ 1–4,
эн 0–5, рад 0–2); патроны — уникальные ammoId оружия (списки «a,b»
раскрыты). НИКАКИХ захардкоженных вариантов: добавили предмет в каталог —
он сам появился в фильтре. Подписи ВСЕ через словари i18n (резолвер
tInventory, закон 422): качества/эффекты — data/system/qualities.json и
damageEffects.json; категории-чекбоксы — тот же словарь categories.*
окна; патроны — ammo_types.json. Фолбэков нет: промах ключа = видимый
путь (дефект данных, не молчаливая заглушка).

Почему чекбоксы категорий и отдельное окно (429, слово владельца):
приложение мобильное — список предметов не должен прятаться за
настройками. Кнопка-воронка в одной строке с поиском (427), панель
закреплена над чертой listDivider (прокручивается только список).
В окне фильтра: сначала ТОЛЬКО чекбоксы категорий (Оружие/Броня/
Силовая броня/Одежда — GEAR_KINDS); параметры раскрываются ПОСЛЕ
отметки (слово 429 дословно: «сначала параметры не видно, пока не
выбрана категория»); «Редкость» — общий параметр, тоже после отметки.
Отмечено — показываются параметры только этих видов (showWeapon/
showArmor) и в списке только они. Одежда добавлена четвёртой агентом:
без своей галочки любая отметка прятала бы её молча.

Почему моды НЕ в фильтре и НЕ в результатах (438, слово владельца):
«1 мод может подходить 9 из 11 оружий, а если 11-го оружия нет, то от
мода смысла нет» — моды в результатах НИКОГДА, weaponModsProviding
удалён. Поэтому же качества фильтра — только встречающиеся на оружии
(22 из 32; собираются из каталога, не из словаря): «нельзя отметить,
поскольку такого качества на оружие нет» — иначе пустые отметки давали
бы «Найдено: 0». Что даёт мод — смотрят в экране установки модов,
подписи в списке запрещены (438).

Результаты (430): при активном фильтре — ПЛОСКИЙ отсортированный
список (по алфавиту) с заголовком «Найдено: N», НЕ каталог; каталог
возвращается при пустом фильтре. В плоском списке только снаряжение
(432: «выбрал оружие редкость 6, а показывают боеприпасы, хлам» —
не-снаряжение предикатом проходит всегда, поэтому собирается по
группам явно; Силовая броня тоже — её сначала пропустили). Счётчик
на воронке — activeEquipmentFilterCount (категории + диапазоны + пункты);
кнопка «Показать (N)» — countFoundItems ПО СЛОВАРНЫМ подписям групп
(урок 433: служебные ключи 'weapon' промахивались мимо дерева,
сгруппированного подписями «Оружие» — счётчик вечно 0; ловить такое
может только поведенческий тест на словаре, source-ассерты не ловят).
Кнопка-воронка — иконка MaterialCommunityIcons name="filter", ТОТ ЖЕ
набор, что иконки категорий крафта (437); бейдж #22c55e с числом
условий, пусто — бейджа нет. minWidth: 0 у поиска (436): на вебе
TextInput не сжимался ниже врождённой ширины и выталкивал кнопку за
границу окна.

## 11. Установщик: отсечка, архив правок, язык вывода (426–435)

```
patchs/baseline.json {"baseline": "N"}  — ключевой патч = ПОСЛЕДНИЙ
  (защёлка baseline-cutoff: baseline == старший патч patchs/; переносит
   агент КАЖДЫМ патчем, не вручную)
./apply-patch.sh N:
  цель >= ключевого (428) → БЫСТРЫЙ ПУТЬ: дерево разом приводится к
  состоянию ключевого патча из истории (git archive), патчи до него
  по одному НЕ перебираются — установка свежей версии = 1–2 сек.
  Грязное дерево НЕ блокер (431): все незакоммиченные правки копируются
  в .install-backup/<дата-время>/ (предохранитель; в выводе — список и
  команда отката cp -R .install-backup/<папка>/. .), установка идёт.
  Полный проход остался: нет ключевого патча/истории, старая цель.
```

Почему так: владелец ставит патчи ПРЫЖКАМИ («ставлю сразу всю пачку
исправлений патчем, который считаю достойным») — отсечка это и делает;
коммитит ПАЧКАМИ (435: «не комитить десятками, одним комитом») —
установщику коммиты безразличны, он проверяет содержимое; папку
владельца на реплите ПЛАТФОРМА пересобирает из git и затирает
незакоммиченное (откат = просто повторная установка). Ручной git fetch
НЕ нужен: установщик сам fetch'ит; вручную — только разовый bootstrap
(`git show <ветка>:apply-patch.sh > apply-patch.sh`) когда в папке
лежит УСТАРЕВШИЙ установщик: старый не умеет отсечку и ползёт полным
проходом (замкнутый круг 430-х). Вывод — по-человечески (434, владелец
не программист): «Готово: приложение обновлено до №N» + «Версия
приложения: N (public/version.json)» как доказательство; канцелярит
(«Ничего не нужно», «дерево», «очередь») запрещён защёлками.
ПАТЧ-ФАЙЛ: `git diff <финал ПРЕДЫДУЩЕГО патча> HEAD -- .
':(exclude)patchs/*.patch'` — урок 427: исключать весь patchs/ НЕЛЬЗЯ
(baseline.json там; правка молча не вошла ни в коммит, ни в патч —
поймано клон-верификацией). baseline.json в коммит добавлять ЯВНО.
Верификация патча — клонами: (1) от финала предыдущего патча (быстрый
путь, в логе «Привожу папку сразу…»), (2) от 12ad784 (bootstrap, полный
проход), (3) грязное дерево (архив правок); дерево сверять diff -r до
ЕДИНОГО ФАЙЛА (exclude: .git, node_modules, patchs, .install-backup).

## 12. Сон\Ждать: «Ожидание» (439)

