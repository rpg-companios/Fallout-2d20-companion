## 2. Модель предметной области

**Пакет** = каркас + установленные части. Неделим при снятии: каркас снимается вместе с частями, надевается с ними же и с вставленным блоком. Пакет автономен: блок живёт ВНУТРИ пакета (надет он или лежит в инвентаре — неважно).

**Слои на экране брони:** одежда → броня → силовая броня (сверху). Слой силовой брони: ряд каркаса, под ним 4 ряда частей (шлем / нагрудник / наручи / поножи — как в данных). Часть `arm` — одна на обе руки, `leg` — одна на обе ноги.

**Прочность (ru) / HP (en):** у каждой части `hpCurrent`, максимум — поле `hp` в данных. У каркаса прочности нет.

**Ядерный Блок** — инстанс боеприпаса с полем зарядов `charges`. Максимум зарядов не зашит: считается из конфига броска кубов (см. §3). Подпись в инвентаре: «Ядерный блок (n/max зарядов)».

### 3.3. Константы (домен `domain/powerArmor.js`)
Запись броска — в конвенции проекта (`diceRollsLogic.js`: `rollByType(rollType, rollValue)`): отдельно тип кубика, отдельно количество бросков.
```
PA_CORE_DRAIN_PER_HOUR = 5            // временное значение
FUSION_CORE_CHARGES_ROLL = { rollType: 'rollD20', rollValue: 1 }  // заряды нового блока
```
Генерация зарядов: `rollByType(FUSION_CORE_CHARGES_ROLL.rollType, rollValue)`, результат клампится к `maxCharges` из данных блока (§3.2). Решишь «5d20» — ставишь `rollValue: 5` и `maxCharges: 100` в данных. Никаких карт «тип кубика → грани»: `rollD20` и `rollCD` умеет бросать `diceRollsLogic`, а максимум — данные предмета.

### 3.4. Контракт модификаторов каркаса
Формат — существующая конвенция проекта `<target>Modifier: { op, value }` (препараты: `hpModifier`, `apModifier`; моды оружия: `damageModifier`, `fireRateModifier`...). Операция **`'set'` в проекте уже есть**: моды оружия `{"op": "set", "value": N}` → строгое назначение значения (применение в `modsEquip.js`: при `set` результат = `value`, иначе `base ± value`). Семейство операций — белый список `{ '+', '-', 'set' }`.

Трейты смотрел — у них иной домен (создание персонажа): `modifiers.attributes: { STR: { baseBonus, min, max } }` — это бонусы/лимиты при создании, не рантайм-подмена значения, поэтому их форму не тянем.

Данные каркаса (в `powerArmor.json`, прописаны сразу):
```
"modifiers": { "attributeModifier": { "STR": { "op": "set", "value": 11 } } },
"effects": []   // книжные эффекты каркаса (герметичность и пр.) — тексты добавим позже данными
```
`attributeModifier` — map по имени атрибута (по образцу `damageResistanceModifier` — map по типу урона), семантика `op` — как у модов оружия. Чтение — из одной точки сборки производных характеристик; пока каркас надет, его модификаторы активны.

## 4. Состояние персонажа (в blob `characters.data`)

```
equippedPowerArmor: {
  frame:  { catalogId, appliedMods: {}, core: { charges } | null } | null,
  pieces: { head, body, hands, legs }   // каждый: { catalogId, hpCurrent, appliedMods: {} } | null
}
powerArmorRuntime: { coreAccumulatorMs }  // накопитель расхода, персистентный
```
`appliedMods` — мапа slotType→modId, конвенция инвентарного оружия (не массив): подписи стеков считаются единообразно.

**Пакет в инвентаре** — предмет каркаса с полями `installedPieces` (та же структура `pieces`) и `installedCore`. StackKey каркаса включает подпись установленных частей и заряд блока (по образцу оружия с модами): два каркаса с разными частями или разным зарядом — разные стопки.

**StackKey части (отдельно лежащей):** каталог-id + подпись модов + `hpCurrent`. Битая часть с модами а+б+в ≠ битая с а+б+г; часть 5/10 ≠ 10/10.

**StackKey блока:** `ammo_fusion_core` + заряд. Блок 13/20 ≠ 14/20.

**Новое поле в старых сейвах:** `equippedPowerArmor` добавляется жёстко — при отсутствии поля создаётся пустое через фабрику `createEmptyEquippedPowerArmor()` (по образцу `createEmptyEquippedArmor()`). Это конструирование дефолта нового поля, не нормализатор. Никаких гадающих веток.

## 5. Механика

### 5.1. Надевание каркаса
1. **Политика экипировки брони** — существующий механизм `canEquipArmor(item, character)` (`domain/equipEquip.js` + `ARMOR_POLICIES` в `domain/origins.js`): супермутант получает политику `raiderOnly` → может носить только предметы с флагом `mutantOnly`; робот — `robotOnly` → только робо-броню. Части силовой брони и каркас **не несут** флагов `mutantOnly`/`robotOnly` → под этими политиками запрещены автоматически, без отдельных констант. Экип PA обязан проходить через `canEquipArmor` (комментарий механизма это прямо предусматривает: «standard → standard + power armor»). Причины отказа — существующие i18n-ключи `equip.error.*` (наличие ключей проверить при реализации, добавить при отсутствии).
2. Блок уже внутри пакета (пакет надевался ранее) → надевается молча.
3. Блока внутри нет (первая экипировка): нет заряженного блока в инвентаре → алерт «Нужен Ядерный Блок», каркас НЕ надевается. Блок один или все с одинаковым зарядом → берётся первый из стопки молча. Блоки с разным зарядом → диалог выбора блока.

### 5.2. Надевание частей
- Без надетого каркаса кнопки «Надеть» у частей в инвентаре скрыты/неактивны.
- Часть с `hpCurrent = 0` не надевается (после починки кнопка активна).
- Часть занимает свой слот пакета; замена = старая часть уходит в инвентарь со своим зарядом прочности и модами.

### 5.3. Таймер расхода
- Пока надет каркас с блоком, копится время работы приложения в `coreAccumulatorMs`.
- Каждые накопленные `60 / PA_CORE_DRAIN_PER_HOUR` минут (сейчас 12) списывается 1 заряд.
- Приложение закрыто/свёрнуто → накопитель на паузе (таймер JS в фоне спит — требование выполняется само, фоновые задачи не заводим).
- Перезапуск приложения: накопитель продолжается с сохранённого значения.

### 5.4. Истощение блока (заряд дошёл до 0)
- Блок израсходован и исчезает.
- В инвентаре есть запасные блоки, все с одинаковым зарядом → молча берётся первый.
- Запасные блоки с РАЗНЫМ зарядом → открывается диалог выбора (пакет при этом остаётся надетым). Отмена/закрытие диалога = «блока нет» → см. следующий пункт.
  > РЕШЕНИЕ, требует подтверждения: «молча берёт следующий» трактую как «когда выбор однозначен»; при разных зарядах выбор — по твоему же пожеланию про выбор блока. Если хочешь всегда молча (первый попавшийся) — скажи.
- Запасных блоков нет → пакет (каркас + части) снимается в инвентарь, алерт «Питание исчерпано».

### 5.5. Подавление нижних слоёв
- **Каркас сам по себе НЕ подавляет нижние слои** (одежда/броня под голым каркасом работают).
- Подавляет **часть силовой брони**: надета хотя бы одна часть пакета → параметры одежды и брони скрыты полностью и в расчётах СУ не участвуют.
- Реализация — один флаг `suppressLowerLayers` (есть надетые части пакета). На экране нижние слои при этом не рисуются целиком — тот же принцип «проще = один флаг», что и у кнопки починки (§5.7); флаг уже есть, ничего дополнительно не отслеживаем.

### 5.6. СИЛ
- Пока надет каркас, СИЛ задаётся модификатором каркаса `attributeModifier.STR = { op: 'set', value: 11 }` (§3.4) — не константа в коде механики, а данные.
- Ветки «обесточен, но надет» нет: без питания пакет снимается целиком (§5.4), значит модификатор активен всегда, пока пакет надет.
- **Точки применения** (эффективные атрибуты = `applyFrameAttributeModifiers(база, каталог-каркас)`): ① `src/store/resolvers.js` — производные в сторе (`calculateDerivedStats` получает `powerArmorFrameId` через `setCharacterContext`); ② `CharacterScreen` — отображаемые атрибуты (режим перка редактирует натуральную базу и не трогается); ③ `WeaponsAndArmorScreen` — локальные боксы инициативы/защиты/бонуса ближнего боя и здоровья. Натуральные атрибуты в сторе и снапшоте не изменяются ни в одной точке; вне перечисленных локальный пересчёт атрибутов — отложенная тема (дорожная карта состояния).

### 5.7. Прочность и починка
- На экране брони у каждой части пакета строка «Прочность: n/max» с кнопками `−` / `+` (шаг 1, в пределах 0..max).
- Прочность достигла 0 (через `−`) → часть автоматически снимается в инвентарь.
- Кнопка «Починить» рендерится по ОДНОМУ условию `hpCurrent < max` (инвентарь и экран). После починки `hpCurrent = max` → условие перестаёт выполняться → кнопка просто перестаёт рисоваться. Никакого отдельного состояния «починено» и дополнительного отслеживания.

## 6. UI-спецификация

- **Каталог**: новая категория «Силовая броня»; `equipmentCatalog.js` подключает `powerArmor.json` (данные сейчас не подключены) и i18n-файлы ru/en. Каркас и комплекты — группы внутри категории.
- **Экран «Оружие и броня»**: слой `powerArmor` выше слоёв одежда/броня: ряд каркаса, 4 ряда частей (шлем, нагрудник, наручи, поножи) со строкой прочности и кнопками; поле эффектов показывает эффекты каркаса + строку «Ядерный блок: n/max» активного блока.
- **Инвентарь**: у частей — кнопка «Надеть» только при надетом каркасе (и hp > 0), «Починить» при hp < max; у каркаса — «Надеть» с проверками §5.1; блоки — с подписью заряда.
- **Диалог выбора блока**: список «Ядерный блок (n/max)» из инвентаря; используется при первой экипировке каркаса и при истощении с разными зарядами.

## 7. Тесты

Белый список «можно то, что разрешено»:
- Стекинг: часть по id+моды+прочность; каркас по id+части+заряд; блок по заряду.
- Пакет: часть без каркаса не надевается; снятие каркаса уносит части и блок; повторное надевание восстанавливает всё как было.
- Таймер: 12 минут накопления = −1 заряд; накопитель переживает «закрытие» (сохранён — восстановлен).
- Истощение: без запасных → пакет снят (части и заряды сохранены в пакете); с запасными одинаковыми → вставлен молча; с разными → затребован выбор.
- Подавление: голый каркас НЕ подавляет; при надетой части пакета СУ одежды/брони = 0 в расчёте.
- СИЛ: модификатор каркаса `attributeModifier.STR {op:'set', value:11}` применяется при надетом каркасе; `op` вне белого списка `{+,-,set}` — ошибка данных, не «тихий минус».
- Запрет через политики: `canEquipArmor` с политиками `raiderOnly` (супермутант) и `robotOnly` отказывает предметам PA.
- Починка: недоступна при max; при < max → ровно до max.
- Каталог: powerArmor подключён, группы/`hp`/слоты arm→обе руки, блок в боеприпасах.
