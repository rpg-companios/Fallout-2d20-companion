# Save Slimming — «худой» сейв предметов

**Статус:** действует (schemaVersion 19)
**Контекст:** сейв персонажа был «жирным» — каждый предмет нёс полную копию
каталога (имя, цену, вес, редкость, урон, качества, эффекты, `imageName`…).
Это дублировало источник истины и приводило к дрейфу (правки JSON не доезжали
до уже созданных персонажей) и «зашитым» русским именам.

---

## 1. Принцип

Предметы в сейве хранят **только состояние экземпляра**, а имя/цену/вес/статы/
моды код достаёт из каталога через `domain/resolveItem.js` («Каталог = источник
истины»). Это:

- делает файл заметно легче;
- убирает дрейф — правки JSON применяются к уже созданным персонажам;
- пере-локализует имена под текущий язык программы (EN ↔ RU без «зашитых» имён).

## 2. Почему два прохода, а не только миграция

Часть потребителей читает поля предмета напрямую из состояния, поэтому:

- на **экспорте** (`saveCharacter` / автосейв, `CharacterContext`) — **ужимаем**
  `slimSaveData` → файл/БД худые;
- на **импорте** (`deserializeState`, тоже в `CharacterContext`) — **восстанавливаем**
  `restoreSaveData` → состояние снова полное, рендер не меняется.

Так нет регрессий в UI, а на диске сейв лёгкий.

## 3. Что хранится, а что выводится

**Хранится (состояние экземпляра)** — `SAVE_STATE_FIELDS` в `domain/saveSlimming.js`:
`id`, `instanceId`, `weaponId`, `itemType`, `quantity`, `equipped`, `locked`,
`appliedMods`, `stackKey`, `charges`, `hpCurrent`, `durability*`,
`equipInstanceId`, `uniqueId`, `sourceSlot`, `isBuiltin`, `isManipulator`,
`isEquipped`, `requiresMkII` и др.

**Выводится (из каталога)** — `name`, `cost/price/value`, `weight`, `rarity`,
`damage`, `fireRate`, `range`, `damageType`, `ammoId`, `qualities`, `effects`,
`imageName`, `protectedAreas`, DR-рейтинги, `positiveEffect/…`, `special`,
`maxCharges` и т.п.

## 4. Безопасность и обратная совместимость

1. Поле вырезается **только** если у `id` есть каталожная запись **и** она
   реально «владеет» этим полем. Иначе инстанс сохраняется целиком.
2. Стабы/кастом вне каталога (например `trinkets_stub_2` «Заглючивший голодиск» —
   в `loot/trinkets.json` это просто `{roll, id}`) **не теряют** свои имя/вес/цену.
3. Восстановление идёт через `resolveItem`; при отсутствии записи/ошибке предмет
   возвращается как есть (`.domain/saveSlimming#restoreItem` → `{...instance, ...resolved}`).
4. Каталог строится один раз на операцию; при сбое построения каталога
   ужимание/восстановление **пропускается** (сейв сохраняется/грузится как есть).

## 5. Что сейчас ужимается

- `equipment.items`
- `equippedWeapons`
- `equippedArmor.*.{armor, clothing}`
- `equippedPowerArmor.{frame, pieces.*}`
- `equippedRobotSlots.*.heldWeapon`

**Не ужимается (пока):** сами слои роботов (`equippedRobotSlots.*.limb/armor/
plating/frame`) и встроенное оружие конечностей. Их схемы вложены и тем тяжелее
для безопасной миграции; приоритет — не сломать обратную совместимость. Это
отдельная задача, требующая проверки каталога робочастей.

## 6. Версия и миграция

- `CURRENT_SCHEMA_VERSION` 18 → **19** (`src/store/saveSchema.js`).
- `MIGRATIONS[18]` (`src/store/migrations.js`) — **только бамп версии**, данных не
  меняет: само ужимание требует каталога (а миграция чистая), поэтому делается
  на экспорте, а восстановление — на импорте. Идемпотентна.
- Старые «жирные» сейвы (≤18) полностью совместимы: `restore` дообогащает их
  теми же каталожными данными, а повторный экспорт приводит к «худому» виду.
