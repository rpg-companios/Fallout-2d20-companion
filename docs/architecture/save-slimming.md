# Save Slimming — «худой» сейв предметов

**Статус:** действует (schemaVersion 19)
**Контекст:** сейв персонажа был «жирным» — каждый предмет нёс полную копию
каталога (имя, цену, вес, редкость, урон, качества, эффекты, `imageName`…).
Это дублировало источник истины и приводило к дрейфу (правки JSON не доезжали
до уже созданных персонажей) и «зашитым» русским именам.

---

## 1. Принцип

Предметы в сейве хранят **только состояние экземпляра**, а имя/цену/вес/статы/
моды код достаёт из каталога через `domain/resolveItem.js` («Каталог = источник
истины»). Это:

- делает файл заметно легче;
- убирает дрейф — правки данных применяются к уже созданным персонажам;
- пере-локализует имена под текущий язык программы (EN ↔ RU без «зашитых» имён).

## 2. Почему два прохода, а не только миграция

Часть потребителей читает поля предмета напрямую из состояния, поэтому:

- на **экспорте** (`saveCharacter` / автосейв) — **ужимаем** через `slimSaveData`;
- на **импорте** (`deserializeState`) — **восстанавливаем** через `restoreSaveData`,
  чтобы рендер и механика по-прежнему получали полные записи.

## 3. Владение полями

`domain/saveSlimming.js` содержит только нейтральный набор
`SAVE_STATE_FIELDS` (идентификатор экземпляра, количество, экипировка, ключ
стека и т. п.). Setting-specific поля приходят из
`services.inventory.itemSaveStateFields`; это отдельный компактный список,
чтобы сериализатор не добавлял в файлы произвольные runtime-поля из более
широкого `itemInstanceFields`.

Если каталожной записи нет, предмет сохраняется целиком — кастомные и legacy
записи не теряют локальные имя/вес/цену. При наличии каталога сохраняются только
нейтральные и объявленные setting-specific state-поля; остальные значения
восстанавливаются по каталогу.

## 4. Контейнеры и совместимость

Engine обходит только общие контейнеры:

- `equipment.items`;
- `equippedWeapons`;
- `equippedArmor.*.{armor, clothing}`.

`services.characterSave.mapItemContainers(data, mapItem)` даёт активному setting
возможность обработать его собственные вложенные контейнеры, не раскрывая их
структуру engine. `slimSettingContainers(data)` выполняет setting-owned
компактное представление после проекции вложенных предметов. Fallout использует
этот контракт для содержимого силовой брони и роботизированных слотов. Его
`getSnapshotFields(state)` проецирует extension state обратно на прежние flat
save keys (`equippedPowerArmor`, `powerArmorRuntime`, `equippedRobotSlots`,
`equippedRobotModules`, `mk2Installed`, радиация и другие setting-owned поля).

Так сохраняется существующий формат файлов: engine больше не перечисляет PA/
robot save containers и не содержит код их slim/restore. Старые и уже компактные
слоты продолжают проходить через Fallout codec до catalog projection; новые
setting-ы могут не реализовывать эту capability.

## 5. Безопасность и обратная совместимость

1. Каталожные поля вырезаются только для предметов с каталожной записью.
2. Стабы/кастом вне каталога (например `trinkets_stub_2`, «Заглючивший
   голодиск») не теряют свои локальные данные.
3. Восстановление идёт через `resolveItem`; если записи нет, предмет остаётся
   как есть.
4. Если каталог недоступен, save pipeline пропускает catalog projection, а
   исходные контейнеры и значения остаются пригодными для загрузки.

## 6. Версия и миграция

- `CURRENT_SCHEMA_VERSION` — 19 (`src/store/saveSchema.js`).
- Переход версии не переписывает данные: ужимание требует каталога и выполняется
  при экспорте, восстановление — при импорте.
- Старые полные сейвы остаются совместимыми; повторный экспорт приводит их к
  компактному представлению активного setting-а.
