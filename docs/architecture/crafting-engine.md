# Движок крафта: универсальная механика и адаптер сеттинга

**Статус:** патч 251. Это про проверку, списание и выдачу; экранов и часов ещё нет.
**Связанные документы:** `docs/architecture/crafting-data.md` (формат рецептов),
`docs/architecture/engine-dna.md`, `docs/architecture/engine-charter.md`.

---

## 1. Кто что знает (железное разделение)

- **`domain/craftingEngine.js` — движок.** Знает только ФОРМУ рецепта
  (`requires.skill/complexity/perks`, `materials[{itemId,count}]`,
  `outputQuantity: число | {base,cd}`). Сторонних полей в контракте нет — даже
  «сгорание при провале» (270): это правило модуля, движок получает его как вход. Результат
  рецепта — предмет с id рецепта: отдельного `output` нет (269). Ему безразлично,
  что такое Fallout: идентификаторы предметов и перков для него непрозрачны,
  каталоги и стор он не читает (тест-охрана следит, что в импортах движка нет
  ничего, кроме d20-резолвера).
- **`domain/registry.js` — где смотреть.** Собирает рецепты из файлов пакета
  сеттинга по манифесту и дополняет их категорией раздела (`getCraftingRecipes`,
  `getCraftingRecipeById`, `getCraftingCategories`). Расхождение манифеста с
  файлами — ошибка загрузки, а не тихая потеря рецептов.
- **`modules/fallout/crafting/operations.js` — адаптер сеттинга.** Переводит
  язык героя в язык движка: ранг навыка и атрибут — из стора, ранги особенностей —
  подсчетом выбранных перков, содержимое сумки — каноническими id (цепочка
  `getItemId`), списание — атомарной операцией стора, выдача — `addNewItem`
  (стор сам резолвит id по каталогу). Здесь же применяются ЧИСЛА ПРАВИЛ модуля
  (см. §4).
- **`modules/fallout/crafting/rules.js` — числа сеттинга.** Не поля рецептов и
  не сейв: атрибут проверки по умолчанию и «на каких верстаках провал сжигает
  материалы» (по книге: кухня и химия — сжигает, остальные — нет).

## 2. Контракт решения («сделано / отказ с причиной»)

`runCraft` (и `craftRecipe` в адаптере) возвращает одну форму:

| Результат | Когда |
|---|---|
| `{ done: true, spent, granted, check, auto }` | гейты пройдены, проверка успешна (или автоуспех), списание и выдача состоялись |
| `{ done: false, stage: 'gate', reasons[] }` | не хватает материала (`missing-material`, с деталями need/have) или ранга особенности (`missing-perk`) — **стор не тронут вообще** |
| `{ done: false, stage: 'store', reason: 'spend-refused' }` | адаптер отказал в списании (например, сумка изменилась между превью и действием) |
| `{ done: false, stage: 'check', burned, ... }` | проверка провалена; `burned` — что сгорело по правилу верстака |
| `{ done: false, stage: 'unknown', reason: 'recipe-not-found' }` | id нет в данных |

Отказ на любом гейте не дергает порты — баланс не меняется (тот же контракт,
что у покупки крышек). Списание `spendItemStacks` — all-or-nothing и не трогает
надетое и запертое комплектом.

## 3. Механика проверки (печатное правило, с. 210–211)

- Сложность проверки = `complexity − ранг навыка`, пол — 0.
- 0 — автоуспех, кубики не бросаются вообще.
- Иначе — стандартный движковый d20-тест (`resolveD20Check`, 2к20): нужно
  успехов не меньше сложности; два «20» — автопровал; «1» — критический успех.
- Количество результата: `1` или `{ base, cd }` — база + боевые кубики (порт
  `rollCD`; для Fallout его дает dice-логика). Форма количества проверяется ДО
  списания: битые данные не успевают стереть сумку.
- Провал: список «горячих» верстаков задан правилом сеттинга; там материалы
  списываются и не возвращаются, на других верстаках провал не меняет ничего.

## 4. Чего здесь намеренно НЕТ

- **Часов и ОД** (длительность, сокращение за 2 ОД, «+30/+10 минут за
  осложнение»). Это интеграция с часом выживания — отдельный шаг; движок
  mechanics к этому готов (числа — в правилах, не в рецептах).
- **Экрана крафта.** `craftingPreview(recipeId)` — готовое «можно ли / чего не
  хватает» для будущего списка рецептов; UI — следующий патч по договоренности.
- **Журнала изученного.** Гейт только по перкам и навыку — решение владельца,
  формат сейва не тронут.
- **Видимости хлама и материалов в инвентаре.** Каталоги `data/junk.json` и
  `data/materials.json` — источник id для крафта; чтобы игрок мог НОСИТЬ и
  РАЗБИРАТЬ эти предметы, их нужно показать каталогу снаряжения — это отдельное
  решение (какие экраны их примут), а не молча проводимая правка.
- **Установки модов.** Ветка отложена (решение владельца).

## 5. Как это тестировать и править

- `__tests__/crafting/crafting-engine.test.js` — движок на выдуманных id
  («in_a», «x_out»): если в движок заползет знание о сеттинге, тест видит это по
  импортам и строкам исходника.
- `__tests__/crafting/crafting-operations.test.js` — адаптер на настоящих
  данных: гейт Ammosmith, сгорание на кухне, неизрасходованный отказ, base+CD.
- Формулы движка правятся только вместе с обоими тестовыми файлами; если при
  этом меняется формат рецептов — еще и перегенерацией данных (см. crafting-data.md).
