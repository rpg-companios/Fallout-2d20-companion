# Карта каскада производных (МК-0, патч 279)

**Дата:** 2026-09-18. **Метод:** ручная инвентаризация кода (`src/store/`,
`domain/`, экраны) по итогам решения владельца: производные значения должны
выводиться сами («меняю один параметр — едет всё»), движок универсальный,
вторые сеттинги реальны. Карта — вход для контракта выводимости (патч 280+)
и для решения «реализация А/Б».

---

## 1. Вердикт одной страницей

1. Каскад сегодня **полуручной**: 24 вызова «пересчитай» руками расставлены
   по действиям стора; автоподписка следит только за экипировкой/профилем и
   **сознательно не смотрит атрибуты** (комментарий в коде: «их стор-действия
   зовут пересчёт сами»). Забытый вызов = устаревшее число на экране.
2. Выводимый слой **Fallout-специфичен, но живёт в движке**: жёсткий список
   fallout-статов в `src/store/resolvers.js`, и этот же файл движка
   **импортирует каталог силовой брони из `modules/fallout`** — живое
   нарушение границы «движок не знает сеттинг».
3. Экраны **не верят стору** и держат третьи копии формул (6 прямых вызовов
   расчёта в двух экранах).
4. Производные **не пишутся в сейвы** (признанный кеш) — починка каскада не
   трогает формат сохранений.
5. «Настоящих реакций» (правил «при изменении X сделать Y») найдено **мало**
   (§6) — для реализации хватает движкового реестра реакций; менять
   реактивное ядро (MobX/effector) обязательной нужды пока нет.

---

## 2. Инвентаризация производных значений

«Чьё правило»: **Д** = движковый механизм (универсальный), **F** = правило
сеттинга Fallout (должно переехать в `modules/fallout`).

| Производное | Где живёт сейчас | Зависит от | Чьё | Как пересчитывается |
|---|---|---|---|---|
| `attributes[id].total` | стор (хранимое) | base + modifiers[] | Д (форма Parameter) | руками: 8 действий стора |
| `skills[id].total` | стор (хранимое) | base + modifiers[] | Д | руками: 4 действия |
| `items[*].{damage,fireRate,3×DamageRating}.total` | стор (хранимое) | base + modifiers[] предмета | Д | `normalizeItemParameters` при записи |
| `derivedStats.maxHealth` | стор (кеш) | ВЫН+УДЧ+уровень; эффекты; перки; СБ-каркас | **F** (формула), Д (механизм стека) | руками (см. §3) |
| `derivedStats.initiative` | стор (кеш) | ВОС+ЛОВ | **F** | руками |
| `derivedStats.defense` | стор (кеш) | ЛОВ≥9?2:1 + эффекты | **F** | руками |
| `derivedStats.meleeBonus` | стор (кеш) | СИЛ + черта | **F** | руками |
| `derivedStats.carryWeight` | стор (кеш) | СИЛ+черта+снаряжение; робот — от корпуса | **F** (двухрежимная) | руками |
| `derivedStats.damageResistance.{physical,energy,radiation}` | стор (кеш) | эффекты + перки | **F** (сами типы — сеттинг) | руками |
| `perkBonuses` | стор (кеш) | выбранные перки | Д (стек) + **F** (состав) | при выборе перков |
| `maxLuckPoints` | стор (не персистится) | УДЧ (правило counters-storage №1) | **F** (формула) + Д (каунтер) | при изменении УДЧ |
| `currency` (крышки) | стор, каунтер | — | Д (каунтер) + F (имя/иконка) | транзакция spend/earn |
| шкалы выживания, усталость, hpBonus сна | стор, слайс расширения | еда/питьё/сон/часы | **F**, уже в модуле — **прецедент: сеттинговое состояние через реестр расширений** | слушатель расходников |
| эффективные атрибуты в силовой броне | вычисляется в resolvers | атрибуты + каталог каркаса **из модуля** | **F** + нарушение границы | при каждом пересчёте |
| обогащение предмета (имя/статы с модами) | при чтении (конвейер) | каталог + моды на предмете | Д (конвейер) | **уже правильно: вычисление при чтении** |
| статы слотов робота | при чтении (robotSlotLogic) | слоты + каталог | F (правила) + Д (механизм) | уже при чтении |

**Вывод по таблице:** механизмы (Parameter-стек, каунтеры, конвейер
обогащения) — движковые и здоровые; **правила** (все формулы из строчек с F)
— Fallout, застрявшие в движке с ручным приводом.

## 3. Ручной привод: 24 вызова пересчёта

`recalculateDerivedStats()` / `triggerDependentCalculations()` (делегирует в
первый) расставлены руками по действиям стора:

| Действие | Файл |
|---|---|
| `updateAttribute`, `addAttributeModifier`, `removeAttributeModifier`, `setBaseAttributes` | characterStore |
| `updateSkill`, `addSkillModifier`, `removeSkillModifier`, `setBaseSkills` | characterStore |
| `setSelectedPerks`, `updateItem`, `spendItemStacks`, `equipItem`, `unequipItem`, `addNewItem` (×2 ветки) | characterStore |
| `addEffect`, `updateEffect`, `expireEffect`, `pruneExpiredEffects`, `advanceScene` | characterStore |
| `recalculateAll`, `setSelectedPerks`… (итого 22 точки в characterStore) | characterStore |
| `setRobotSlots`, `setRobotModules` | robotSlice |
| `syncTimedEffectsToStore` | effectsSync |

Каждое новое действие — кандиддат забыть вызов. Обратная сторона: вызов
«на всякий случай» после каждого чиха — лишние пересчёты всей кучи.

## 4. Полуавтоматическая подписка (патч 243)

Подписка стора пересчитывает производные при изменении
`trait / level / origin / equippedArmor / robot.slots / equippedPowerArmor`
и **не смотрит атрибуты, навыки, эффекты и перки** — их закрывают ручные
вызовы §3. Подписка пушит контекст в `_characterContext` (зеркало для
пересчёта) — ещё одно хранимое промежуточное состояние, которого в целевой
картине нет.

## 5. Третьи копии в экранах

| Экран | Что пересчитывает локально |
|---|---|
| Оружие и броня | макс-здоровье (`calculateMaxHealth`), бонус ОЗ от эффектов, бонус ОЗ от сна, защита + бонус от эффектов |
| Персонаж | 2 прямых вызова формул домена |

Плюс 19 прямых чтений `.total` в экранах — экраны зависят от того, успел ли
кто-то обновить хранимые тоталы.

## 6. Найденные «настоящие реакции» (правила при изменении)

| Правило | Где сейчас | Чьё |
|---|---|---|
| макс-здоровье уменьшился → текущее ОЗ подтягивается (`Math.min`) | ручной кламп в действии стора | Д (механизм) + F (порог) |
| урон → текущие ОЗ ≥ 0 | действие стора | Д |
| силовая броня надета → атрибуты подменяются для производных | resolvers | F |
| голод/жажда/сон пересекли порог → усталость/снятие ОЗ | модуль выживания (слушатель) | F, уже модульно |

**Итого настоящих реакций — единицы.** Это главный факт для решения по
реализации: каскад почти целиком — «вывод при чтении», а не «правило при
изменении».

## 7. Требования к контракту выводимости (вход для патча 280)

Из карты + спеки тестового сеттинга владельца:

1. **Параметр**: `{ base, modifiers[], total }`; операции модификаторов — не
   только `+/−`, но и **процентные** (+5/10/15% из спеки тест-сеттинга) и
   «set» (СБ-каркас: СИЛ=11).
2. **Производное**: сеттинг регистрирует `{ id, deps: [paramId…], формула }`;
   движок выводит при чтении, кеша в сторе нет.
3. **Каунтер с производным максимумом**: мана = атрибут+навык, тратится
   заклинанием; отказ при нехватке (движковая форма уже есть —
   `domain/counters.js`, spend → `{ok}|{ok:false,reason}`).
4. **Потолок рангов от параметра**: ранги навыка ≤ f(атрибут) — обобщение
   существующих «лент» (`domain/levelBands.js`, потолки рангов перков от
   уровня).
5. **Гейты-требования**: «заклинание требует навык ранга 4» — обобщение
   существующих `requires` (рецепты крафта, навесы роботов).
6. **Виды значений**: сегодня всё числовое; контракт должен оставить версию
   для треков-полосок (здоровье-клетки VtM) и списков — не закладывать
   «только число» в фундамент.
7. **Регистрация через реестр расширений** (`{id, fieldKey, factory,
   hydrate, reset}` + новые `derived`, `reactions`, `requirements`) — тот же
   механизм, каким уже живёт выживание.

## 8. Тестовый сеттинг (спека владельца, дословно)

5 атрибутов; 5 производных (здоровье, манна, сила магии, защита, нападение);
7 навыков; 5 заклинаний. Атрибуты влияют на производные; заклинания тратят
манну (мана = атрибут + навык); +5/10/15% к силе магии / защите от магии;
заклинания с гейтом «навык ранга 4»; число рангов навыка зависит от атрибута.

**Критерий успеха контракта:** Fallout и тестовый сеттинг описываются
регистрациями **без правок движка**. Если для мини-мира пришлось ковырять
движок — контракт дырявый, чиним до любых вторых сеттингов.

## 9. Что следует для решения «реализация А/Б»

- Реакций мало (§6) → **пути А достаточно**: вывод-при-чтении (мемо-селекторы
  над стором) + маленький движковый реестр реакций для правил §6. Замена
  реактивного ядра (Б) обязательной нужды не показывает.
- Решение фиксируется после контракта (патч 280), финально — после того, как
  тестовый сеттинг встанет на контракт.

## 10. План переезда (ориентир для серии МК)

1. Контракт (типы + реестр) — движок.
2. Fallout-формулы §2 (строчки F) → регистрации `modules/fallout` (код
   модуля, JS) — заодно чинится нарушение границы (resolvers → каталог СБ).
3. Хранимые `total`/`derivedStats`/`perkBonuses`/`_characterContext` уходят
   из стора → вывод-при-чтении; 24 ручных вызова и подписка 243 умирают.
4. Экраны переводятся на чтение выводов (третьи копии §5 сливаются в одну
   правду).
5. Сейвы не меняются ни на шаге (производные и так не пишутся).
