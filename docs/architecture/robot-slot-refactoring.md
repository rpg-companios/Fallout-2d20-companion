Дата: 2026-09-04. Базовый коммит: `d40e6b9` (ветка `arena/01a06b0b-fallout-2d20-companion`).

### Критерий готовности (уточнён)

Принятая формулировка про «две атаки» (§10 исходного документа) заменена на
точную. Конечность `robot_arm_mister_handy` (хватка + встроенный манипулятор):

| Состояние ладони | Атак от слота |
|---|---|
| пустая | **1** (встроенный манипулятор) |
| держит оружие | **2** (вложенное оружие + встроенный манипулятор) |

«Голая рука даёт две атаки» — неверно. Проверяются оба состояния отдельно
(см. `__tests__/robot/mister-handy.test.js`).

## 2. Что показал разбор кода (факты, влияющие на план)

1. **`getRobotSlotKeys` уже читает данные** — имена слотов не захардкожены.
   Ломается не список слотов, а всё, что *сопоставляет* имена: `includes('arm')`,
   `leftArm||arm1`, `Hand → [leftArm, rightArm]`.
2. **Три независимые модели слотов** (9.1–9.3): слоты конечностей (данные),
   слоты человеческой брони (литерал 6 позиций в `equippedArmor.js`), локации
   брони робота (`Optics/Main Body/Arms/Thruster`, маппинг цепочкой `if`).
3. **`arm3` не потерян в `initRobotSlots`**, но **теряется при сборе атак**:
   `getBuiltinWeaponsFromSlots` дедуплицирует по id оружия *глобально*, поэтому
   у Хэнди с двумя руками-манипуляторами вторая атака исчезает
   (комплект `mister_handy_nanny` → 2 атаки вместо 3).
4. **`builtinToArm` содержит ошибку данных**: `robot_weapon_smoke_claws.builtinToArm
   = "robot_arm_robobrain"`, хотя `builtinWeaponId` на неё стоит у
   `robot_arm_smoke_manipulator`. Сейчас робомозг получает дымовые когти «из
   воздуха» через reverse lookup. Удаление обратной ссылки (этап 6) — это
   **исправление данных**, а не только чистка.
5. **Оружие вместо руки принимает броню** (9.7): слот с
   `robot_weapon_flamethrower` матчится на локацию `Arms` и получает обшивку.
6. **Поля конечностей живут в UI**: `melee`, `guns`, `mind`, `other`, `body`,
   `carryWeight`, `complexity`, `perksRequired`, `rarity` читаются
   `LimbUpgradeModal` и расчётом переносимого веса (`body.carryWeight`).
   Схема `limbs.json` из задания их не перечисляет — терять их нельзя.
7. **`hitTable` в данных нет нигде**, кроме `securitron.hitLocations`
   (`head 1-2`, `body 3-11`, `leftArm 12-14`, `rightArm 15-17`, `wheel 18-20`) —
   и то это строка для подписи в UI (`robotSlotLogic.js:38`). Боевой системы
   с таблицей попаданий в проекте нет: диапазоны для остальных 6 планов нужно
   взять из книги (решение владельца).
8. **Сейв хранит конечности и слои брони целиком** (объектами, не ссылками):
   `saveSlimming` ужимает только `heldWeapon`. Значит переименование id
   конечностей (`robot_arm_protectron` → `limb_arm_protectron`) требует
   миграции сейвов, иначе старые персонажи потеряют конечности.
9. **Дубли id разрешаются по `itemType`**, а не по каталогу:
   `resolveItem.js:84 case 'robotPart'` перебирает каталоги подряд и для 13
   задвоенных id всегда вернёт версию-руку.

## 3. Целевые схемы

### `bodyPlans.json` — 5 полей на план

```json
"protectron": {
  "slots": [
    { "id": "head",     "accepts": ["head"],  "capacity": 1, "swappable": false },
    { "id": "leftArm",  "accepts": ["arm"],   "capacity": 1, "swappable": true },
    { "id": "rightArm", "accepts": ["arm"],   "capacity": 1, "swappable": true },
    { "id": "body",     "accepts": ["body"],  "capacity": 1, "swappable": true },
    { "id": "leftLeg",  "accepts": ["mover"], "capacity": 1, "swappable": true },
    { "id": "rightLeg", "accepts": ["mover"], "capacity": 1, "swappable": true }
  ],
  "pairedTypes": ["arm", "mover"],
  "hitTable": [
    { "range": [1, 3],   "slotId": "head" },
    { "range": [4, 7],   "slotId": "leftArm" },
    { "range": [8, 11],  "slotId": "rightArm" },
    { "range": [12, 15], "slotId": "body" },
    { "range": [16, 18], "slotId": "leftLeg" },
    { "range": [19, 20], "slotId": "rightLeg" }
  ],
  "defaults": { "head": "…", "leftArm": "…", "rightArm": "…", "body": "…", "leftLeg": "…", "rightLeg": "…" }
}
```

* `pairedTypes` — какие типы у **этого** плана приходят парами (протектрон:
  руки и движители). У Хэнди руки **не** парные → `pairedTypes: []`: замена
  `arm1` не должна трогать `arm2`/`arm3`.
* `swappable: false` у головы — не отдельное правило, а данные; проверяет
  валидатор.
* `hitTable` — диапазоны d20, непрерывно покрывающие 1..20, без дыр и наложений.

### `limbs.json` — все конечности, `itemCategory: "limb"`

`limbType`: `head` | `body` | `arm` | `mover`. Поля: `canHoldWeapons`,
`weaponSlots`, `builtinWeaponId`, `physicalDR`/`energyDR`/`radDR`,
`installComplexity`/`installPerksRequired`/`installSkill` **плюс сохраняемые
как есть** `melee`/`guns`/`mind`/`other`/`body`/`carryWeight`/`rarity`/
`compatibleBodyPlans`/`defaultForBodyPlan`.

### `weaponAsLimb.json` — оружие вместо конечности, `itemCategory: "weaponAsLimb"`

`limbType`, `attackId`, требования установки. Ни `DR`, ни `canHoldWeapons`,
ни `weaponSlots` — поля **отсутствуют**, а не равны 0/false.

### `weapons.json` — единственный источник боевых характеристик

Добавляется `handheld: true|false`: можно ли вложить в `weaponSlots` руки.

### Броня: `limbType` вместо `robotLocation`

`Optics → head`, `Main Body → body`, `Arms → arm`, `Thruster → mover`.

### Рантайм-состояние слота (новое)

```json
"leftArm": {
  "content": "robot_arm_securitron",
  "armorLayers": { "frame": null, "plating": "robot_plating_standard_arms", "armor": null },
  "heldWeaponId": "weapon_railway_rifle",
  "heldWeaponMods": ["mod_001"],
  "installedWeapons": [{ "id": "weapon_laser_gun", "modIds": [] }]
}
```

Оружие в слоте — **id базы + список id установленных модов** (решение
владельца): характеристики восстанавливаются из каталога, моды накладываются
`applyWeaponMods`. Ни имён, ни посчитанных характеристик в сейве нет.

`installedWeapons` — оружие, **установленное в конечность** (апгрейд игрока:
лазерная пушка секьюритрона). Это НЕ то же, что встроенная атака конечности:
своя атака объявлена каталогом (`attackId` / `builtinWeaponId`), всё сверх неё
— установка. Поле появилось из живых сейвов: у секьюритрона в руке лежат и
манипулятор, и лазерная пушка, причём у левой — один состав, у правой — другой.

### Решения владельца, вошедшие в план

| Вопрос | Решение |
|---|---|
| `pairedTypes` | **Убрать.** Атавизм. Замена конечности меняет ровно один слот |

### Этап 1 — сделано (патч 163)

Данные. Старые файлы на месте и продолжают работать, новое лежит рядом:

| Файл | Что появилось |
|---|---|
| `equipment/robot/limbs.json` | 29 конечностей: 7 голов, 6 корпусов, 10 рук, 6 движителей. `itemCategory: "limb"`, `limbType` |
| `equipment/robot/weaponAsLimb.json` | 11 записей оружия вместо конечности. `itemCategory: "weaponAsLimb"`, `attackId`, без СУ и хватки |
| `equipment/robot/weapons.json` | + `handheld` (true только у двух манипуляторов) |
| `armor.json` / `armor_plating.json` / `frames.json` | + `limbType` (`Optics→head`, `Main Body→body`, `Arms→arm`, `Thruster→mover`) |
| `bodyplans/bodyplans.json` | слоты из строк стали объектами `{ id, accepts, capacity, swappable }`; `hitTable` — только для `protectron` и `securitron`, где диапазоны известны |

Разделение рук на «конечность» и «оружие вместо конечности» — по правилу §3:
нет хватки и нет своей СУ → оружие вместо конечности. Из 21 записи рук
10 остались конечностями (включая два манипулятора — у них есть хватка),
11 ушли в `weaponAsLimb.json`.

Инструменты:

* `scripts/migrate-robot-limbs.mjs` — пересоздаёт каталоги из старых файлов
  (идемпотентно, `--check` для CI);
* `scripts/migrate-bodyplans.mjs` — структурированные слоты и `hitTable`
  (тоже `--check`);
* `scripts/validate-robot-data.mjs` — одна реализация на CLI и на тест
  (`__tests__/robot/robot-data-catalogs.test.js` импортирует её же).

Единственная правка в коде — три строки, чтобы планы тел читались в обоих
форматах слотов: `getBodyPlanSlotIds()` в `domain/bodyplan.js`, использована
в `createSlotsFromBodyPlan` и `getRobotSlotKeys`. Тесты это покрывают:
имена слотов всех семи планов не изменились.

`hitTable` для `assaultron`, `sentryBot`, `robobrain`, `misterHandy`
**отсутствует** — диапазоны неизвестны, выдумывать их не стали.

### Этап 2 — сделано (патч 164)

Новый модуль `domain/robotSlots.js` — чистые функции, **ничего не подключено**
к рабочему коду: старые `robotEquip.js` / `robotDamageResistance.js` работают
как раньше. Тесты: `__tests__/robot/robot-slot-model.test.js` (34 шт).

| Функция | Что делает |
|---|---|
| `normalizeSlot(slot)` | читает оба вида состояния: старый `{ limb, armor, plating, frame, heldWeapon }` и новый `{ content, armorLayers, heldWeaponId }` |
| `resolveLimb(catalog, content)` | содержимое слота → запись каталога; понимает id, объект каталога и объект старого формата (`itemType: robotArm`) |
| `getSlotDef(bodyPlan, slotId)` | описание слота `{ id, accepts, capacity, swappable }` |
| `slotsForLimbType(bodyPlan, type)` | все слоты плана, принимающие тип (`arm` → `arm1/arm2/arm3` у Хэнди) |
| `canEquip(slot, item, opts)` | можно ли поместить конечность / оружие / защитный слой |
| `slotAcceptsArmor(slot, opts)` | принимает ли слот броню: пустой слот — нет, оружие вместо руки — нет |
| `totalDR(slot, opts)` | СУ слота = конечность + совместимые слои (конфликты по `incompatibleLayers`) |
| `attacksFromSlot(slot, opts)` | **список** атак: встроенная + оружие в ладони |
| `resolveHit(bodyPlan, roll)` | слот по броску d20 (null, если таблицы нет) |
| `validateHitTable(bodyPlan)` | покрытие 1..20 без дыр и наложений; отсутствие таблицы — предупреждение |

Ключевое отличие от старого кода — **`attacksFromSlot` никогда не дедуплицирует
по id оружия глобально**. Дедуп только внутри слота и только по экземпляру
(`instanceKey = слот:источник:id`). Две одинаковые руки-манипулятора дают две
карточки — ровно тот баг, из-за которого «arm3 теряет атаку».

Ещё два уточнения, которые всплыли на тестах:

* **оружие вместо руки не держит ничего в ладони** — `attacksFromSlot` игнорирует
  `heldWeaponId`, если содержимое слота — `weaponAsLimb` (ладони у него нет);
* **`handheld: false` означает «в ладонь не класть»** — циркулярная пила это
  сама конечность, поэтому рука с пилой в ладони даёт одну атаку, а не две.
  Тест «рука + оружие = две атаки» использует защитный манипулятор протектрона
  (`handheld: true`).

Каталог конечностей добавлен в реестр: `getRobotLimbCatalog()`
(`domain/registry.js`) — конечности, оружие вместо конечности, атаки, слои
защиты.

### Этап 3 — сделано (патч 165): первая точка использования за флагом

Переведён **сбор атак**: `getBuiltinWeaponsFromSlots` (`domain/robotEquip.js`)
при включённом флаге уходит в `collectAttacks` (`domain/robotSlots.js`).

**Фича-флаг `useNewSlotModel`** — временный, снимается на этапе 4:

| Способ | Как |
|---|---|
| `setNewSlotModelEnabled(true/false/null)` | из кода и тестов; `null` — вернуться к умолчанию |
| `ROBOT_NEW_SLOT_MODEL=1` | из окружения: прогнать **весь** набор тестов под новой моделью |
| по умолчанию | **выключено** — поведение прежнее |

> **Флаг снят патчем 172** (этап 4, шаг 2): модель одна, старых веток в коде
> нет, переменная `ROBOT_NEW_SLOT_MODEL` больше ни на что не влияет.

Формат записи на выходе сохранён один в один (`id`, `weaponId`, `sourceSlot`,
`sourceLimb`, `isBuiltin`, `isManipulator`) — экраны и сейвы не меняются.
Служебные поля нового домена (`source`, `slotId`, `instanceKey`) наружу не
уходят и в сейв не пишутся.

Три правила, по которым живёт новый сбор:

1. **дедуп по экземпляру** (`слот:источник:id`), а не по id оружия — две
   одинаковые руки дают две карточки (это и есть лечение «arm3 теряется»);
2. **экземпляр важнее каталога** — оружие в ладони это конкретный предмет
   со модами и именем, каталог только подставляет недостающие характеристики;
3. **приоритет источников встроенной атаки** тот же, что и раньше:
   `limb.builtinWeapons` → `builtinWeaponId` → `attackId` у оружия вместо руки.

**Прогон набора тестов (228 шт.):**

| Режим | Зелёных | Красных |
|---|---|---|
| флаг выключен (как в проде) | 227 | 1 |
| `ROBOT_NEW_SLOT_MODEL=1` | 227 | 1 |

Один и тот же красный в обоих режимах — acceptance-критерий «оружие вместо
руки не принимает обшивку»: броня пока не переведена, этим займётся
следующий шаг этапа 3. **Ни один другой тест не сломался** — это главная
новость: остальной набор уже готов к включению флага.

#### Шаг 2 (патч 166): раскладка защиты

Переведены ещё две точки, тоже за флагом:

* **подбор слота под защитный слой** в `initRobotSlots`. Слот ищется по типу
  конечности из данных (`limbType` + `slotsForLimbType`), а не по строковому
  совпадению имени слота с локацией (`k.includes('arm')`);
* **проверка установки** `canEquipRobotArmor` → `slotAcceptsArmor`.

Три уточнения, без которых новые правила не сходятся с жизнью:

1. **при раскладке комплекта пустой слот защиту принимает.** Конечности
   проставляются автозаполнением *после* цикла по предметам, поэтому в момент
   раскладки слоты ещё пустые. Инвариант добивается вторым проходом: после
   автозаполнения защита снимается со всех слотов, где нет настоящей
   конечности (оружие вместо руки или пусто).
2. **свободного слота нет — предмет не пропадает и не стирает надетое.** Старая
   модель в этой ситуации молча заменяла защиту в первом подходящем слоте;
   новая отправляет лишний предмет в инвентарь.
3. **интерактивная установка строже раскладки**: пустой слот броню не берёт
   (`equip.error.noLimb`) — на собранном роботе пустых слотов не бывает.

**Прогон набора тестов (237 шт.):**

| Режим | Зелёных | Красных |
|---|---|---|
| флаг выключен (как в проде) | **237** | 0 |
| `ROBOT_NEW_SLOT_MODEL=1` | **237** | 0 |

#### Шаг 3 (патч 167): расчёт СУ

`getRobotSlotDamageResistance` и `getActiveRobotLayers`
(`domain/robotDamageResistance.js`) при включённом флаге уходят в `totalDR` и
`activeArmorLayers`. Через `robotSlotLogic.js` это покрывает весь расчёт
защиты персонажа.

Два правила, которые здесь проявляются:

* **защита считается только там, где она законна.** Нет конечности или в
  слоте оружие вместо руки — надетые слои вклада не дают. Для старых сейвов
  (обшивка на огнемёте) это означает не «начислить СУ», а «не начислять»;
* ~~у оружия вместо конечности СУ нет по определению~~ — **снято владельцем в

#### Шаг 4 (патч 168): диапазоны попаданий и СУ конечности-оружия

**Таблица попаданий — свойство плана тела** (решение владельца). Сейчас

**СУ конечности-оружия (коррекция шага 3).** В патче 167 новая модель

#### Шаг 5 (патч 169): замена конечностей

`applyLimbReplacement` и `canReplaceLimb` переведены на новую модель:

1. **замена меняет ровно один слот.** Пар конечностей в модели нет: старый
   код обнулял `rightArm`, если обе руки держали один и тот же объект
   конечности, — игрок терял конечность, которую не трогал. Для Хэнди это
   выглядело бы как потеря `arm3`;
2. **защита следует за конечностью.** Поставили вместо руки огнемёт — броня,
   обшивка и рама снимаются (инвариант «защита только на конечности»);
3. **съёмность слота берётся из данных**, а не из имени: `swappable: false` у
   головы теперь реально запрещает замену (`equip.error.slotNotSwappable`),
   а не просто лежит в JSON.

Старая ветка сохранена целиком: при выключенном флаге пары обнуляются,
обшивка на оружии остаётся, голову заменить можно.

#### Шаг 6 (патч 170): стороны и каталог по типу

Последние места, где слон определялся по имени:

1. **сторона комплекта** (`left` / `right` / `center`) → `slotForDirection`:
   это N-й слот нужного типа в порядке плана тела. Для Хэнди `left→arm1`,
   `right→arm2`, `center→arm3`; для протектрона `left→leftArm`,
   `right→rightArm`, центра нет. Тесты сравнивают обе модели: результаты
   совпадают, но новая берёт их из данных;
2. **раскладка конечностей комплекта** в `initRobotSlots`: голова, корпус,
   движитель и руки находятся по типу (`slotsForLimbType`), а не по

3. **каталог конечностей для слота** в `LimbUpgradeModal`: кандидаты

   слота и `itemType`. Тип каждой записи берётся из нового каталога по id —

Сейв хранит только id (да id установленных модов) — ровно как попросил

## Слои защиты: чтение и запись экранами (патч 185)

**Симптом (со слов владельца):** на старом сейве Штурмотрона хочу поменять
обшивку на руке — «пытаюсь в модалке выбрать, а мне сразу модалка
«Улучшить броню», не давая выбора». Плюс: обшивок и рам предлагается мало,
хотя в каталоге их много.

Разбор показал три разные причины.

### 1. Пикер не сбрасывал выбранный слой (видимый баг)

`ArmorPickerModal` хранит `activeLayer` и сбрасывал его только в
`handleLayerClose` — то есть когда закрыта модалка **слоя**. Пикер же
закрывали по фону или кнопкой OK: `activeLayer` оставался, и при следующем
открытии модалка слоя вылетала **сразу**, поверх списка обшивка/броня/рама.
Владелец именно это и описал: «сразу модалка, не давая выбора».

Исправлено: сброс `activeLayer` при смене `visible` и `slotKey`.

### 2. Экраны читали и писали слои по-старому (латентный баг)

Сейв хранит слот в двух видах: старый «толстый» (`{ limb, plating, frame,
armor }`) и новый (`{ content, armorLayers }`), причём в новом слои могут
лежать одним id. Экраны работали с верхним уровнем:

| Место | Было | Стало |
|---|---|---|
| `ArmorPickerModal` | `slot?.plating / .armor / .frame` | `normalizeSlot(slot).armorLayers` + разрешение id в запись каталога |
| `ArmorLayerModal` | запись `{ ...slot, [layer]: item }` | `withArmorLayer(slot, layer, item)` |
| `WeaponsAndArmorScreen` (`localizeRobotSlotData`) | `slotData.limb / .plating / …` | `normalizeSlot(slotData)` → `content` и `armorLayers` |

`withArmorLayer` (domain/robotSlots.js) сохраняет форму слота: новому виду
пишет в `armorLayers`, старому — на верхний уровень. Примешивать
`armorLayers` к старому виду нельзя: слот станет «новым» без `content`, и
конечность потеряется — это прямо проверено тестом.

Пока `deserializeSlot` восстанавливает толстый вид (`limb` со встроенным
оружием), так что в UI всегда лежит старая форма; правка не меняет
поведение на текущих сейвах, но снимает минуту под slim-слотом.

### 3. Мёртвая карточка робота в сетке не-робота

`renderArmorPart` (путь обычной сетки брони) отдавал `<RobotSlot>` без
обработчиков, без `bodyPlan` и без локализации: кнопки «Конечность» и
«Броня» были немыми, подзаголовок с диапазоном попаданий не считался.
Теперь карточка получает тот же набор пропсов, что и сетка плана тела.

### Списки слоёв: почему их «мало»

Кандидаты режутся по типу конечности слота
(`getSlotDef(bodyPlan, slotKey).accepts[0]`), а не отказом
`canEquipRobotArmor` — проверка на слоте `assaultron.leftArm` (принимает
`arm`) даёт **ноль отказов**:

| Каталог | Всего | Для руки |
|---|---|---|
| обшивка | 28 | 7 (стандартная, Храбрец, заводская, первобытная, зубчатая, ядовитая, радиоактивная) |
| рама | 12 | 3 (раздвижная, вольтовая, гидравлическая) |
| броня | 5 | 1 (заводская броня для руки) |

То есть «мало» — это фильтр по конечности, а не потеря данных. Если по
книге обшивка/рама не привязаны к типу конечности или у руки больше
вариантов брони — это правка данных, не кода.

### Тесты

`__tests__/robot/robot-armor-layer.test.js` (+7): запись слоя видна движку
в обоих видах слота, конечность не теряется, снятие слоя (`null`) работает,
СУ слота растёт, и регрессия — запись на верхний уровень в новом виде
слота движком не видна.

**Итог:** 312 тестов / 27 файлов, все зелёные.

   стоимость в компонентах, перки, навык и раритет.
3. Всё это учитывается **при сборке** робота и может входить в тот же бросок,
   что и сборка автоматрона — отдельной процедуры «установить навес позже» в
   книге нет. В приложении такого потока тоже нет: `installedWeapons`
   меняются только комплектами, а в интерфейсе можно лишь заменить
   конечность целиком.

### Как это смоделировано

Один и тот же id живёт в двух каталогах: `weapons.json` — оружие как таковое,
`weaponAsLimb.json` — если оно может быть рукой (arm attachment). Карабин
Теслы (`robot_weapon_tesla_arm`) лежит в обоих: для робомозга это навес,
в остальных комплектах — обычное оружие (как кувалда: `weapon_sledgehammer`
в комплекте защитрона — оружие, в комплекте робомозга — навес).

Выбор «любых двух» уже реализован: `robobrain_nonordinary` содержит два
независимых выбора (левая и правая рука), в каждом ровно книжный список —
smoke claw (`robot_arm_smoke_manipulator`), Tesla rifle, flamer, laser gun,
sledgehammer.

### Что поправлено

Требования установки остались **только у пяти навесов из таблицы**. У Карабина
Теслы они были скопированы с Криоструи (сложность 4, Robotics Expert 1 +
Science! 1, Science) — в таблице его нет, он навес из комплекта. Поля
`installComplexity/PerksRequired/Skill` сняты и в `weaponAsLimb.json`, и в
`weapons.json` (данные дублировались в обоих каталогах).

### Что книга даёт, а мы не храним

- стоимость навеса в компонентах;
- раритет навеса (по книге все пять Uncommon) — числовое поле `rarity` у нас
  есть только у самого оружия, легенда шкалы в данных не зафиксирована.
