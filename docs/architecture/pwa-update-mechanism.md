# PWA Update Mechanism — Design Document

**Статус:** черновик к ревью  
**Контекст:** предеплойное планирование. Кодирование — отдельный шаг после утверждения.

---

## 1. Текущее состояние

### Что уже есть

| Компонент | Файл | Состояние |
|---|---|---|
| Service Worker | `public/service-worker.js` | Работает. `skipWaiting` + `clients.claim`. Network-first стратегия. |
| Версия кэша | `CACHE_NAME = 'rpg-companion-v9'` | Меняется вручную при каждом деплое |
| Схема БД | `db/schema.js` — `SCHEMA_VERSION = 9` | Версионируется. Миграция: каталог сбрасывается, персонажи сохраняются |
| Принудительное обновление | `src/utils/forcePwaUpdate.js` | Есть. Грубый инструмент: unregister всех SW + `location.reload(true)` |
| Регистрация SW | `index.js` | Регистрирует, но **не слушает** события обновления |
| Дубль SW | `public/sw.js` | Существует параллельно с `service-worker.js`. Не регистрируется — мёртвый файл |

### Текущие проблемы

1. **Тихое обновление.** SW применяет `skipWaiting` сразу при установке. Пользователь не знает, что страница обновилась. Возможна рассинхронизация состояния React и нового бандла прямо в сессии.
2. **Нет сигнала о новой версии.** `index.js` регистрирует SW, но не подписывается на `updatefound`. Нет UI-уведомления.
3. **Ручная версия кэша.** Разработчик должен помнить поднять `rpg-companion-vN` в SW. При забытом bump старый кэш не инвалидируется.
4. **`sw.js` — зомби.** Файл существует, не регистрируется. Создаёт путаницу и риск случайной регистрации.
5. **Нет версии приложения в рантайме.** `app.json` содержит `"version": "1.0.0"`, но она нигде не читается и не отображается пользователю.
6. **Нет совместимости бандла и схемы.** При деплое с новым `SCHEMA_VERSION` пользователь со старым SW может получить смешанное состояние: новый JS + старая схема в AsyncStorage.

## 2. Цели

- **G1.** Пользователь с установленной PWA узнаёт о новой версии без перехода на сайт.
- **G2.** Обновление применяется только с согласия пользователя (явная кнопка), либо автоматически при следующем открытии вкладки — на выбор (см. §6).
- **G3.** Данные персонажей не теряются и не ломаются при обновлении схемы.
- **G4.** Версия кэша SW инкрементируется автоматически при сборке — без ручного вмешательства.
- **G5.** Пользователь может видеть, какая версия приложения у него установлена.

## 3. Схема версионирования

Три независимых номера, которые нужно координировать:

```
APP_VERSION      — видимая пользователю строка (например "1.2.0")
CACHE_VERSION    — суффикс кэша SW (целое число, автоинкремент)
SCHEMA_VERSION   — версия схемы AsyncStorage (целое число, уже есть)
```

### Предложение: единая точка истины — `app.json`

```json
{
  "expo": {
    "version": "1.2.0",
    "extra": {
      "schemaVersion": 9
    }
  }
}
```

`CACHE_VERSION` берётся из `version` строки или генерируется как хэш при сборке (см. §4.1).  
`SCHEMA_VERSION` в `db/schema.js` остаётся авторитетным источником для DB-кода, но согласуется с `extra.schemaVersion` для перекрёстных проверок при необходимости.

## 4. Архитектура обновления

### 4.1 Автоматическая версия кэша при сборке

**Вариант A — хэш из даты сборки:**  
Скрипт `scripts/bump-sw-version.js` перед `expo export` заменяет `CACHE_NAME = 'rpg-companion-vX'` на `rpg-companion-v<timestamp>` или `rpg-companion-v<git-sha-short>`.

```
"prebuild": "node scripts/bump-sw-version.js"
```

**Вариант B — переменная среды в SW:**  
При сборке Expo Metro подставляет `process.env.EXPO_PUBLIC_BUILD_ID` в SW через `define`. Минус: требует поддержки Metro для SW-файлов.

**Рекомендация:** Вариант A — проще, не зависит от бандлера, работает с текущим Metro.

### 4.2 Поток обнаружения обновления

```
Browser                   index.js                  Service Worker
  |                          |                            |
  |── открытие вкладки ──>   |                            |
  |                          |── register SW ──────────>  |
  |                          |                            |── install (новый SW waiting)
  |                          |<── updatefound ────────────|
  |                          |                            |
  |                 показать баннер "Доступно обновление"
  |                          |                            |
  |── клик "Обновить" ──>    |                            |
  |                          |── postMessage(skipWaiting)─|
  |                          |                            |── skipWaiting()
  |                          |<── controllerchange ───────|
  |                          |                            |
  |                    window.location.reload()
```

Ключевые события:
- `registration.addEventListener('updatefound')` — новый SW начал загружаться
- `newWorker.addEventListener('statechange')` — `state === 'installed'` → SW готов, ждёт
- `navigator.serviceWorker.addEventListener('controllerchange')` → новый SW взял контроль → перезагрузка

### 4.3 Изменения в Service Worker

SW должен слушать `message` и вызывать `skipWaiting` только по явной команде приложения (а не сразу при установке):

```js
// БЫЛО:
self.addEventListener('install', () => self.skipWaiting());

// СТАНЕТ:
self.addEventListener('message', (event) => {
  if (event.data?.type === 'SKIP_WAITING') {
    self.skipWaiting();
  }
});
```

> **Важно:** это единственное breaking-изменение в SW. Без `skipWaiting` в `install` новый SW будет корректно ждать явного сигнала от пользователя.

### 4.4 Новый модуль: `src/utils/swUpdateManager.js`

Заменяет нынешний `forcePwaUpdate.js` (или дополняет его). Ответственности:

```
swUpdateManager
├── registerAndWatch(onUpdateAvailable: fn)
│     Регистрирует SW, подписывается на updatefound,
│     вызывает колбэк когда waiting SW готов.
│
├── applyUpdate()
│     Посылает SKIP_WAITING в waiting SW,
│     слушает controllerchange → reload.
│
└── getInstalledVersion() → string
      Читает APP_VERSION из константы, вшитой при сборке.
```

### 4.5 UI-уведомление

Минималистичный баннер поверх навигации (не модалка, не блокирует контент):

```
╔══════════════════════════════════════════════════════╗
║  🔄  Доступна новая версия приложения    [Обновить]  ║
╚══════════════════════════════════════════════════════╝
```

- Показывается в `App.js` через `useState(false)` / `useEffect` с подпиской на `onUpdateAvailable`
- Кнопка "Обновить" → `applyUpdate()` → перезагрузка
- Крестик / "Позже" → скрыть баннер до следующего открытия вкладки (не персистировать)

## 5. Безопасность данных при обновлении схемы

### Текущая логика миграции (уже работает)

`WebAdapter.initDatabase()` при старте:
1. Читает `storedVersion` из AsyncStorage
2. Если `storedVersion !== SCHEMA_VERSION` — сбрасывает каталожные таблицы, сохраняет `characters`
3. Записывает новый `storedVersion`

### Что нужно добавить

**Проблема:** пользователь может открыть новую вкладку с новым бандлом, пока старый SW ещё обслуживает кэшированную страницу → рассинхронизация.

**Решение — проверка совместимости при старте:**

```
App.js (componentDidMount / useEffect):
  1. Прочитать APP_VERSION из константы бандла
  2. Прочитать lastSeenVersion из AsyncStorage
  3. Если версии расходятся — принудительно запустить initDatabase()
     (она сама проверит SCHEMA_VERSION и сделает нужные миграции)
  4. Записать APP_VERSION в AsyncStorage
```

Это страховочный слой поверх SW-механизма.

### Матрица совместимости

| Старый SW | Новый бандл | SCHEMA_VERSION | Итог |
|---|---|---|---|
| = | = | = | Норма |
| старый | новый | = | SW обновится по обычному флоу; схема не меняется — OK |
| старый | новый | **+1** | SW обновится → `initDatabase()` увидит несовпадение → миграция → OK |
| ❌ нет SW | новый | любой | Первый запуск → `initDatabase()` → OK |

## 6. Открытые вопросы к владельцу

**Q1. Поведение обновления:**  
Баннер с кнопкой "Обновить сейчас" (пользователь контролирует момент) **или** автоматическое обновление при следующем открытии вкладки (тихое, без UI)?  
*Рекомендация: кнопка — пользователь не теряет несохранённый контекст.*

**Q2. Версия в UI:**  
Показывать текущую версию где-то в приложении (например, в футере настроек или в экране персонажа)?  
*Рекомендация: да, хотя бы в одном месте — помогает при отладке и репортах.*

**Q3. Версия кэша — хэш или дата?**  
`rpg-companion-v20260803` (дата) или `rpg-companion-vabc1234` (git sha)?  
*Дата — читаема, git sha — точнее привязана к коду.*

**Q4. sw.js — удалять?**  
Файл `public/sw.js` — мёртвый код, нигде не регистрируется. Удалить перед деплоем?

**Q5. Offline-режим:**  
Network-first стратегия означает, что без сети приложение работает только из кэша (и только если кэш не устарел). Это приемлемо, или нужна полноценная offline-поддержка (cache-first для статики, network-first для данных)?

## 8. Что НЕ меняется

- Стратегия хранения данных (AsyncStorage через WebAdapter) — без изменений
- Логика миграции схемы в `WebAdapter.initDatabase()` — без изменений (только убедиться что вызывается при каждом старте)
- Навигация, компоненты — без изменений
- Expo build pipeline — только добавляется `prebuild` хук
