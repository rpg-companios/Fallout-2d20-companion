# Комнаты мастера (админ-режим и «Сервер» у игрока) — план

> Статус: **ПЛАН, код не тронут.** Решения владельца от 2026-09-28:
> транспорт — **свой мини-сервер (Node + WebSocket)**; синхронизация
> двусторонняя, **правки мастера — только с явного согласия игрока**
> (§3.5, просмотр через `editDiff` §3.8), **состояния — авто-приём с
> уведомлением** (§3.4/§3.5); код **6 знаков** — занять всё пространство
> нереально (§3.2);
> мастер — много комнат, комната — много игроков (§3.3); адрес
> копируется из UI; мастерское пространство — **движковая часть, может
> отсутствовать** (§3.9). Старт реализации — по слову владельца.
> Документ живёт в разделе «Открытые вопросы» `docs/agents/state.md`.

## 1. Постановка владельца (что делаем)

- На главном экране в шапке, **по центру между переключателем языков и
  меню настроек**, кнопка **«Админ»**.
- Админская часть **повторяет главный экран**, но кнопка становится
  **«Пользователь»** (обратный переход).
- Когда админ создаёт папку — это **серверная комната** со своим
  адресом: короткий префикс + буквенно-цифровой код (не слишком сложный).
  **У одного мастера может быть несколько комнат, в каждой — несколько
  игроков.** Адрес комнаты виден на папке и копируется кнопкой (для
  передачи игрокам сообщением/голосом).
- У пользователя в меню персонажа появляется пункт **«Сервер»**: выбор →
  ввод адреса комнаты админа.
- У админа появляется **копия персонажа пользователя**, админ может его
  редактировать. Правки мастера уходят пользователю **как предложение и
  применяются только с его явного разрешения** (решение владельца от
  2026-09-28: защита от скрытых правок; см. §3.5).
- Двусторонка: правки пользователя уходят мастеру и применяются
  автоматически — это копия на стороне мастера, им распоряжается мастер.
- Задел на будущее: по этому же каналу мастер шлёт персонажу **состояния
  и другой функционал** (директивы). Решение владельца от 2026-09-28:
  **состояния от мастера принимаются БЕЗ подтверждения** — авто-применение
  с видимым уведомлением, что именно применено (§3.5). Подтверждение
  остаётся только на правках листа персонажа.
- **Мастерское пространство — движковая часть** и может отсутствовать:
  без адреса сервера и/или без заявки сеттинга кнопки «Админ» нет,
  приложение остаётся одиночным (§3.9).

## 2. Контекст движка (что меняет задачу)

- Приложение — статический PWA (Expo web): данные — локальная SQLite
  (`db/`), единственная «сеть» — Google Drive appDataFolder
  (`components/cloudSync/googleDriveSync.js`). appDataFolder **приватен**
  для пары «приложение+пользователь» и межпользовательские комнаты через
  него не построить → нужен собственный транспорт. Это 80% работы фичи.
- Переиспользуется уже готовое:
  - `domain/characterTransfer.js` — версионируемый payload персонажа
    (снапшот для сети; «экспорт = сейв», закон 361);
  - папки персонажей — таблицы + `domain/characterFolders.js` + UI
    (комната = папка со штампом адреса);
  - автосейв-подписка `src/saves/characterSaves.js` — точка подключения
    исходящего push;
  - диалоги `components/alerts/*` (единая точка окон), zustand
    `src/store/appSettingsStore.js` — образец добавления настройки,
    зеркала i18n `i18n/ru-RU` + `i18n/en-EN`.

## 3. Архитектура

### 3.1. Транспорт — `server/` (новая папка)

- Node + `ws` (+ Express для раздачи статики `dist/`). Единственная
  точка — WebSocket на пути `/ws`; REST не нужен.
- Модель: **релей комнат**. Сервер хранит: карту комнат
  `code → { members, lastSnapshotByCharacterId, revisions }`, сообщения
  не разбирает глубже конверта. Персистентность — этап 5 (JSONL-журнал
  на комнату, чтобы комната переживала перезапуск), TTL пустых комнат.
- Деплой: один контейнер рядом со статикой (Replit: `npm run build` →
  serve `dist` + upgrade `/ws` на том же порту). Клиент берёт адрес из
  `EXPO_PUBLIC_ROOM_SERVER_URL`, по умолчанию — `wss://<тот же origin>/ws`.
  На проде обязателен **wss** (PWA идёт по https, mixed content запрещён).
- Масштаб: 1 мастер + 3–6 игроков на комнату; in-memory релея хватает
  с запасом, узких мест нет.

### 3.2. Адрес комнаты

- Формат `PP-XXX-XXX`: префикс 2–3 буквы + код **6 знаков** из алфавита
  без неоднозначных символов (исключены `0/O`, `1/I/L`): пример
  `GM-7Q3-K9M`. Отображение — группами по 3 через дефис (диктовать и
  вводить удобно), дефисы при вводе игнорируются.
- **Префикс НЕ захардкожен**: клиент предлагает его в `room.create`
  (по умолчанию `GM`, сеттинг-пакет может задать свой — движок
  универсальный), сервер только валидирует формат. Префикс — косметика
  и пространство имён для читаемости; в уникальности не участвует.
- **Ёмкость (решение владельца 2026-09-28: занять всё пространство
  должно быть нереально)**: 23 буквы (A–Z без O, I, L) + 8 цифр (2–9) =
  31 символ на позицию.

  | Знаков | Вариантов | Оценка |
  |---|---|---|
  | 4 | 923 521 | мало: ~6 тыс. комнат → 50% коллизии без проверки |
  | 5 | 28 629 151 | достаточно от подбора, но пространство «занимаемо» ботнетом |
  | **6 (принято)** | **887 503 681** | занять 1% при лимите 200 комнат/IP/сутки — ~44 тыс. IP·дней; всё пространство — ~4,4 млн IP·дней. Нереально |
  | 7 | 27 512 614 111 | запасной вариант, если 6 сочтём коротким — одна константа на сервере |

  Длина кода — конфиг сервера (константа), смена не ломает протокол:
  код для клиента — непрозрачная строка, валидация по форме, не по длине.
- **Уникальность конструктивная, не вероятностная**: код генерирует
  только СЕРВЕР (устройства коды не генерируют) циклом «сгенерировать →
  проверить реестр активных комнат → занят — ещё раз». Дубликат среди
  живых комнат невозможен по построению. Один сервер = одно пространство
  имён → уникальность автоматически на всех устройствах всех
  пользователей. Подбор чужого кода: 1/887 млн на попытку, с rate-limit
  join'а перебор исключён; параллельно действуют лимиты §3.3.
- Нормализация ввода: верхний регистр, срез пробелов/дефисов; принимать
  и полную ссылку-вставку. Пруф тестами.

### 3.3. Идентичность и доступ

- `clientId` (uuid) создаётся при первом запуске и хранится в
  AsyncStorage; при входе в комнату спрашивается отображаемое имя.
- **Код комнаты = единственный публичный секрет** (capability-ссылка):
  аккаунтов нет, для настольной сессии достаточно. Полные адреса не
  логируем.
- **Токен владельца**: при `room.create` сервер выдаёт мастеру
  случайный ownerToken; хранится в штампе комнаты в сейве → едет в
  облачную синхронизацию вместе с папками/персонажами. Решает: (а)
  **перезапуск сервера** — мастер восстанавливает комнату под ТЕМ ЖЕ
  кодом, предъявив токен (`room.create` с запрошенным кодом принимается,
  если код свободен или подтверждён токеном); (б) переезд мастера на
  другое устройство — из облака приехали и код, и право владения.
  Игрокам токен не нужен и не сообщается.
- Этап 5: опциональный PIN мастера (модерация: кик, закрытие комнаты).
- **Лимиты (модель «несколько комнат у мастера, несколько игроков в
  комнате»)**: целевой сценарий — 1 мастер + 3–6 игроков; серверные
  потолки (конфиг): комнат на одного мастера (по ownerToken/clientId) —
  20; членов в комнате — 12; комнат на IP в сутки — 200 (см. исчерпание
  пространства §3.2); rate-limit на join/publish; лимит размера
  сообщения (снапшот персонажа ~100–300 КБ; потолок 2 МБ).

### 3.4. Протокол — `src/room/roomProtocol.ts` (TS, по уставу новые
контракты — в TypeScript)

Конверт: `{ v, type, roomCode, clientId, ts, payload }`, где `v` —
версия протокола. Типы:

| type | Кто шлёт | Назначение |
|---|---|---|
| `room.create` | мастер | создать комнату → сервер отвечает `{ roomCode }` |
| `room.join` | игрок | вход по коду → сервер отвечает `room.state` (участники + последние снапшоты) |
| `room.leave` / `presence.ping` | все | выход / живучесть соединения |
| `char.publish` | обе стороны | полный снапшот `{ characterId, revision, snapshot }`; snapshot = payload `domain/characterTransfer`. От игрока — применяется у мастера сразу; от мастера — у игрока становится ПРЕДЛОЖЕНИЕМ (§3.5) |
| `char.approve` / `char.reject` | игрок | решение по предложению мастера `{ characterId, baseRevision, proposalId }`; сервер рассылает решение, мастерская копия помечается «принято/отклонено» |
| `char.focus` | обе стороны | мягкий маркер «редактирую сейчас» (индикатор у другой стороны) |
| `gm.directive` | мастер | состояния/счётчики/сообщения (вложенный payload открытый, версионируемый). **Применяется у игрока АВТОМАТИЧЕСКИ** (решение владельца 2026-09-28), с уведомлением в UI |
| `error` | сервер | `ROOM_NOT_FOUND`, `ROOM_FULL`, `ROOM_QUOTA_EXCEEDED`, `PROTOCOL_VERSION_MISMATCH`, `RATE_LIMITED`, … |

Совместимость версий: снапшот несёт версию сейва (`src/store/saveSchema.js`).
Клиент со старым сейвом мигрирует своей цепочкой `migrations.js` (тот же
закон, что у файлов импорта); клиент новее версии сервера — просит
обновить приложение (update-flow уже есть, `UpdateNoticeModal`).

### 3.5. Двусторонняя синхронизация (закон правок, с согласием игрока)

Модель **асимметричная** (решение владельца 2026-09-28: мастер не может
изменить персонажа без явного разрешения игрока):

- **Игрок → мастер: автоматически.** Правка игрока публикуется и сразу
  применяется в мастерскую копию — мастер распоряжается своей стороной
  сам, копия всегда актуальна.
- **Мастер → игрок: предложение → просмотр → решение.** `char.publish`
  от мастера у игрока НЕ применяется сам, а кладётся в очередь
  `pendingGmEdits` (хранит `proposalId`, `baseRevision`, снапшот).
  Решение уходит `char.approve` / `char.reject`: approve → снапшот
  валидируется и пишется как обычный входящий; reject → мастер видит
  «отклонено игроком» на своей копии. **Игрок — финальный арбитр своего
  персонажа, всегда.** Как игрок ВИДИТ правки — §3.8 (диалог → бейдж →
  окно сравнения), до кнопок «Применить/Отклонить» он может изучить
  каждое изменение.
- **Состояния (`gm.directive`) — БЕЗ подтверждения** (решение владельца
  2026-09-28): применяются автоматически сразу по получении, но каждая
  директива сопровождается видимым уведомлением («Мастер: получено
  состояние «Отравление»»), чтобы авто-приём не был скрытым.
- **Постоянное разрешение** (опция, по умолчанию ВЫКЛ): тумблер у игрока
  «Принимать правки мастера этой комнаты без подтверждения» (настройка на
  комнату, не глобальная) — для доверенных столов; вкл → предложения
  применяются автоматически, но в журнале видно «применено от мастера».
- **revision** — монотонный счётчик на стороне автора правки; хранится в
  сейве и на сервере. Конфликт решает **last-write-wins** по
  `(characterId, revision)`: сервер хранит последний снапшот и рассылает
  его членам комнаты; устаревшая ревизия отбрасывается (ошибкой не
  считается). Предложение несёт `baseRevision` (на чём мастер правил):
  если к моменту решения игрок сам успел изменить персонажа —
  предупреждение «персонаж менялся после предложения мастера» и выбор
  всё равно за игроком (его решение и есть разрешение конфликта).
- **Анти-эхо**: снапшот, применённый из сети, помечается `origin='remote'`
  и автосейвом обратно не пушится.
- **Мягкий замок**: `char.focus` включает у другой стороны баннер
  «редактирует мастер/игрок» — напоминание, не блокировка (настольная
  игра, координация голосом). Жёсткий замок — только по отдельному слову
  владельца.
- **Оффлайн**: исходящие publish складываются в очередь `roomStore`; при
  переподключении — сверка ревизий, старым снапшотом новый не затираем.
  Предложения мастера живут на сервере до решения (или TTL) — игрок,
  вошедший позже, получит последнее ожидающее предложение.

### 3.6. Клиентский слой `src/room/` (новый, TS)

- `roomCode.ts` — генерация/нормализация/валидация адреса (чистые
  функции, тесты).
- `roomProtocol.ts` — типы конвертов и редьюсеры (чистые).
- `roomClient.ts` — ws-клиент: reconnect с backoff, heartbeat, очередь,
  мок-порт для тестов (образец портов крафта).
- `editDiff.ts` — **чистое сравнение двух payload'ов персонажа** (текущего
  и предложенного мастером): обходит оба дерева, возвращает список
  изменений `{ kind: 'changed'|'added'|'removed', path, before, after }`.
  Массивы инвентаря сопоставляются по идентичности предмета
  (`domain/itemIdentity.js`): «Стимулятор ×2 добавлен», «10мм пистолет
  удалён», «Крышки 120 → 85». Без UI и без знания сеттинга: подписи путей
  — словарь i18n движка, неизвестное поле показывается техническим
  именем. Тесты — обязательная часть модуля.
- `roomStore.ts` (zustand) — соединение, комнаты, участники, удалённые
  снапшоты, очередь `pendingGmEdits` (предложения мастера до решения),
  статусы «кто редактирует».

### 3.7. Шов с сейвами и стором

- Штамп комнаты на сейве **по образцу folder (патч 212)**:
  `room: { code, role: 'player' | 'gm-copy', linkedCharacterId,
  ownerToken? } | null`. Мастерская копия хранится локально у мастера
  как обычный персонаж с `role='gm-copy'` (открывается и правится
  **теми же экранами** — это главное упрощение), `linkedCharacterId`
  связывает её с id персонажа игрока. В списке — значок связи и имя
  игрока.
- **Что хранит сейв (вопрос владельца 2026-09-28)**: сейв по-прежнему
  хранит ОДНОГО персонажа + штампы (`folder`, `room`). Состав комнаты
  числом нигде не хранится — он выводится: на сервере — реестром членов
  комнаты; на устройстве мастера — набором gm-copy сейвов внутри
  папки-комнаты (каждая копия — обычный самостоятельный сейв → едет в
  облако и считается в папке как любой персонаж). Пустая комната
  (игроков ещё нет) существует на сервере + как папка мастера;
  её привязка (код + ownerToken) живёт в записи папки слоя БД
  (`character_folders` + код/токен комнаты — бамп SCHEMA_VERSION db, не
  сейва), а переезд пустой комнаты на другое устройство — через любой
  gm-copy/свой сейв с тем же штампом + восстановление по ownerToken §3.3.
- **Адрес комнаты едет в Google-синхронизацию** (вопрос владельца от
  2026-09-28 — да, пишем): штамп лежит в сейве → действующий
  `googleDriveSync` разносит его по устройствам пользователя сам, без
  нового кода. Синхронизируется ТОЛЬКО привязка (код/роль/токен); живое
  состояние (участники онлайн, последние снапшоты, ревизии) — удел
  сервера. Два устройства одного пользователя с одним сейвом уживаются
  по общему закону LWW (публикует то, где сейчас правят).
- Паспорта в том же патче: `src/store/characterState.ts` +
  `saveSnapshot.ts` (иначе упадёт тест data-passports). Вопрос версии
  сейва решаем по прецеденту v24 (поле опциональное, преобразований нет).
- Исходящий путь: хук «после записи» в `startCharacterAutosave`
  (`src/saves/characterSaves.js`): у персонажа есть room-штамп и правка
  локальная → `char.publish` с инкрементом revision.
- Входящий путь: пришёл `char.publish` → валидация как при импорте →
  `db.saveCharacter` → если персонаж открыт — перезагрузка стора по
  обычным правилам загрузки (origin='remote').
- Аватары в снапшоте **не едут** (тяжёлые data-url) — этап 5: отдельный
  обмен по md5 по образцу `avatarSync.js`.

### 3.8. UI

- Шапка `HomeScreen` (`languageRow`, сейчас `space-between`: меню —
  языки): по центру кнопка **«Админ»/«Пользователь»**; переключает новую
  настройку `uiMode` в `appSettingsStore` (по образцу
  `characterFoldersEnabled`: значение + сеттеры + селекторы, паспорт).
- Режим мастера: тот же HomeScreen, но список — из `roomStore`: папки =
  комнаты; «создать папку» → `room.create` → диалог с адресом комнаты и
  **кнопкой «Копировать адрес»** (web — `navigator.clipboard`; натив —
  fallback без новой зависимости на этапе 2, `expo-clipboard` — по
  решению в патче). Адрес дублируется в заголовке открытой
  папки-комнаты с той же кнопкой — «откуда-то копировать» = с папки
  всегда можно. Внутри — карточки gm-copy.
- Меню ячейки персонажа (`CharacterCell`: скачать/дублировать/удалить) —
  пункт **«Сервер»** → диалог ввода адреса (TextInput) → `room.join` +
  первый `char.publish`; когда связь есть — состояние «в комнате
  GM-7Q3-K9M», тумблер «принимать правки мастера без подтверждения»
  (§3.5, по умолчанию ВЫКЛ) и пункт «Отключиться».
- **Как игрок видит правки мастера (вопрос владельца 2026-09-28)** —
  три точки входа + окно сравнения:
  1. **Диалог при получении** (AlertHost): «Мастер предлагает изменения
     персонажа — Посмотреть / Отклонить / Позже». Очередь предложений не
     копится диалогами — новое предложение заменяет старое (оно устарело).
  2. «Позже»/закрытое приложение → **бейдж на карточке персонажа** в
     списке и **баннер на его экранах** («Есть предложение от мастера —
     посмотреть»). Предложение не теряется: хранится на сервере до
     решения/TTL и доставляется при следующем входе в комнату.
  3. **Окно сравнения** («Посмотреть»): список изменений из `editDiff`
     по секциям листа (характеристики, навыки, инвентарь, здоровье…),
     строки вида «Сила: 5 → 6», «Крышки: 120 → 85», «Добавлено:
     Стимулятор ×2», «Удалено: 10мм пистолет»; предупреждение, если
     `baseRevision` устарел («вы меняли персонажа после этого
     предложения»). Кнопки: **«Применить всё»** / **«Отклонить»**.
     Закон длинных окон: заголовок и кнопки зафиксированы, список в
     ScrollView (финт 402). Изменений нет (мастер переслал то же) —
     показываем «изменений нет» и только «Закрыть» (авто-решения нет).
- **Авто-приём директив** — короткое уведомление с тем, что применил
  мастер (строка/тост над экраном персонажа + запись в журнал),
  диалогом не прерываем.
- Индикаторы: точка соединения в шапке; баннер «редактирует мастер»
  поверх экрана персонажа; на карточке gm-copy у мастера — метки
  «ожидает решения игрока / принято / отклонено».
- i18n: новые ключи зеркально в `i18n/ru-RU` и `i18n/en-EN`
  (home.adminMode.*, home.server.*, admin.rooms.* — названия уточнятся в
  патче).
- Закон владельца о длинных окнах: любое новое окно со списком/текстом —
  заголовок и кнопки вне прокрутки, контент в ScrollView (финт 402).

### 3.9. Граница «движок / сеттинг» (мастерское пространство — движковое)

Решение владельца 2026-09-28: пространство мастера — **само по себе
движковая часть**; сеттингу в нём принадлежит только содержимое —
и этого пространства **может не быть**.

- **Движок (универсально, без импортов `modules/...`)**: транспорт и
  протокол (`server/`, `src/room/`), адреса и токены, роли
  мастер/игрок, модель правок §3.5, кнопка «Админ/Пользователь» и режим
  `uiMode`, диалоги входа/копирования/согласия, штампы `room` в сейве,
  лимиты. Ничего Fallout-специфичного в этих слоях нет: сервер вообще не
  знает о сеттингах, клиентские модули `src/room/` — тоже.
- **Сеттинг (через дверь модуля, как уже принято в движке)**: дефолтный
  префикс комнаты (fallout может задать свой вместо `GM`); подписи ролей
  в UI («Мастер»/«GM»/«Хранитель»… — словарь сеттинга); **содержимое
  `gm.directive`** — что вообще бывает «состоянием»: у fallout это
  каталог состояний и болезни модуля (`i18n/conditionsCatalog.js`,
  `modules/fallout/diseases`). Конверт директивы универсален
  (`{ kind, data }`); `kind` регистрирует модуль, интерпретатор
  живёт в модуле. Сеттинг без состояний → раздел директив просто не
  показывается, комнаты работают (правки персонажей — чисто движковые).
- **Пространства может не быть**: кнопка «Админ» рендерится только если
  (а) задан адрес сервера (`EXPO_PUBLIC_ROOM_SERVER_URL` или тот же
  origin) И (б) активный сеттинг не запретил пространство
  (флаг-паспорт в двери модуля, напр. `gmSpace: false`). Иначе приложение
  полностью одиночное: ни кнопки, ни пункта «Сервер», ни сетевых
  подключений — отсутствие пространства ничего не ломает.

## 4. Этапы (один этап = один патч/серия, старт — по слову владельца)

0. **Сервер-скелет — СДАН 2026-09-29**: `server/` (node http + `ws`:
   статика `dist/` + upgrade `/ws`, `room.create`/`room.join`/релей
   `char.publish`, генерация кода 6 знаков, квоты/рейт-лимиты, TTL пустых,
   ownerToken-восстановление), клиент `src/room/` (`roomClient` — очередь,
   reconnect с backoff, heartbeat; `roomStore`), команда `npm run serve:app`.
   Вместо Express — чистый node http (меньше зависимостей). Критерий
   выполнен: два клиента видят presence друг друга (интеграционный тест).
1. **Каркас режимов — СДАН 2026-09-29**: `uiMode` в `settingsCatalog`
   (select user/gm, не показывается в окне настроек), кнопка
   «Админ/Пользователь» по центру шапки с гейтом §3.9 по адресу сервера
   (флаг-паспорт сеттинга `gmSpace` — пока не реализован: модульная
   система сеттингов молодая, выносится в отдельную серию).
2. **Комнаты — СДАН 2026-09-29**: создание папки в режиме мастера =
   `room.create` + диалог с адресом и копированием (веб — clipboard),
   бейдж кода на папке и плашка с адресом/числом игроков в заголовке;
   у игрока пункт «Сервер» → ввод адреса → `room.join` + связка
   `character_room_bindings`, авто-rejoin на старте, бейдж на карточке.
   **Отступление**: связка персонаж↔комната хранится в таблице
   устройства, НЕ в штампе сейва (штамп + паспорта + облако перенесены
   в этап 3 вместе с публикацией — иначе серия раздувается).
3. **Публикация персонажа**: `char.publish` → копия у мастера
   (readonly). Критерий: карточка игрока открывается у мастера обычными
   экранами.
4. **Двусторонние правки по §3.5**: revision/LWW (игрок → мастер авто),
   предложение→решение (мастер → игрок): `editDiff`, диалог, бейдж/баннер,
   окно сравнения с «Применить всё»/«Отклонить», тумблер постоянного
   разрешения, хук автосейва, анти-эхо, «кто редактирует». Критерий:
   правка игрока видна мастеру за ≤2 с; правка мастера применяется у
   игрока только после просмотра и «Применить» (или тумблера).
5. **Задел владельца**: `gm.directive` (состояния/счётчики — авто-приём
   с уведомлением, толкование в сеттинге §3.9), аватары, PIN мастера,
   персистентность комнат.

Каждый этап: обе локали, зелёный `npm test`, паспорта при новых полях,
2–3 строки в `state.md`, при смене механики — правка этого документа.

## 5. Тест-план (vitest)

- unit: `roomCode` (алфавит, нормализация с дефисами, границы длины),
  редьюсеры протокола и LWW (старая ревизия отброшена, равная — без
  дубля), анти-эхо; **`editDiff`**: поле изменено/добавлено/удалено,
  инвентарь (по идентичности предмета: добавлен/удалён/количество),
  вложенные секции, пустой diff; **модель согласия**: предложение от
  мастера не применяется без approve; reject оставляет персонажа игрока
  нетронутым; тумблер постоянного разрешения применяет без диалога;
  baseRevision устарел → предупреждение, решение всё равно игрока;
  **директива применяется сразу** (без approve) и порождает
  уведомление.
- сервер (интеграция): ws-клиент из теста: create/join/publish/рассылку,
  предложение живёт до решения (и TTL), rate-limit, TTL, лимит размера,
  квоты (комнат на мастера, членов в комнате), уникальность кодов при
  параллельном создании.
- клиент: `roomStore` поверх мок-транспорта; шов автосейва — мок-портом;
  видимость кнопки «Админ» по §3.9 (нет сервера/запрет сеттинга).
- ручной чек-лист двух браузеров: переподключение, оффлайн-очередь,
  одновременная правка, вход по неверному адресу, копирование адреса,
  сценарий «мастер предложил → игрок отклонил → метки у мастера».

## 6. Риски и открытые вопросы

- Хостинг сервера 24/7 (Replit Always-On / Reserved VM или VPS) —
  решить **до этапа 2**, цена вопроса уточняется владельцем.
- LWW осознанно проигрывает одновременным правкам одного поля (редкий
  случай за столом); жёсткий замок — по запросу. На стороне игрока
  LWW подкреплён моделью согласия §3.5: скрытая перезапись невозможна
  в принципе, мастер всегда проходит через «Применить/Отклонить».
- Ссылка-секрет: комнату может читать/писать любой обладатель кода —
  приемлемо для сессии, но адрес не публикуем в открытом виде в UI
  сверх необходимого.
- **Перезапуск сервера** до этапа 5 (без персистентности): реестр
  комнат теряется → устройства мастера при переподключении
  восстанавливают комнату под тем же кодом по ownerToken из штампа
  (§3.3); игроки просто входят заново по прежнему адресу.
- Открыто: точечные патчи вместо полного снапшота (`char.patch`) —
  отложено до появления реальной нагрузки; формат-задел в протоколе
  заложен.
