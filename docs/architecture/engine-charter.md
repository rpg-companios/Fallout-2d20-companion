# Устав движка и порядок работы (engine charter)

> **Назначение.** Единая точка правды для разработки. Новая сессия начинает с чтения этого файла.
> Если желаемое изменение противоречит уставу — это либо ошибка, либо требуется явное решение
> владельца и правка устава в том же патче. Каждое правило раздела 3 обеспечено предохранителем
> (тест/компилятор): «сделать не так, как предписывает программа» должно падать до сдачи.
>
> Владелец — не программист: объяснения и чейнджлоги — игровыми терминами на конкретных примерах.

## 1. Статус проекта

- Приложение: компаньон Fallout 2d20 (React Native + Expo, состояние — zustand).
- Сеттинг — модуль `modules/fallout/` (+ `modules/fallout/survival`); движок сеттинга не знает.
- **Завершено (факты, без привязки к нумерации):**
  - Всё состояние персонажа — в едином хранилище (`src/store/characterStore.js`);
    старый файл-раздатчик и его обёртка в точке входа удалены; фасадов нет.
  - Сохранения — отдельный модуль без React (`src/saves/characterSaves.js`); автосохранение — часть приложения.
  - TypeScript-слой паспортов: данные хранилища (`characterState.ts`), формат сейва (`saveSnapshot.ts`),
    операции (`characterActions.ts`) — с контрактными тестами.
  - Формат сейва v2: картотека модов не пишется; при загрузке старых сейвов мост переносит её записи на предметы.
  - Чейнджлоги обновлены; предохранитель существования относительных импортов добавлен; устав — этот файл.
- **Очередь намерений (ГИБКАЯ — не план и не обязательство):**
  Владелец меняет состав и порядок в любой момент; пункты могут уходить и возвращаться.
  Утверждено 2026-09-18: идёт TypeScript-серия по плану
  `docs/architecture/typescript-migration-plan.md` — движок (`domain/`, `src/`, `db/`,
  `i18n/`, движковые экраны `components/`, `App.tsx`) переводится на TS; сеттинг
  `modules/fallout` остаётся живым JS за типизированной дверью (адаптер + гварды данных).
  Движковые экраны: Инвентарь первым, HomeScreen вторым. Миниатюры HomeScreen — отдельная
  фича, с конверсией не смешивать. Цель серии — ловить ошибки до старта приложения
  (`tsc` в песочнице, предохранители при сдаче, гварды при загрузке пакета).

## 2. Система правок (цикл сдачи патча)

1. Один шаг = один патч. Номер — только ярлык доставки: берётся следующий свободный
   (последний сданный + 1) и используется в имени файла и команде применения. После шага приложение рабочее.
2. Перед сдачей ОБЯЗАТЕЛЬНО: полный `npx vitest run` + `tsc --noEmit` (все предохранители зелёные).
3. Коммит в ветку `arena/01a08a17-fallout-2d20-companion` → файл патча в `patchs/` → коммит файла → push.
4. Владелец применяет `./apply-patch.sh <номер>` (скрипт сам ставит недостающую цепочку).
   **Ручной перенос файлов запрещён** (инцидент с потерей правок при ручном копировании).
5. e2e-проверка разработчика (каждый патч): чистый checkout 565b417 из локального клона,
   `sed` ветки в apply-patch.sh на актуальную, `./apply-patch.sh N`, сверка ключевых файлов
   `git hash-object` с рабочим деревом (IDENTICAL).
6. Отчёт владельцу: что случилось игровыми терминами + примеры; отдельно — риски и найденные дефекты.
7. **Правило вопросов:** есть варианты развития или неясность — спрашивать обязательно, не додумывать.

### Окружение разработчика (песочница)
- Песочница периодически пересоздаётся: `node_modules` исчезает → `npm ci`;
  `.git` откатывается к 565b417 при живом рабочем дереве → восстановление:
  `git fetch origin <ветка> && git reset FETCH_HEAD` (дерево не трогать; коммит+пуш после КАЖДОГО шага).
- Названия инструментов по памяти не писать; heredoc — только полная перезапись файла;
  `require()` в ESM-коде запрещён (vitest); `sed`-правки «по памяти» — нет.

несовместимое с программой изменение не проходит тесты, а не ловится на запуске.

## 4. Инварианты геймплея (решения владельца, по книге)

- **Усталость:** −⌊N/2⌋ текущих ОЗ за игровой час активности. Сон из правила исключён;
  лечение — постелью. Сжигание еды/воды сном НЕ менять.
- **Болезни:** «Сопротивляться» — одна попытка в сутки; лечение снижает ранги болезни.
- **Предмет = база + id модов на предмете.** Имена собирает каталог («тупой сборщик»);
  пример: `weapon_huntingRifle_05_76_48_35` → «.50 длинноствольная охотничья высокоемкая тихая винтовка».
- **Формат сейва v2:** картотека модов в запись не идёт; мост при загрузке переносит записи
  старых сейвов на предметы; записи без пары — только чтение в инвентаре.
- **Смена комплекта:** здоровье/радиация/сцены/условия/журнал доз/tagged-навыки переживают
  смену. Полный («жёсткий») сброс хранилища — опасный инструмент: любое его новое
  использование обязано осознанно собрать переживаемое состояние (был инцидент с потерей).
- **НЕ ТРОГАТЬ без владельца:** цепочку миграций сейва, данные и тексты комплектов и крышек,
  модалку выдачи комплекта, резолвер комплектов, соответствующие тексты интерфейса.
- **Силовая броня:** алерты слоя — временный компромисс; программное надевание до готовности
  состояния запрещено (перепроверка не отменяет уже надетое).
- **UI:** без текстовых подсказок «что делать» — индикация цветом.

## 5. Архитектура после Шага 8 (карта)

- `src/store/characterStore.js` — единственный источник; слайсы: `robotSlice`, `powerArmorSlice`,
  `orchestratorsSlice` (расходники/болезни/сцены), `stateExtensions`, `effectsSync`, `selectors`.
- Derived-самосинхронизация: стор сам пушит данные экипировки подпиской (вне рендера);
  фабрика полей сеттингов — действие стора (`ensureStateExtensionFields`).
- Сейвы: `src/saves/characterSaves.js` (снапшот/сохранение/загрузка/список/удаление/автосейв);
  база — `db/` (канон), облако — `components/cloudSync/`, файловый обмен — `domain/characterTransfer`.
  Автосейв: только для сохранённого героя с известной записью, с паузой, пропуск неизменённого;
  стартует в точке входа после готовности базы и хранилища. Таймер блока СБ — в точке входа.
- Универсальный движок: общее ядро + сеттинг-паки через реестр расширений состояния
  (`{id, fieldKey, factory, hydrate, reset}`) и встраивание сеттинговых миграций в общую цепочку.
  Сейв = конверт с версиями (`schemaVersion`).

## 6. Стиль и коммуникация

- **Роль владельца — архитектор программы**: он держит в голове данные и их потоки,
  взаимодействие экранов и ожидаемое поведение программы. Поэтому КАЖДОЕ описание
  изменения — это описание ПОТОКА ДАННЫХ: какие данные, откуда, куда, через какой
  механизм, в какой момент (какое действие игрока/событие), и что меняется в
  поведении или на экране.
- Запрещено сжимать изменение в жаргонную метафору («кожанка мутирует в стор»).
  Правильная форма: «броня из категории «кожаная броня» сохраняет свои модификации
  и улучшения в общее хранилище состояния; при загрузке сохранения каталог
  восстанавливает её имя и статы по идентификатору предмета».
- **Уровень детализации — поведение и данные, НЕ код.** Владелец не писал внутренние
  функции и не обязан их знать: «getCharactersList() пишет через db.saveCharacter()»
  читается как «кусок кода делает с куском кода». В отчётах НЕ называть имена
  функций, файлов и API. Формула описания: «сейчас <наблюдаемое поведение> →
  в патче <как изменится поведение или хранение данных>». Уровни допустимых
  понятий: экран → хранилище состояния → сохранение/каталог → поведение.
  Образец: «Когда вы меняете что-то у сохранённого героя, игра через полсекунды
  после последнего изменения сама обновляет его запись в хранилище сохранений;
  подряд идущие изменения записываются один раз, после паузы».
- Термины (стор, слайс, паспорт, конвейер) — допустимы только рядом с расшифровкой
  потока данных, который они называют. Игровые примеры — дополняют поток, не заменяют.
- Решения с вариантами — через явный вопрос владельцу (не додумывать).

### Протокол отчёта об ошибке (формат согласован с владельцем)
Каждая ошибка, дошедшая до владельца, описывается пятью строками:
1. **Симптом** — что видно (цитата сообщения, экран).
2. **Орган** — какой слой: окружение (машина) / адреса между частями / контракты-паспорта /
   типы / поток данных во время работы / слой записи на диск.
3. **Нога** — первопричина, потоком данных (откуда что не потекло).
4. **Почему не поймали раньше** — какой слой проверки пропустил и чего не хватало.
5. **Что меняю** — фикс + при необходимости новый предохранитель, чтобы класс ошибки умер.
- Коммиты и докстринги — по-русски; код-идентификаторы — английские.
- Чейнджлоги: `docs/changelog.ru.md` + `docs/changelog.en.md` (парно), новые записи сверху.

## 7. Уроки (не повторять)

- Воссоздавая хелперы — брать оригинал из истории Git, не писать «по докстрингу» (был случай семантической подмены).
- Наивные проверки «строки нет в файле» ломаются об комментарии-истории — нужны контекстные проверки или разбор структуры.
- Разбор структуры кода не резолвит адреса импортов — для этого отдельный предохранитель (раздел 3, п.6).
- Большой патч без промежуточных коммитов = риск. Коммит+пуш после каждого шага.
- Экраны переводить на TypeScript, когда они успокоились; кипящий код — после фичевой волны.

## 8. Диагностика — видение владельца (ЗАКЛАДКА, не в работе)

- Желаемое (формулировка владельца): **логгер действий-команд**. Владелец включает
  диагностику одной командой из консоли браузера, затем обычными нажатиями проходит
  сценарий в программе; лог показывает, откуда что и куда потекло: кого создали,
  что выбрали, что изменилось и что не поменялось. При ошибке владелец прикладывает
  этот лог к отчёту (по протоколу пяти строк выше) — «ноги ошибки» видны по логу.
- Основа уже существует: встроенный дневник программы — по умолчанию выключен
  (ноль шума и тормозов для игроков), включается с компьютера из консоли, хранит
  буфер последних событий по категориям с выгрузкой. Будущий логгер ляжет на него;
  сейчас на пути «загрузка героя: картотека пар → предметы по id → каталог →
  хранилище состояния» дневник пишет только сбои, сама механика — молча.
- Идея «отчёта о загрузке» (сколько пар легло на предметы / осталось в архиве;
  скольких предметов каталог не узнал; сводная строка по-русски) — обсуждена,
  НЕ в работе, ждёт решения владельца.
