## 1. Присутствие и комната (`RoomPresence`)

> Уже сохранено в 447; не меняется.

- `roomServer` — единый источник правды о том, кто в комнате (`playerId` ↔ `roomId`).
- `isRoomServerConfigured()` (из `src/room/roomClient.ts`) — проверка доступности.
- **Создание комнаты (`ROOM_CREATE`)** — это действие **админа**, выполняемое из **админской секции** (экраны админа, не из пользовательской секции). Комнате присваивается код (`roomCode`, формат `GM-XXX-XXX`).
- **Подключение игрока (`ROOM_JOIN`)** — это действие **пользователя/игрока**, выполняемое из **пользовательской секции** (карточка персонажа `CharacterCell` → пункт «Сервер» (`onServer`) → модалка `serverDialog` с вводом кода `GM-XXX-XXX` и кнопкой «Подключиться»). Пользователь никогда не создаёт комнаты — только подключается к существующим.
- **Действие админа (`AdminAction`)** требует: `admin.online == true` и `targetPlayer.online == true` в одной `roomId`. Без этого — отказ.
- **Просмотр (`ViewMode`)** работает через `lastSnapshot` (см. §3). Не требует `online`, но требует доступ (админ знает `playerId` или видит его в списке подключавшихся к комнате).

## 2. Снапшот (`Snapshot` / `lastSnapshot`)

- Формат: **тот же JSON-персонажа**, что в памяти приложения. Не отдельная схема.
- Хранение: `roomServer` хранит `lastSnapshot` для каждого `playerId` в `roomId`.
- Обновление: клиент отправляет снапшот в `roomServer` (автоматически или по событию, например, после сессии или по таймеру); админ получает `lastSnapshot` для просмотра.
- **Разница в режиме админа (свои экраны vs. просмотр персонажа):**
  - **Свои экраны админа:** выбор персонажей, управление контейнерами, интерфейс эффектов (создание `EffectPayload`), просмотр списка подключавшихся. Эти экраны не связаны с данными конкретного персонажа.
  - **Просмотр персонажа (`readonly`):** админ выбирает конкретного персонажа → загружается `lastSnapshot` → отображаются стандартные экраны (`CharacterScreen`, `perks`, `equipment`, `inventory`, `parameters`) в режиме `readonly`. Никаких правок, никаких кликов по счётчикам. Выход возвращает на экраны админа.
- Оффлайн-просмотр: админ выбирает персонажа из списка (подключавшихся к комнате) и видит `lastSnapshot`. Править не может, эффекты не может насылать (требуется `online`).

## 3. Предметы и контейнер (`ContainerPayload`)

> Основано на 446/447 (`OwnEquipmentSection`, «Самодельное снаряжение» / `Homebrew Equipment`), закон 438.

### 3.1 Формат предмета в контейнере / инвентаре / снапшоте

Каждый предмет — ссылка на каталог. **Не встраивается полный JSON предмета.**

```typescript
interface CatalogItemReference {
  catalogItemId: string;  // id из каталога (нативный или паковый)
  packRef?: string;        // id пакета (например, "forge-5173"); отсутствует для нативных
  qty: number;
  price?: number;          // виден всегда (для торговли)
  weight?: number;         // виден всегда (для веса инвентаря)
  // Параметры предмета (stats, mods, slots и т.д.) НЕ хранятся в снапшоте.
  // Они вычисляются при загрузке/рендере из файла данных каталога по catalogItemId (+ packRef, если есть).
}
```

- **Нативный предмет:** `packRef` отсутствует или `null`.
- **Паковый предмет (`homebrew`):** `packRef` = `packId` из `itempack/`.
- **Без установленного пакета у получателя:** предмет сохраняется в инвентаре как `CatalogItemReference`, но приложение **не может обогатить** его параметрами (нет доступа к файлу данных пакета). Пользователь видит `catalogItemId`, `qty`, `price`, `weight`. Не может надеть, модифицировать или использовать (кроме как «строка в сейве»). После установки пакета — автоматическое обогащение при следующей загрузке.

### 3.2 Контейнер (`ContainerPayload`)

```typescript
interface ContainerPayload {
  containerId?: string;     // опционально, для торговца или готового контейнера
  items: CatalogItemReference[];
  // Контейнер содержит как нативные, так и паковые предметы.
  // Валидатор проверяет: если `packRef` указан — пакет должен быть известен валидатору (см. item-forge-plan.md v3).
}
```

- Админ создаёт контейнер через экран (по образцу экрана получения добычи + инвентарь).
- Пользователь видит содержимое (если пак установлен — с параметрами; если нет — минимальное представление).
- Торговля: двупанельное окно (инвентарь пользователя ↔ содержимое контейнера/торговца). Пользователь сам выбирает, что продаёт, что покупает.
- Завершение (`finish`): приложение выполняет атомарную транзакцию с экономической валидацией (контракт `characterStore` из `__tests__/saves/currency-store-slice.test.js`):
  1. Проверяет баланс `currency` (через `spendCurrency`): сумма покупок не может превышать имеющиеся средства (`delta > state.currency` → `{ ok: false, reason: 'not-enough-currency' }`, транзакция отклоняется, ничего не меняется).
  2. Проверяет наличие продаваемых предметов у пользователя (`spendItemStacks`): нельзя продать больше, чем есть (`qty` в инвентаре); при недостатке — `{ ok: false, reason: 'not-enough-items' }`, отказ.
  3. Проверяет наличие у контейнера/торговца продаваемых предметов в нужном количестве (`qty` в `CatalogItemReference` контейнера); при недостатке — отказ.
  4. При успешной проверке: атомарно списывает средства (`spendCurrency`), начисляет от продажи (`earnCurrency`), убирает проданное, добавляет купленное, обновляет `lastSnapshot`.
  5. Без пакета у получателя: предмет добавляется в минимальном виде (`catalogItemId`, `packRef`, `qty`, `price`, `weight`), без параметров (`stats`).
- Количество (`qty`) — всегда проверяется: нельзя купить больше, чем есть у торговца; нельзя продать больше, чем есть у пользователя. Никаких отрицательных балансов. Никаких частичных изменений.

## 4. Эффекты (`EffectPayload`)

> Основано на `domain/effects.js` (`createdAt`, `durationMs`, `expiresAt`, `scenesLeft`), `docs/effects-cell-refactoring.md`.

### 4.1 Единый механизм (нет «админского» движка)

Админ отправляет `EffectPayload`. Клиент (или сервер, при необходимости) применяет его через **тот же механизм**, что и для пользовательских действий (ручное нажатие счётчика, применение препарата и т.д.). Никакого отдельного байпаса.

### 4.2 Формат `EffectPayload`

```typescript
interface EffectPayload {
  effectId: string;              // id эффекта (статический каталог приложения, см. docs/effects-cell-refactoring.md)
  appliedAt: number;              // timestamp (ms) наложения (от клиента или сервера)
  sourcePlayerId?: string;        // кто наложил (админ или игрок)
  sourceRoomId?: string;          // из какой комнаты

  // Параметры — точечные, в зависимости от типа эффекта:
  amount?: number;                // m (например, +1 радиация)
  interval?: number;              // n (например, каждые 3 сцены)
  durationType: 'scene' | 'realtime' | 'permanent';
  durationValue?: number;         // количество сцен (для 'scene') или часов/минут (для 'realtime')
  durationUnit?: 'scenes' | 'hours' | 'minutes'; // для realtime

  targetCounter?: string;         // на что влияет: 'radiation', 'hp_max', 'food', 'water', 'fatigue' и т.д.
  operation?: 'add' | 'subtract' | 'modify_rate'; // тип операции
  modifier?: number;              // для modify_rate (например, +20% расхода еды при «жаре»)

  // Для сложных цепочек влияний (будущее, см. item-forge-plan.md §4):
  // influences?: InfluencePayload[]; // зарезервировано; ключ отклоняется валидатором (закон 438)
}
```

### 4.3 Правила жизни эффекта (критично)

Эффект **не прерывается** при отключении клиента или выходе из комнаты. Он живёт в снапшоте/БД и рассчитывается по дельте времени.

| Тип | Правило расчёта | Пример |
|---|---|---|
| `scene` | Каждые `interval` сцен (`SCENE_DURATION_MS` из `domain/effects.js`). При загрузке: `scenesPassed = Math.floor((currentTime - appliedAt) / SCENE_DURATION_MS)`. Оставшиеся применения: `remaining = Math.max(0, totalApplications - scenesPassed)`. | Радиация: `amount=1`, `interval=3` сцены, `durationValue=10` сцен. За 30 сцен = 10 применений. |
| `realtime` | По реальному времени: `remainingMs = expiresAt - currentTime`. При `currentTime > expiresAt` — эффект снят. | Зависимость от препаратов: `durationType='realtime'`, `durationValue=24`, `durationUnit='hours'`. Через 4 часа реального времени: осталось 20 часов. |
| `permanent` | Нет `expiresAt`. Живёт в снапшоте до явного снятия (`removeEffect`). | Постоянные модификаторы от черт/перков. |

- При входе в приложение (или при получении обновлённого снапшота) клиент сверяет `appliedAt` с текущим временем и пересчитывает состояние (`scenesLeft` или `remainingMs`).
- Эффект с `realtime` может истечь даже когда приложение было выключено; с `scene` — только при прогрессе сцен (но если клиент не играл, сцены не прошли, эффект не изменился).
- Постоянные эффекты (`permanent`) хранятся в снапшоте без `expiresAt`; их снятие — отдельная команда (будущий `AdminAction` или внутренний механизм).

### 4.4 Правило отправки (`AdminAction`)

```typescript
interface AdminAction {
  actionType: 'EFFECT_APPLY' | 'CONTAINER_GRANT' | 'TRADE_OPEN' | 'SNAPSHOT_REQUEST';
  targetPlayerIds: string[];  // пустой или ['all'] для всех в комнате
  payload: EffectPayload | ContainerPayload | TradePayload;
  scope: 'ROOM_ONLINE_ONLY' | 'SNAPSHOT_OFFLINE';
  roomId: string;
}
```

- `scope: 'ROOM_ONLINE_ONLY'` — действие возможно только если `admin` и `targetPlayer` в одной `roomId` с `online == true`.
- `scope: 'SNAPSHOT_OFFLINE'` — просмотр снапшота (`SNAPSHOT_REQUEST`) не требует `online`.

## 5. Режим просмотра (`readonly` / `view` mode)

> Не только `CharacterScreen`. Все экраны.

- **Админ имеет свои экраны (2-я сущность)** — в дизайне текущей программы, с функциями управления:
  - «Погода» (`Weather`) — управление погодными условиями для сцены/комнаты.
  - «Столкновения и повреждения» (`Encounters & Damage`) — создание столкновений, применение повреждений игрокам.
  - «Добыча и торговля» (`Loot & Trade`) — создание контейнеров, торговцев, управление добычей.
  - Выбор персонажей, управление контейнерами, интерфейс создания эффектов (`AdminAction`), список подключавшихся к комнате, просмотр снапшотов.
  - Эти экраны — не `CharacterScreen`; они — инструменты админа.
- **Когда админ входит в конкретного персонажа для просмотра (1-я сущность)** — загружается `lastSnapshot` и отображается **весь набор экранов** (`CharacterScreen`, `perks`, `equipment`, `inventory`, `parameters`) в режиме `readonly`. В этом режиме есть **кнопка выхода**, которая возвращает админа на его собственные экраны (2-я сущность).
- **Когда админ входит в конкретного персонажа для просмотра** (выбирает из списка или из снапшота) — тогда загружается `lastSnapshot` и отображается **весь набор экранов** (`CharacterScreen`, `perks`, `equipment`, `inventory`, `parameters`) в режиме `readonly`. Это временный режим просмотра; выход из него возвращает админа на его собственные экраны.
- Взаимодействие с UI отключено в режиме просмотра: нет кнопок изменения, нет перетаскивания предметов, нет кликов по счётчикам, нет добавления эффектов вручную.
- Индикатор: «Персонаж в комнате X, обновляется через `roomServer`» или «Оффлайн-просмотр (последний снапшот)».
- **Кнопка выхода из просмотра:** возвращает админа из 1-й сущности (экраны персонажа, `readonly`) во 2-ю сущность (экраны админа: «Погода», «Столкновения и повреждения», «Добыча и торговля» и т.д.).
- Если админ в комнате с пользователем (`online`) — снапшот обновляется в реальном времени (или по интервалу). Если офлайн — виден `lastSnapshot` на момент последней синхронизации.

## 6. Торговля и контейнеры — атомарность и валидация

- Пользователь выбирает предметы для продажи (из своего инвентаря) и для покупки (из контейнера/торговца) в двупанельном интерфейсе.
- Приложение проверяет: если в выбранных предметах есть `packRef`, у пользователя должен быть установлен этот пакет (для обогащения параметров). Если нет — предмет всё равно может быть куплен (как минимальная ссылка), но пользователь не сможет его использовать (надеть, модифицировать) до установки пакета.
- При нажатии «завершить» (`finish`): приложение выполняет атомарную транзакцию.
  1. Убирает проданные предметы из инвентаря пользователя.
  2. Добавляет купленные предметы (как `CatalogItemReference`).
  3. Обновляет снапшот (`lastSnapshot`) в `roomServer`.
  4. Если пользователь не установил пакет для купленного предмета — предмет добавляется в минимальном виде (`qty`, `catalogItemId`, `packRef`, `price`, `weight`), без `stats`.

### 10.1 Конфликт данных при синхронизации

- **Приоритет: данные игрока.** При подключении игрока и админа к комнате, если локальные данные игрока (из его приложения) отличаются от `lastSnapshot` в комнате, **локальные данные игрока перезаписывают снапшот**. Админ видит актуальную версию после синхронизации.
- Это предотвращает потерю оффлайн-прогресса игрока (уровни, перки, изменения характеристик).
- `roomServer` выступает релеем: получает актуальный JSON игрока, обновляет `lastSnapshot`, транслирует админу.

### 10.2 Хранение снапшотов (привязка к аккаунту)

- **Двойное хранение (как сейвы пользователя):**
  - **Локально:** `AsyncStorage` / локальный файл на устройстве (для работы без интернета).
  - **Google Drive:** привязано к аккаунту текущего пользователя программы (админа) — для доступа с других устройств (ноутбук на игре → ПК дома).
- **Комната (`roomId`) привязана к аккаунту.** Удаление комнаты в приложении текущего юзера → удаление связанных снапшотов из Google Drive и из локального хранилища.
- **Доступ с разных устройств:** админ входит в свой Google-аккаунт на другом устройстве → загружает те же комнаты и снапшоты из Drive; или работает оффлайн с локальной копией (`AsyncStorage`).
- **Разделение каналов:**
  - `googleDriveSync` (`syncAllCharactersWithCloud`): личные сейвы игрока + снапшоты комнат (хранение в Drive + синхронизация).
  - `AsyncStorage`: локальная копия снапшотов (для оффлайн-просмотра).
  - `roomServer`: релей для синхронизации в сессии (передача актуального JSON игрока админу, отправка `EffectPayload`).

### 10.3 Доступ оффлайн (без подключения к комнате)

- Админ загружает снапшоты **из локального хранилища (`AsyncStorage`)** или **из своего Google Drive** (`cloudSync` / прямой доступ к файлам) — в зависимости от наличия интернета и синхронизации.
- Видит `CharacterScreen`, `perks`, `equipment`, `inventory` в режиме `readonly`.
- Не может отправлять `AdminAction` (`ROOM_ONLINE_ONLY` — требуется подключение к комнате).

### 10.4 Toggle для поэтапной проверки

- `ADMIN_SCREEN_UI_ENABLED = false` (по умолчанию) в `components/screens/HomeScreen/HomeScreen.js`.
- Возврат в UI = `ADMIN_SCREEN_UI_ENABLED = true`.
- Это позволяет включать экран админа для проверки работы после каждого этапа внедрения, не ломая существующий интерфейс.
