# Единая модель защиты: броня / одежда / силовая броня — план упрощения

Дата: 2026-07-31. Анализ ветки `main` (после 905c49a + патч `fix-clothing-not-armor-mods`).
Состояние: **план, код не меняется**. Решения сверены с владельцем 2026-07-31:
- сейчас — только этот документ, без рефакторинга;
- полусобранный clothing-режим модалки — **оставить** как заготовку;
- силовую броню — **пока не трогать** (данные мёртвые, подключение отложено).

## TL;DR

Данные о снаряжении чистые и однозначные. Баги «моды утекают не туда» происходили
не из-за данных, а из-за того, что **код в пяти местах независимо угадывал вид предмета**
— по слоту, по областям защиты, по подстроке имени — и по умолчанию разрешал всё
(fail-open). Целевая модель: один резолвер вида защиты + белые списки модов из данных
(`fail-closed`). Реализация — маленькими шагами, когда владелец даст добро.

## 2. Диагноз: почему баги появлялись на «простой» механике

Корень зла — **слот вместо типа** и **fail-open умолчания**:

1. **Слот вместо типа.** `InventoryScreen.handleEquipArmor` кладёт обмундирование
   (`itemType: 'clothing'`, `clothingType: 'outfit'`, `allowsArmor: false`) в под-слот
   `.armor` — чтобы оно вытесняло броню. Дальше `WeaponsAndArmorScreen` считал:
   «лежит в слоте брони → броня → можно моды». Тип предмета никто не спрашивал.
2. **Fail-open.** Неизвестная категория брони исторически разрешала все 22 уникальных
   мода («можно всё, что не запрещено»). Стандартные моды фильтровались только по
   `protectedAreas` — у одежды области те же (`Body/Hand/Leg`), поэтому 8 из 15 модов
   формально «подходили».
3. **Трупы недоделанных фич.** `ArmorModificationModal` имеет half-built clothing-режим
   (`mode='clothing'`, ключ `appliedClothingModId`) под моды одежды, которых в данных
   нет. `isPowerArmorItem` (InventoryScreen) определяет силовую броню по подстроке
   «силов» в **названии** — эвристика, которой не место в проде.

Вывод: источник правды о виде предмета должен быть один, и он должен читать только
поля данных. Сейчас таких «угадывателей» пять: маршрутизация экипировки, рендер
строки брони, модалка, `getAvailableArmorMods`, `applyArmorMods`.

## 3. Целевая модель

### 3.1 Единый резолвер вида защиты (будущий шаг 1)

```js
// domain/ — единственное место, отвечающее «что это за защита?»
getProtectionKind(item) -> 'armor' | 'clothing' | 'powerArmor' | null
```

Правила (ПРАВИЛО от владельца — продублировать комментарием и тестом):

- Вид определяется **только полями данных**: `itemType`, `clothingType`,
  `armorCategoryKey` (и позже — поле силовой брони). **Никаких эвристик по имени,
  названию или слоту.**
- Неизвестный вид → `null`, и `null` означает «модов нет» (fail-closed),
  а не «разрешить всё».
- Все потребители (кнопка «Улучшить», модалка, `applyArmorMods`, расчёт КЗ)
  спрашивают только резолвер.

### 3.2 Моды — белый список из семейства (фактически уже так, закрепить)

- Источник модов — конфиг семейства в данных:
  `armor.json → allowedModCategories / allowedUniqueModCategories`.
- `protectedAreas` — второй фильтр **внутри** белого списка, а не врата.
- Тесты — в духе «можно только то, что разрешено»: для каждого семейства
  перечисляется точный разрешённый набор (так уже написано в
  `unique-mods-per-category.test.js` — эталон стиля).

### 3.3 Соотношение слоёв одежда/броня

Текущая слот-модель: 6 слотов тела (`head, body, leftArm, rightArm, leftLeg, rightLeg`),
у каждого два под-слота: `.clothing` и `.armor`. Особые случаи:

- `suit` / `allowsArmor: true` → `.clothing`, поверх можно броню. Моды у каждого свои.
- `outfit` (`allowsArmor: false`) → сейчас кладётся в `.armor`, чтобы вытеснять броню.
  Это **задокументированный хак** и именно он породил баги с модами. v2-патч закрыл
  течь, но модельно это костыль.
- Целевой вариант (шаг 2, отдельно, с миграцией сейвов): outfit/suit **всегда** лежат
  в `.clothing`; блокировка экипировки брони поверх outfit — **вычисляемая** проверка
  по `allowsArmor === false`, а не физический перенос в чужой слот.

### 3.4 Моды одежды — заготовка оставлена (решение владельца)

`ArmorModificationModal` хранит clothing-режим (`mode='clothing'`, `appliedClothingModId`).
Данных модов одежды нет (`data/equipment/` не содержит `clothes_mods.json`).
Когда владелец добавит данные — режим «оживёт» через тот же резолвер
(`kind === 'clothing'` → категории модов из конфига семейства одежды), без новых веток
в UI. До тех пор: кнопка «Улучшить одежду» скрыта, `getAvailableArmorMods` возвращает
пусто, `applyArmorMods` — no-op.

### 3.5 Силовая броня — пока НЕ трогаем (решение владельца)

Фактура на будущее, чтобы не переоткрывать исследование:

- `data/equipment/powerArmor.json` **существует и качественный**: 21 деталь
  (frame + raiderPower, t45, t51, t60, x01), `itemType: 'powerArmor'`, у деталей есть
  `hp`. i18n-файлы есть для обеих локалей.
- Но данные **никуда не подключены**: `i18n/equipmentCatalog.js` файл не импортирует,
  комплекты/магазины не ссылаются, слота/экипировки/кэдра нет. В игре получить
  силовую броню сейчас невозможно.
- `isPowerArmorItem` по подстроке «силов» в имени — удалить при подключении и
  заменить типом из данных.

Согласованный свод правил на тот момент (зафиксировать при подключении — ПРАВИЛО
от владельца):

1. Силовая броня — отдельный вид `kind === 'powerArmor'` со своими модами
   (по `allowedModCategories` семейства, когда данные будут).
2. Пока `hp` детали > 0 — её КЗ имеет **приоритет**: КЗ брони и одежды по этой области
   скрыты и игнорируются.
3. Когда `hp` детали = 0 — деталь не защищает, работают показатели подложки
   (броня/одежда под ней).

## 4. План по шагам (каждый — отдельный патч, только по команде владельца)

| Шаг | Содержание | Требует миграции сейвов |
|-----|-----------|------------------------|
| 1 | `getProtectionKind` в `domain/` + перевод всех потребителей на резолвер + инвариант-тесты | нет |
| 2 | Слот-рефактор: outfit/suit всегда в `.clothing`, блокировка брони вычисляется | **да** (пересадка предметов в старых сейвах) |
| 3 | Моды одежды — только когда появятся данные (`clothes_mods.json` + конфиги семейств) | нет |
| 4 | Подключение силовой брони: каталог, экипировка/кадр, приоритет КЗ по `hp`, прочность/ремонт, моды PA | да (новое поле состояния) |

Шаг 1 не меняет поведение — только убирает разброд угадывания (по сути подводит
код под уже принятые правила v1/v2). Шаги 2–4 — функциональные изменения.

## 5. Инвариант-тесты целевой модели (чек-лист для шагов)

- [ ] Каждое семейство брони получает **ровно** свой набор: std из белого списка +
      uniq своего семейства (уже есть — `unique-mods-per-category.test.js`).
- [ ] Одежда (любой `clothingType`) → 0 std / 0 uniq; `applyArmorMods` — no-op
      (уже есть, сохранить при рефакторинге).
- [ ] Неизвестная/отсутствующая категория → 0 uniq (fail-closed; уже есть).
- [ ] Резолвер: вид определяется только полями данных — тест с предметом, у которого
      «обманчивое» имя (напр. содержит «силов»), но `itemType: 'armor'` → kind `'armor'`.
- [ ] (шаг 2) outfit в `.clothing`-слоте → броня поверх заблокирована; КЗ считается верно.
- [ ] (шаг 4) PA: `hp > 0` скрывает подложку, `hp = 0` — подложка работает.

## 6. Свод ПРАВИЛ (от владельца) — держать в коде комментариями и тестами

1. Уникальные моды — только своего семейства; неизвестное семейство → ничего.
2. Одежда — не броня: армор-моды на одежду не действуют, даже если она в слоте брони.
3. Вид защиты определяется полями данных, а не слотом и не названием.
4. (на будущее) Силовая броня приоритетна: пока `hp > 0`, показатели подложки
   скрыты и игнорируются; при `hp = 0` — работает подложка.
