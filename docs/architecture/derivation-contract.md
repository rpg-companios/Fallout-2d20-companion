# Контракт выводимости (МК-1, патч 281)

> Статус: **реализован, изолирован**. Контракт и реестр живут в `src/engine/`,
> работают и покрыты тестом `__tests__/engine/derivation-contract.test.js`,
> но в работающую программу пока НЕ подключены — ни один экран, действие или
> экран-оркестратор их не импортирует. Подключение — МК-3 (патчи 283+).
> Это страховка: контракт приживается без риска для Fallout-модуля.

## Зачем

Диагноз карты каскада (`cascade-map.md`): производные значения хранятся в
сторе и пересчитываются 24 ручными вызовами по действиям, экраны держат свои
копии пересчёта. Разворот серии: сеттинг **объявляет** правила выводимости,
движок **исполняет** их и каскадирует. Движок универсальный (Fallout сегодня —
Герои, Disciples, свой сеттинг завтра), сеттинг — данные.

## Что объявляет сеттинг (`SettingExtension`, `src/engine/contracts/setting.ts`)

Основа — действующий контракт расширений состояния (патч 207):
`{ id, fieldKey, factory, hydrate, reset }`. Поверх него — секции выводимости:

| Секция | Тип | Что задаёт |
|---|---|---|
| `parameters` | `ParameterDefinition[]` | числа-параметры (атрибуты, навыки); v1 — только `kind: 'number'` |
| `derived` | `DerivedDefinition[]` | производные: `{ id, kind, deps, compute(ctx), description }` |
| `counters` | `CounterDefinition[]` | расходуемые ресурсы; `max` — число или **ссылка на производное** |
| `rankBands` | `RankBands[]` | ступени потолка ранга от параметра-входа |
| `requirements` | `Requirement[]` | гейты «можно ли»: `minValue` / `minRank` по параметру |
| `reactions` | `ReactionDefinition[]` | правила при изменении: `{ watch, on(changed, ctx) }` |
| `initialModifiers` | `ParameterModifier[]` | стартовые модификаторы ориджина/трейтов |

## Порядок модификаторов (`applyModifiers`, договор v1)

```
база → set (последний побеждает) → '+' и '-' (суммарно) → '%' (суммарно) → Math.round
```

- `set` — семантика «СИЛ в силовой броне = 11»: заменяет базу целиком;
  несколько `set` — берётся последний (переопределение сильнее дополнения).
- `'+'`/`'-'` аддитивны и коммутативны.
- `'%'` суммируются и применяются к результату аддитивов: +10% и +5% = ×1.15.
- Округление — один раз, в самом конце.

**Открытый вопрос владельцу (проверяется тестовым сеттингом 282):** в текущем
стеке Fallout есть только `+`/`-`; спека тест-сеттинга (+5/10/15%) впервые
требует проценты. Предложенное правило выше — база для решения.

## Реестр (`src/engine/derivations/registry.ts`)

`createDerivationRegistry()` → `{ register, order, evaluate, reactionsFor }`:

- **Валидация при регистрации**: id уникальны глобально; каждый id обязан
  начинаться с префикса сеттинга (`fallout.maxHealth`, `test.attr.strength`) —
  коллизии между сеттингами исключены конструктивно; `deps` непусты и ссылаются
  только на известные параметры/производные; цикл — ошибка регистрации
  с перечислением участников, а не вечный пересчёт.
- **Топологический порядок** (Кан): производное вычисляется после всех своих
  производных-входов. Параметры — источники.
- **`evaluate(state, modifiers)`** — чистый каскад: снимок параметров +
  модификаторы → `{ values, ceilings }`. Производные всегда свежие, вход не
  мутируется. Потолки счётчиков разрешаются в числа или производные.
- **`reactionsFor(changed)`** — отбор реакций по изменённым id (для МК-3).

## Проверка формы (дверь JS→TS)

`validateSettingExtension(ext)` возвращает список ошибок формы — сеттинги
остаются живым JavaScript, дверь проверяется при загрузке пакета сеттинга
(подключение — МК-3, вместе с адаптером данных).

## Критерий успеха (слово владельца, карта §8)

И Fallout, и мини-сеттинг (5 атрибутов, 7 навыков, 5 производных, 5 заклинаний,
бонусы +5/10/15%, потолок ранга от атрибута, манна = атрибут + навык)
описываются декларациями **без правок движка**. Мини-сеттинг уже описан
декларацией в приёмочном тесте — все 16 проверок зелёные.
