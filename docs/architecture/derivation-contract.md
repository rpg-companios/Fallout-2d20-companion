# Контракт выводимости (МК-1, патчи 281–284)

> Статус: **реализован, изолирован**. Контракт и реестр живут в `src/engine/`,
> работают и покрыты тестом `__tests__/engine/derivation-contract.test.js`,
> но в работающую программу пока НЕ подключены — ни один экран, действие или
> экран-оркестратор их не импортирует. Подключение — МК-3 (патчи 286+).
> Это страховка: контракт приживается без риска для Fallout-модуля.

## Зачем

Диагноз карты каскада (`cascade-map.md`): производные значения хранятся в
сторе и пересчитываются 24 ручными вызовами по действиям, экраны держат свои
копии пересчёта. Разворот серии: сеттинг **объявляет** правила выводимости,
движок **исполняет** их и каскадирует. Движок универсальный (Fallout сегодня —
Герои, Disciples, свой сеттинг завтра), сеттинг — данные.

## Что объявляет сеттинг (`SettingExtension`, `src/engine/contracts/setting.ts`)

Основа — действующий контракт расширений состояния (патч 207):
`{ id, fieldKey, factory, hydrate, reset }`. Поверх него — секции выводимости:

| Секция | Тип | Что задаёт |
|---|---|---|
| `parameters` | `ParameterDefinition[]` | числа-параметры (атрибуты, навыки); v1 — только `kind: 'number'`; конвейер модификаторов (`modifierPhases`) |
| `derived` | `DerivedDefinition[]` | производные: `{ id, kind, deps, compute(ctx), description, modifierPhases? }` |
| `counters` | `CounterDefinition[]` | расходуемые ресурсы; `max` — число или **ссылка на производное** |
| `rankBands` | `RankBands[]` | ступени потолка ранга от параметра-входа |
| `requirements` | `Requirement[]` | гейты «можно ли»: `minValue` / `minRank` по параметру |
| `reactions` | `ReactionDefinition[]` | правила при изменении: `{ watch, on(changed, ctx) }` |
| `initialModifiers` | `ParameterModifier[]` | стартовые модификаторы ориджина/трейтов |

## Модификаторы: порядок объявляют правила (слово владельца, 2026-09-18)

> Слово владельца: «Это программа rpg игр. Там есть правила, и как в правилах
> напишут, так % и будут рассчитываться. [...] Базовая скорострельность будет
> зависеть от установленных модов, % от черты будет влиять на неё, а перк уже
> после удваивать. Но может быть и случай, когда черта вместо базовой
> скорострельности будет увеличивать итоговую [...] А может вообще примениться,
> если скорострельность будет меньше или равна определённому значению.
> И это хрен угадаешь.»

**Принцип:** движок НЕ диктует порядок модификаторов — его объявляет правило
сеттинга. Контракт даёт словарь, правило — рецепт:

- **Фазы-якоря.** Значение объявляет свой конвейер: список фаз в порядке
  исполнения (`modifierPhases`). Каждый модификатор привязывается к фазе
  (`phase`). Якорь «+10% базовой» против «+10% итоговой» — это просто место
  фазы в списке. Дефолт, если фазы не объявлены: `['add', 'percent', 'mult']`
  (аддитивы → суммарный процент → множители).
- **Операции.** `'+'`, `'-'` — аддитивы; `'%'` — процент (в фазе суммируются
  одним множителем); `'×'` — множитель (перк «х2»); `'set'` — замена
  («СИЛ в силовой броне = 11»). Внутри фазы канонический порядок:
  set → аддитивы → процент → множители.
- **Условия.** Модификатор может нести `when(value, ctx)` — применяется,
  только если условие выполнено на входе фазы («перк действует, если
  скорострельность ≤ N»).
- **Округление.** Режим тоже диктует сеттинг (слово владельца, патч 284):
  `'math'` — математическое (0.5 вверх, по умолчанию), `'up'` — всегда в
  большую (32.01 → 33), `'down'` — всегда в меньшую (32.99 → 32), `'none'` —
  не округлять (32.2 остаётся 32.2). Объявляется на значении (`rounding`);
  фаза может округлить на своём шаге (`round: true` — тем же режимом,
  `round: 'up'` — своим). `(10+18)×1.15 = 32.2` может стать и 32, и 33,
  и остаться собой — по правилу.
- **Модификатор в необъявленную фазу** — ошибка с перечислением объявленных
  фаз, не молчаливый пропуск.

**Пример владельца (скорострельность), все варианты живут в тесте:**

| Правило | Объявление | Расчёт (база 5, моды +1/−2) |
|---|---|---|
| Черта +10% базы с модами, перк ×2 | `['mods','traitPercent','perkMult']` | 4 × 1.1 = 4.4 × 2 = 8.8 → **9** |
| Черта +10% итоговой (после перка) | `['mods','perkMult','traitPercent']` | 4 × 2 = 8 × 1.1 = 8.8 → **9** |
| Те же + пофазное округление | `round: true` на фазе | **8** против **9** — якорь наблюдаем |
| Условный перк ×2 | `when: (v) => v <= 5` | при базе 4.4 — сработает; при 7.7 — нет |

**Ярость ботаника (пример владельца):** порог «текущие ОЗ < 30% максимальных» —
это реакция (`watch: [maxHealth, текущие ОЗ]`), а максимум сам движется:
химия даёт +50% максимуму (модификатор `'%'` на производном), потолок
пересчитывается каскадом, и планка 30% сместилась — 12 из 30 = 40% (перк
молчит), но 12 из 45 = 27% (перк сработал). Всё в тесте контракта.

**Проценты от одной базы** (первое слово владельца о %) остаются чистой
функцией `applyPercent(база, проценты)`: «+15% жизней = база × 1.15,
округлённая математически»; «+15% защиты от магии огня = −15% входящего урона
от атаки со свойством огня» — тот же помощник для будущих каналов урона.

**Совсем дикие правила** — это `compute()`: производное может вычислить что
угодно из контекста; фазы покрывают типовые конвейеры, формула — всё остальное.

## Реестр (`src/engine/derivations/registry.ts`)

`createDerivationRegistry()` → `{ register, order, evaluate, reactionsFor }`:

- **Валидация при регистрации**: id уникальны глобально; каждый id обязан
  начинаться с префикса сеттинга (`fallout.maxHealth`, `test.attr.strength`) —
  коллизии между сеттингами исключены конструктивно; `deps` непусты и ссылаются
  только на известные параметры/производные; цикл — ошибка регистрации
  с перечислением участников, а не вечный пересчёт.
- **Топологический порядок** (Кан): производное вычисляется после всех своих
  производных-входов. Параметры — источники.
- **`evaluate(state, modifiers)`** — чистый каскад: снимок параметров +
  модификаторы → `{ values, ceilings }`. Производные всегда свежие, вход не
  мутируется. Потолки счётчиков разрешаются в числа или производные.
- **`reactionsFor(changed)`** — отбор реакций по изменённым id (для МК-3).

## Проверка формы (дверь JS→TS)

`validateSettingExtension(ext)` возвращает список ошибок формы — сеттинги
остаются живым JavaScript, дверь проверяется при загрузке пакета сеттинга
(подключение — МК-3, вместе с адаптером данных).
