# План: Кузница предметов (генератор домашнего контента)

**Статус:** план v3 (2026-10-19). **Этап P (прототип) СДАН 2026-10-19.**
**2026-10-25: Кузница выделена в самодостаточный репозиторий**
`rpg-companios/fallout2d20forge` — сборка/рантайм не читают файлы этого
репозитория; данные арсенала хранятся там слепками
(`src/data/forge-refs.json` + копии `src/itempack/{contract,validate}.js`,
штамп GENERATED) и обновляются командой `npm run sync -- --from <клон
этого репозитория>` (инструмент `tools/sync-from-main.mjs` там). План
остаётся здесь — контракт и движок принимают решения в этом репозитории.
**Интерпретатор деревьев влияний перенесён в будущее** — механика описана
(§4, §9) и зарезервирована в контракте (ключ `influences` отклоняется
ошибкой «зарезервировано», чтобы паки будущего не проходили молча).

Рамки сданного прототипа (осознанные, зафиксированы тестами/сообщениями):
- своя категория оружия (`weaponType` вне каталога) валидатор пока
  отклоняет (категории движутся после прогона владельца);
- операции модов — ванильные `{+, −, set}`; × и ÷ появятся вместе с
  интерпретатором влияний;
- свои моды назначаются ванильному ЛЮДСКОМУ оружию и своему любому;
  ванильному РОБОТ-оружию — пока нет (робо-слоты выводятся из
  applies_to_ids робо-модов, наш пак туда не лезет);
- каскад удаления режет массивы предметов/модов и надетые объекты;
  словари-карманы (`{id: count}`) осознанно не трогает.

Отдельное мини-приложение-генератор пользовательского контента. Стартовый
охват — оружие / броня / одежда с эффектами и **цепочками влияний**; целевой
охват — origin, trait, perk, собственные моды. Результат — **один JSON-файл**
(пак контента) для загрузки в основное приложение.

---

## 0. Решения владельца (2026-10-19)

1. **Размещение.** Генератор — **отдельное мини-приложение**, не экран основного.
2. **Формат.** Лёгкий контракт **«пак контента»**: один JSON-файл поверх
   активного сеттинга (не полный `.trpg`-сеттинг).
3. **Оформление.** В стиле экранов основного приложения. Выбор создаваемого
   типа — **по образцу окна категорий крафта** (`CraftingModal`: плитки по 3
   в ряд, углубление в выбранную плитку, кнопка «назад»).
4. **Модификаторы.** Цели — **включая S.P.E.C.I.A.L.** Операции: **+, −, set,
   ×, ÷**. Числа со знаком у «+» не запрещены (− дублирует отрицательный add,
   оставляем оба для читаемости UI).
5. **Модификации предметов учитываются**: оружие — слоты и совместимые моды
   (каталог `weapon_mods`), броня — `allowedModCategories`, одежда — её
   мод-категории. Создание **своих модов** — будущий тип пака, не v1.
6. **Сложные влияния — цепочками** в стиле Power Automate: выбираем стартовое
   условие («надели предмет», «получили урон», …), затем следующий шаг
   (простой модификатор или сложная механика), затем его параметры
   (что модифицирует / какое действие / какое значение).
7. **Варианты берём из текущего движка**: смотрим, как работают существующие
   effects/условия, и собираем варианты на их основе.
8. **ЗАКОН РАСШИРЕНИЯ:** новые условия/триггеры/механики пользователь
   **создать не может** — сначала правка движка (патч основного приложения),
   потом соответствующий вариант появляется в генераторе. Генератор никогда
   не пишет код механик, только ссылки на существующие.
9. **Локали.** Достаточно одного языка (ru или en). Без перевода выводится
   id, не заглушка.
10. **Будущее.** Тот же каркас — полноценный генератор origin, trait, perk
    (и собственных модов). Схема пака это не должна заблокировать (см. §2).

## 1. Аренда репозитория

Один репозиторий, **два приложения**:

```
Fallout-2d20-companion/
  src/itempack/                    — ОБЩИЙ модуль: контракт, схема полей,
                                     валидатор, реестры целей/условий/хуков,
                                     константы. Импортируют ОБА приложения.
  modules/fallout/…                — данные сеттинга (источник справочников)
  item-forge/                      — генератор (Vite + React + TS), порт 5173,
                                     статическая сборка в item-forge/dist/,
                                     отдельный деплой
```

Границы:

- **Правило одного поведения:** генератор собирает пак тем же кодом
  (`src/itempack/`), которым приложение валидирует его при загрузке.
- **Справочники** (качества, эффекты урона, боеприпасы, моды, категории модов,
  состояния, потребности, список целей/условий/хуков) генератор читает
  **на этапе сборки** прямо из `modules/fallout/` и `src/itempack/`.
  Без снимков и ручной синхронизации; обновление сеттинга ⇒ пересборка.
- Генератор не импортирует экраны/сторы основного приложения.
- Визуальное единство: в `item-forge/src/theme.js` — палитра/радиусы/типографика
  приложения (цвета `#0a0c10`, панели, рамки, акценты — с комментариями-ссылками
  на файлы стилей), оттуда мап в CSS-переменные. Расхождение — вопрос владельцу,
  не тихий дрейф.

## 2. Контракт пака контента v1

Один файл `<packId>.content.json`:

```jsonc
{
  "itemPackFormat": 1,
  "manifest": {
    "packId": "maria_arsenal",   // латиница/цифры/подчёркивание
    "name": "Арсенал Марии",
    "author": "Maria",
    "locale": "ru-RU",           // обязательная и единственная обязательная
    "requiresCore": 1,
    "version": 1
  },
  "names":  { "ru-RU": { "<id>": { "name": "…", "description": "…" } } },
  "items":  { "weapons": [], "armorSets": [], "clothingGroups": [] },
  // ЗАРЕЗЕРВИРОВАНО (будущие типы, валидатор v1 должен отклонять явно,
  // чтобы старый движок не молчал при новых паках):
  // "origins": [], "traits": [], "perks": [], "mods": []
}
```

Правила:

- id предмета **обязан** начинаться с `hb_<packId>_` (генератор ставит сам).
  Чужой префикс или дубль — ошибка с путём.
- Ссылки на справочники движка — по существующим id; неизвестный id —
  ошибка с путём (закон контракта сеттинга: не «подчищаем» чужое).
- Своя категория оружия (`weaponType` вне набора) — **отображаемая метка**,
  механики, привязанные к id категорий (черты, ближний бой), на неё не
  распространяются. UI генератора честно предупреждает; валидатор не режет.
- Свои `damageType`/`mainAttr`/`mainSkill`/слоты модов — **запрещены**
  (механика по id).
- Картинки: ссылка или имя ассета, в файл не вживлять. Пусто — заглушка с
  иконкой типа (отрисовывает принимающая сторона).

Валидация (`src/itempack/validate.js`): один проход, собирает **все** ошибки
с путями. Тесты — золотые фикстуры валидные/невалидные.

## 3. Схема полей и мастер

`src/itempack/fieldSchema.js` — декларативное описание полей (тип,
обязательность, справочник, диапазон, подсказка). Из неё строятся и форма
генератора, и половина валидатора.

- **Оружие**: id; weaponType (список + «своя», с предупреждением); damage;
  damageType (мультивыбор из каталога); fireRate; range (C/M/L); ammoId
  (каталог боеприпасов или «—»); mainAttr; mainSkill; weight/cost/rarity
  (свободные числа); qualities[] (каталог 32); effects урона[] (каталог 10);
  **слоты модов**: выбор слотов из каталога и модов в каждый слот (из 164,
  фильтр по слоту) ⇒ запись в стиле `weapon_mod_slots`; картинка; влияния
  (см. §4).
- **Броня**: семейство { id; allowedModCategories[] (чекбоксы из
  armor_mods/uniq); tiers (standard|sturdy|heavy — любой поднабор) ×
  pieces[{ protectedAreas[], рейтинги физ/энерг/рад, weight, cost, rarity }] };
  влияния на частях-записях. Помощники мастера: «скопировать значения на все
  части», «создать тир по образцу».
- **Одежда**: группа { clothingType (список или свой), allowsArmor } + предметы
  { protectedAreas[], рейтинги, weight, cost, rarity }; мод-категории — как в
  данных одежды (плетение/подкладки), выбор чекбоксами; влияния.

## 4. Влияния: модификаторы и цепочки (хуки)

### 4.0. Принцип (вариант Б, утверждён владельцем)

Предмет несёт массив **влияний**. Простое влияние = один модификатор при
триггере «надели/в руках». Сложное = **дерево влияний** от стартового условия:
узел-условие имеет ветки `yes`/`no`, в каждой — свои шаги, вложенность
неограничена. **Логика — только данными**: никакого пользовательского JS
в паках (владелец спрашивал про «effects.js рядом с json» — отклонено как
риск: чужой код в контексте приложения = доступ к сейвам/токенам, нет
валидации, время исполнения; закон §0.8 не отменяется). Дерево конечное по
построению (циклы невозможны), валидатор идёт по нему рекурсивно, ошибки —
с путями. UI-форма дерева — вложенные вертикальные блоки «Условие ▸ да/нет»
(как карточки-контейнеры Power Automate), не свободный холст.

Прецедент-модель уже в приложении: расходники — данные со строками-ссылками
(`"STR": "+1"`, `removeCondition`, `cure_addictions`), формулы — в
`domain/effects.js`. Пак — ещё один источник таких же ссылок; движок
растёт механиками патчами, генератор их комбинирует.

**Алфавит и слова (решение по возражению владельца «миллион пилюль»).**
Патч нужен под новую **букву алфавита**, не под вариант предмета. Миллион
вариаций — миллион слов из конечного алфавита универсальных примитивов:
система модификаторов (цели-шаблоны `disease.*`, `attribute.*`, `skill.*`,
`addiction.*`…; операции add/sub/set/mult/div; булевы цели —
`set: immune` обычным модификатором), `scheduler { everyGameHours, do,
missed }` (единая буква для доз/яда/регенерации/проклятий — `doseTimer` и
`withdrawalTick`-как-отдельные-механики отменяются, это scheduler + add),
состояния, урон/лечение, потребности. Контрольная задача «пилюля» целиком
пишется этими двумя буквами. Граница осознанная: операции — только
арифметика над целями, повторения — только scheduler, ветвления — деревом;
новая буква (что-то неигровое, вроде перекраски UI) — по закону §0.8.
**Гейт этапа 1: тест на невиданную комбинацию** — интерпретатор кормится
случайно сгенерированными комбинациями примитивов (property-based): итог
верен, порядок op-групп соблюдён, недопустимые пары «форма/цель»
отвергаются валидатором с путём (типизация целей: числовые/булевы/
коллекции).

```jsonc
{
  "trigger": "equipped",                 // стартовое условие из реестра хуков
  "steps": [
    { "if": { "type": "hasState", "stateId": "rad_poisoning" },   // необяз.
      "kind": "modifier",
      "target": "attribute.STR",         // SPECIAL трогать можно
      "op": "add", "value": 1 },          // add|sub|set|mult|div
    { "kind": "mechanic",
      "mechanicId": "applyState",         // сложная механика из реестра
      "params": { "stateId": "inspired", "scenes": 2 } }
  ]
}
```

### 4.1. Модификаторы (фиксированная форма)

- `target` — из **реестра целей** `src/itempack/targets.js`: производные
  (макс. ОЗ, макс. вес, инициатива, защита, бонус ближнего боя, ОД),
  **атрибуты S.P.E.C.I.A.L.**, навыки, рейтинги урона защиты по типам,
  параметры надетого предмета (урон оружия в руках и т.п.).
- `op` — `add | sub | set | mult | div` (по слову владельца).
- Порядок применения: `set` → `mult`/`div` → `add`/`sub` (приоритет групп,
  внутри группы — порядок источников). Зафиксировать тестами.
- **Интеграция в движок:** атрибутные влияния идут через тот же путь, что и
  существующие `getTimedAttributeModifiers` (химия/расходники) — один закон
  агрегации атрибутов, производные пересчитываются существующим каскадом МК.
  Второй параллельный путь запрещён.

### 4.2. Реестры (что можно выбирать; расширение — только патчем движка)

Собираются из **текущих** механик (этап 0: инвентаризация по коду + тест-снимок;
источники: `domain/effects.js`, `domain/diseaseConditions.js`, выживание/потребности,
состояния экипировки, рабочие перки/черты):

- **Хуки (стартовые условия) — кандидаты:** `equipped` (надели/в руках),
  `unequipped`, `stateGained`, `stateLost`, `damageTaken` (парам: тип урона),
  `sceneStart`, `always` (для фон-перков — резерв под будущие типы).
- **Условия (фильтры шагов) — кандидаты:** `needsAtLeast` {need,level}
  (голод/жажда/сон), `radiationAtLeast` {N}, `hasState` {stateId},
  `originIs` {originId}, `weaponTypeInHands` {weaponType}, `attributeAtLeast`/
  `attributeBelow` {attr,value} — по образцу проверок существующих перков.
- **Сложные механики (шаг-механика) — кандидаты:** `applyState {stateId,scenes}`
  / `removeState`, `applyTimedEffect {…}` по образцу расходников
  (атрибуты/ОЗ/защита на N сцен), `damage {type,amount}`, `heal {target,amount}`,
  `needsDelta {need,delta}`, `radiationDelta {amount}`, `addictionRoll {level}`
  (образец — `checkAddiction`), `counterTargetModifier` (модификатор на
  параметр враждебного предмета — резерв).

Пустые/спорные кандидаты режутся на этапе 0 по факту инвентаризации;
новые добавляются только патчем движка + пересборкой генератора (закон §0.8).

### 4.3. Применение

Надевание/снятие и смена условий/сцен пересчитывают активные взносы;
источник виден в UI («+1 к Силе (Потрошитель Марии)»). События механик
(наложено состояние, урон) идут в существующий журнал событий игры.
Сейв: активные взносы пересчитываются, историю не плодим.

## 5. Генератор (item-forge): UI

Стек: **Vite + React + TS**, порт 5173, статика в `item-forge/dist/`.
**Оформление в стиле экранов приложения** (палитра — `item-forge/src/theme.js`,
панели/окна/кнопки как в приложении). Длинные окна — по закону владельца:
заголовок и действия зафиксированы, контент скроллится.

- **Выбор типа** — экран-плитки **по образцу окна категорий крафта**
  (`CraftingModal`): плитки по 3 в ряд («Оружие», «Броня», «Одежда»;
  задел «Происхождение/Черта/Перк/Мод» — скрыты до своих этапов),
  углубление внутрь плитки, кнопка «назад» в заголовке.
- Дальше мастер: **категория** (существующая или своя — с предупреждением
  для оружия; для брони = имя семейства) → **параметры** (форма по
  fieldSchema) → **моды-совместимость** (для оружия/брони: слоты/категории)
  → **влияния** → **имена** → **Экспорт**.
- **Редактор влияний (Power-Automate-стиль):** вертикальный список:
  карточка «Стартовое условие» (выбор из реестра хуков) → [+] → шаг
  (карточка выбора: «Простой модификатор» или «Сложная механика») →
  параметры шага (цель/операция/значение или тип механики + её поля) →
  [+] … Каждый шаг может иметь строку-условие из каталога. Порядок шагов —
  стрелки вверх/вниз; удаление — крест. Без мини-карты и drag-and-drop
  в v1 (дорого, не критично).
- **Экспорт/Импорт**: экспорт — кнопка, валидация (список ошибок с путями),
  скачивание `<packId>.content.json`; импорт своего файла обратно в мастер
  (итерации), несколько предметов в одну сессию-файл.
- **Превью**: карточка предмета компактно (параметры + влияния текстом,
  иконка заглушки при пустой картинке).

Тесты генератора: билдер экспорта, round-trip импорт/экспорт, набор гейт-кейсов
«экспорт проходит валидатор». UI — smoke-рендеры ключевых шагов.

## 6. Загрузчик в основном приложении

- Точка входа v1: окно **«Игровой сеттинг»**, рядом со списком паков —
  «Загрузить пак контента» (файл `.content.json`). Путь: прочитать →
  `validateContentPack()` → отчёт (N предметов, имя пака / ошибки с путями)
  → подтверждение.
- Хранение: реестр + содержимое в AsyncStorage (как `settingPackStore`) —
  состояние устройства, не сейв.
- Оверлей: предметы паков в снаряжении/лавке/добавлении с пометкой
  «пак: <name>»; продажа/нахождение — **стандартно**, по тем же законам
  данных (решает движок: rarity/cost), специальной обработки нет.
- **Удаление пака — полное, без следов** (решение владельца): экземпляры
  предметов пака удаляются из инвентарей и надетых слотов всех персонажей;
  имена не снапшотятся. Диалог подтверждения сообщает масштаб («в паке
  N предметов у M персонажей — удалится всё»).
- Механика влияний включается только для надетых/в руках предметов паков;
  ваниль без изменений поведения (зелёным остаётся весь существующий сьют).

## 7. Этапы и гейты

После каждого этапа: typecheck основного приложения, `npm test` зелёный,
сборки обоих приложений, документы обновлены.

**Будущее после этапа 5 (отдельными сериями, каркас уже готов):**
- типы **origin / trait / perk** — те же плитки + цепочки; триггеры профиля
  (`characterCreated`, `levelUp`, `restEnd`…): некоторые потребуют правки
  движка — по закону §0.8;
- тип **мод** (собственные улучшения) — к модеркам существующих категорий;
- событие-урон по цели («поражен целью ») и цепочки с внутрибоевыми хуками —
  после экрана сражений.

## 8. Решённые вопросы владельца (2026-10-19)

1. **Удаление пака — полное, без следов** (см. §6): экземпляры удаляются
   вместе с паком, диалог сообщает масштаб.
2. **Продажа/нахождение — стандартно** по законам данных (лавка/лут);
   движок умеет из коробки.
3. **Хостинг генератора — отдельный** статический деплой.
4. Совместимые моды для домашнего оружия: полный каталог с фильтром
   по слоту (рабочее предложение; уточнит прогон владельца на этапе 3).

## 9. Интерпретатор: добавить, не переписывать (ответ владельцу)

Архитектурное решение: интерпретатор влияний — **новый чистый модуль
(domain-пакет)** на входе существующей агрегации, а не переделка движка.
Он переводит JSON-дерево в список активных взносов (Contribution[])
**тех самых потоков**, которые движок уже суммирует сегодня (прецедент:
`chems.json` → `domain/effects.js` → единый сумматор). Не переписывается:
агрегация производных, сторы, сейвы (выход интерпретатора выводим —
миграций старых сейвов нет; персистентно только состояние живущих
scheduler-тикеров, по образцу списка эффектов). Точечные патчи, чтобы
существующие точки «уважали стек»: наложение болезней — проверка
`immune: disease.*`; `checkAddiction` — immune/exceptSelf; навыки как
цель — модификатор на total; scheduler подписывается на существующие
игровые часы. Направление — в сторону `modifiers-vision.md` (каждый
источник переводится в общий язык), но полное слияние — отдельный проект,
этой фичей не требуется.

**Не входит (осознанно):** расходники/хлам/роботы и их части, торговцы
спавном, уникальные качества экземпляра, многоязычия сверх «1 локаль + id»,
свои damageType/навыки, пользовательский код в паках — никогда.
