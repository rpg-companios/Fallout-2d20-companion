# Аудит разделения «движок + сеттинг»

Дата: 2026-08-15. Ветка: `arena/01a0050b-fallout-2d20-companion`.
Статус на момент аудита: коммит 2b8843c. Актуально после патчей 96–101 (коммиты bde4eb2…83be478).

Цель: выяснить, что уже реализовано для разделения программы на универсальный движок и сеттинг (Fallout 2d20), что осталось и как двигаться дальше.

---

## 1. Целевая модель (решения владельца, 2026-08-15)

- **Сеттинг** — `modules/fallout/`: только контент (данные предметов, i18n-имена), никакой логики.
- **Движок** — `domain/`, `src/store/`, `components/`, `db/`, `i18n/` (общие механизмы); `data/` — временная «пустая движковая база» (для перенесённых категорий файлы опустошены до `[]`).
- **Модульность данных — обязательна.** Одна категория = отдельный файл (и подпапка); категории не смешиваются (еда и напитки — раздельно, любая категория может вырасти в разы). Переводы повторяют строение данных (зеркало раскладки) — для удобства поддержки.
- **Модуль — единственный источник данных.** После полного переноса `data/` удаляется, merge-механизм (база + модуль) из реестра/каталога убирается. Фолбэки и нормализация разнородных форматов запрещены; если данных нет — запросить.
- **Прямая работа с данными — приоритет**: потребители читают файл-владельца напрямую (без прослоек слияния); обогащение (механика + i18n из своих файлов) — там, где нужно для отображения (каталог), без фолбэков.
- **БД — только состояние.** SQLite/AsyncStorage хранят персонажей и настройки между запусками. Все игровые данные живут в файлах. Сейвы хранят id и экземплярные данные; при загрузке предметы обогащаются из файлов; сейвы мигрируются на новый формат во время загрузки (`src/store/migrations.js`) — изменение формата данных не должно ломать сейвы.
- **Данные динамичны**: меняются, обогащаются, влияют на другие данные и/или подменяют их. Отображение и расчёт предмета — единый конвейер (база → моды → уникальные качества → свойства), чтобы имя/статы считались одинаково во всех местах. Урок: баг «модифицированное оружие комплекта — в одном месте имя без модов, в другом с модами, но моды не считались и новые не ставились».
- **Будущие механики**: уникальные моды, применимость которых зависит от типа оружия, его параметров, перков и наличия других модов (меняют/дополняют/соседствуют); свойства, получаемые крафтом или иным образом и прикрепляемые к предметам в процессе (не числятся изначально или числятся на части id/категорий/по фильтру).
- **UI и его переводы переезжают в модуль** (полный перенос; очередь после данных).
- **Настройки — часть сеттинга (решение владельца, 2026-08-15)**: механики
  сеттинга описываются в `modules/<id>/settings.json` (данные: id, type,
  секции, дефолты, dependsOn); значения хранятся по модулям
  `{ [moduleId]: { [settingId]: value } }` — разные сеттинги не смешиваются.
  Движковые UI-настройки (каталоги персонажей, вид карточек) — встроенный
  ENGINE_SETTINGS (исключение: у движка они есть). Язык интерфейса —
  настройка сеттинга (select из locales). (Патч 120.)
- **Упакованные сеттинги (требование владельца, 2026-08-15)**: скоро появится
  новый модуль-сеттинг; программа должна уметь загружать УПАКОВАННЫЕ сеттинги
  по выбору пользователя. Фундамент уже есть: `modules/<id>/manifest.json`
  (id/name/version/requiresCore/locales), модуль самодостаточен (данные + i18n
  внутри, без чтения data/). Механизм выбора/загрузки пакетов (UI настроек,
  распаковка, активация модуля, переключение каталога на активный модуль)
  проектируется отдельным дизайн-патчем — перенос данных продолжается так,
  чтобы каждый модуль оставался автономным пакетом.

### 2.4 Механика чтения

- `domain/registry.js` — origins/traits/uniqQualities читаются из модуля (merge-слой для origins/traits убран в патче 117; `mergeArraysById` остался только для uniq_qualities).
- `i18n/equipmentCatalog.js` — сборка каталога: механика из data/ или модуля + имена из i18n (mergeById, строгий контракт: нет имени → throw). Расходники (chems/drinks/food/magazines) возвращаются без нормализующего валидатора (удалён в патчах 99–100).
- `i18n/conditionsCatalog.js` — болезни читаются только из модуля (патч 98).
- `components/screens/CharacterScreen/logic/RandomLootLogic.js` — лут и стабы читаются напрямую из модуля (решение владельца, патч 101).
- `db/catalogSource.js` — прослойка, воспроизводящая «row shape» старой БД поверх каталога.
- Контракт-тесты разделения: `module-data-move`, `conditions-module-move`, `chems-module-move`, `magazines-module-move`, `loot-module-move`, `module-i18n-structure`, `module-data-structure`, `equipment-kits-split/*`, `i18n/no-fallbacks`.

Канонизация данных (например `itemType`) — вместе с переносом категории.

## 5. Открытые вопросы (на решение владельца)

Решены (2026-08-15): модель — модуль единственный источник; i18n и данные модуля — зеркало легаси; базы категорий переносятся целиком; UI — в модуль (после данных); порядок — мелкие категории сначала (выполнено).

Осталось решить по ходу:
1. Статус `bodyplans` — движковые данные или контент сеттинга (`weapon_mod_slots` — решено: контент, п. 4 плана).
2. Инверсия `domain/kitResolver.js`, `domain/skillRewards.js` → импортируют `RandomLootLogic` из `components/` — куда перенести при разборе UI-слоя.
3. `resolveItem.js` — двойные case `'chem'/'chems'`, `'robotLeg'/'robotLegs'` и т.п. для старых сохранений: оставить как совместимость сейвов или мигрировать сейвы и убрать.
4. Конвейер обогащения предмета (п. 9 плана) — проектируется с владельцем: формат «база → моды → качества → свойства», единое имя/статы во всех местах.
