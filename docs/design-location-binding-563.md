# Привязка к локации: один закон на обе стороны (патч 563)

Слово владельца:

> «Я всё ещё в локации не могу перемещать сущности. И нужна тождественность
> привязки терминалов/замков к локации и наоборот. Если я в терминале/замке
> выбираю локацию, то они туда встраиваются. А не только через локацию.»

Уточнения, полученные вопросами: сломано **перетаскивание порядка строк** в
дереве; поле «Локация» у терминала/замка **есть, но выбор ничего не делает**;
сущность **может** жить в нескольких локациях («например, "бродячий" торговец»);
перетаскивание должно делать **и порядок, и переезд**.

## 1. Почему ручка в дереве ничего не делала

React Native Web опрашивает владельца жеста пропсами системы ответственности:

```
onStartShouldSetResponder[Capture]
onMoveShouldSetResponder[Capture]
onResponderGrant / Move / Release / Terminate / Reject
```

Хук `src/ui/useDragResponder.js` собирал `panHandlers` и `handlersFor` из
**имён конфига** (`onStartShouldSetPanResponderCapture`, `onPanResponderGrant`,
…). У `View` таких пропсов нет — вызов не приходил, `activeDragRef` оставался
пустым, `finishDrag` не срабатывал. Сетка карточек работала только потому, что
подписывалась на ответ **самого** PanResponder (`panHandlers` в чистом виде),
а не на собственный пересобранный объект. Отсюда «в сетке двигается, в дереве
нет» — два пути через один и тот же код.

**Исправление.** `withRowPayload(rowPayload)` оборачивает именно responder-пропсы:
каждый сначала зовёт исходный обработчик PanResponder (он сам решает про фазу),
затем заявляет нагрузку строки через `claim(rowPayload)`. Имена конфига остались
там, где их читает `PanResponder.create`.

## 2. Где живёт привязка

Ссылка всегда хранится **в родителе**, и полей ровно два:

| Что | Где ссылка |
| --- | --- |
| локация внутри локации | `child.parentLocationId` |
| сундук / торговец / терминал / замок | `hub.links[].containerId` |

До 563 существовали две независимые правки: форма предмета знала только свои
поля, дерево — только свои. Поэтому «через локацию работает, из терминала нет».
Теперь решение принимается одной чистой функцией в `domain/hubBindings.js`:

* `locateContainer(container, allContainers)` — где сущность сейчас (одна точка
  правды для формы, дерева и баннера);
* `planLocationBinding({ container, primaryHubId, extraHubIds, allContainers })` —
  что записать: `containerPatch` для самой сущности и `hubUpdates` для локаций;
* `planMoveIntoLocation({ container, targetHubId, fromHubId, allContainers })` —
  переезд: из источника снять, в цель добавить, прочие привязки не трогать.

Новых полей у ребёнка не появляется. Иначе появятся две правды, которые
разъедутся при первом же переносе, — ровно то, что и случилось.

## 3. Несколько локаций

Основная локация идёт первой в `links` (её и читают карточка и дерево),
дополнительные — после неё. Снятие из одной локации не трогает остальные:
«бродячий» торговец остаётся там, где стоял. `inRoot` — не флаг «вложенности», а
следствие: сущность с корня уходит, если у неё есть хоть одна локация, и
возвращается, когда локаций не осталось.

## 4. Что видит Мастер

- **Параметры терминала/замка/торговца/сундука.** Сверху «Локация» — обычное
  поле выбора, как «Родительская локация» у локации. Ниже «Ещё локации» — поиск
  по складу для тех редких случаев, когда сущность нужна в нескольких местах.
- **Набранное не теряется молча.** Если в поле что-то набрано, но вариант не
  выбран, сохранение останавливается с подсказкой: раньше текст просто исчезал
  вместе с привязкой.
- **Дерево локации.** Ручка перетаскивает строку: среди соседей — порядок,
  на строку-локацию — переезд внутрь (переезд приоритетнее). Перенос в
  собственного потомка отклоняется.
- **«Добавить в локацию»** открывает выбор существующих вещей; оттуда же можно
  создать новую — она сразу встанет в открытую локацию (поле «Локация»
  предзаполнено).

## 5. Проверки

`__tests__/room/location-binding-563.test.js` — 13 проверок поведением, а не
поиском строк в исходнике:

1. закон привязки: где живёт ссылка, порядок основной/дополнительных, возврат на
   корень, переезд с сохранением третьей локации, вложенная локация двигается
   полем родителя;
2. драг в дереве на смонтированном экране: порядок доходит до БД; бросок на
   строку-локацию переносит сущность; нажатие без движения ничего не меняет;
3. «Добавить в локацию» действительно открывает выбор;
4. форма терминала: выбор локации пишет ссылку в неё и снимает с корня;
   дополнительная локация не теряется; набранный-но-не-выбранный текст даёт
   подсказку вместо тихой потери;
5. создание сундука из локации кладёт его в эту локацию.

Старые моки `PanResponder: { create: (config) => ({ panHandlers: config }) }`
переделаны на честные (props системы ответственности → обработчики конфига):
549, 548, 545. Из-за них и жил баг.
